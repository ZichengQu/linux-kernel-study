# Linux 内核内存管理：一小时面试版

> 目标：面向通用 Linux 岗，在一小时内建立可以回答常见面试追问的内存管理框架。
>
> 阅读方法：先掌握地址转换、分配、回收三条主线，再看排障与高频问答，最后用末尾速记复习。

**缩写约定：** MMU（Memory Management Unit，内存管理单元）、TLB（Translation Lookaside Buffer，地址转换缓存）、VMA（Virtual Memory Area，虚拟内存区域）、PFN（Page Frame Number，页帧号）、NUMA（Non-Uniform Memory Access，非统一内存访问）、COW（Copy-On-Write，写时复制）、LRU（Least Recently Used，最近最少使用）、OOM（Out Of Memory，内存耗尽）、RSS（Resident Set Size，常驻内存集）、DMA（Direct Memory Access，直接内存访问）、CMA（Contiguous Memory Allocator，连续内存分配器）、KASAN（Kernel Address Sanitizer，内核地址消毒器）。

## 1. 一张总图串起 Linux 内存管理

```text
进程使用虚拟地址
    ↓
MMU 查询 TLB；未命中时查询多级页表
    ↓
找到物理页，或触发 page fault
    ↓
内核按需建立映射、分配物理页或从文件/swap 读入
    ↓
物理内存由 node → zone → struct page 描述
    ↓
整页主要由 buddy 分配，小对象主要由 SLUB 分配
    ↓
文件数据尽量缓存在 page cache
    ↓
空闲页低于水位时进行 reclaim、writeback 或 swap
    ↓
仍无法满足分配时，可能触发 OOM killer
```

面试时可以概括为：

> Linux 用虚拟内存隔离进程，以页表建立虚拟页到物理页的映射；物理页由 node、zone 和 `struct page` 描述，整页由 buddy 管理、小对象由 SLUB 管理。内存紧张时先回收 page cache、匿名页和可回收 slab，必要时使用 swap，最终无法满足分配约束才进入 OOM。

### 1.1 三条学习主线

```text
地址主线：虚拟地址 → TLB/页表 → 物理地址
分配主线：分配请求 → PCP/buddy → SLUB 等上层分配器
压力主线：watermark → kswapd/direct reclaim → swap/OOM
```

## 2. 为什么需要虚拟内存

进程看到的是虚拟地址空间，而不是直接使用机器物理地址。
虚拟内存主要解决：

```text
隔离：一个进程不能随意访问另一个进程的内存
保护：页表可设置读、写、执行和用户/内核权限
抽象：每个进程都可拥有看似连续的地址空间
共享：多个虚拟地址可以映射同一物理页
按需分配：只给真正访问的虚拟页分配物理页
文件映射：文件内容可以直接映射进进程地址空间
```

虚拟地址空间很大，不代表系统已经分配了同样多的物理内存。

### 2.1 进程地址空间

典型用户进程可以抽象为：

```text
低地址
├── 代码段 text
├── 只读数据
├── 数据段 data / bss
├── heap，通常向高地址增长
├── mmap 区域：共享库、文件映射、匿名映射
├── stack，通常向低地址增长
└── 内核保留范围
高地址
```

具体布局、地址宽度和增长方向依体系结构、ABI、随机化及内核配置而异，不应死背固定地址。

### 2.2 mm_struct 和 VMA

```text
task_struct
    ↓
mm_struct：描述一个进程的整个用户地址空间
    ├── 页表根
    ├── 地址空间统计和锁
    └── 一组 VMA

VMA：一段连续、属性相同的虚拟地址范围
    起止地址
    读/写/执行权限
    匿名映射或文件映射
    共享或私有属性
```

同一进程的线程通常共享 `mm_struct`，所以线程共享地址空间；`fork()` 创建的子进程拥有逻辑上独立的地址空间。

VMA 只说明“这段地址是否合法、有什么属性”，不代表其中每一页已经有物理页或页表项。

### 2.3 brk、mmap 和 malloc

```text
brk/sbrk：调整传统 heap 边界
mmap：创建文件或匿名虚拟映射
malloc：用户态分配器接口，内部可能使用 brk 或 mmap
```

`malloc()` 成功通常只表示获得了虚拟地址和提交许可；物理页往往在首次访问发生缺页时才真正分配。

## 3. 虚拟地址如何转换成物理地址

典型分页系统把虚拟地址拆成：

```text
虚拟地址
├── 多级页表索引
└── 页内 offset
```

转换过程：

```text
CPU 发出虚拟地址
    ↓
查询 TLB
    ├── 命中：直接得到物理页号和权限
    └── 未命中：硬件或体系结构相关代码遍历多级页表
            ↓
        找到 PTE 中的物理页号
            ↓
物理页基址 + 页内 offset = 最终物理地址
```

页表项除物理页号外，还包含：

```text
present/valid
read/write/execute 权限
user/kernel 权限
accessed/young
dirty
体系结构相关属性
```

### 3.1 TLB 为什么存在

如果每次内存访问都遍历多级页表，一次 load/store 会引入多次额外内存访问。
TLB 缓存近期虚拟页到物理页的转换和权限：

```text
TLB hit：快速完成地址转换
TLB miss：进行 page-table walk，再把结果填入 TLB
```

修改页表后，旧 TLB 项可能仍存在，所以内核需要在适当范围执行 TLB invalidate/flush。

### 3.2 为什么 TLB shootdown 昂贵

多核系统中，同一个地址空间可能正在多个 CPU 上运行：

```text
CPU0 修改页表
    ↓
通知使用该地址空间的其他 CPU
    ↓
其他 CPU 清除对应 TLB 项并确认
```

这包含处理器间中断和同步开销，因此频繁修改映射会影响性能。

### 3.3 大页的收益与代价

大页用一个页表项覆盖更大范围：

```text
收益：更少页表项、更高 TLB 覆盖率、减少 TLB miss
代价：内部碎片、连续内存需求、回收迁移和拆分页更复杂
```

HugeTLB 和 Transparent Huge Page（THP，透明大页）机制不同，面试中知道目标和权衡即可。

## 4. page fault、按需分页与 COW

### 4.1 page fault 不一定是错误

CPU 访问虚拟地址时，页表项不存在或权限不符，会产生 page fault（缺页异常/页故障）。
内核先检查对应 VMA：

```text
地址不属于合法 VMA
    → 通常向进程发送 SIGSEGV

地址合法但物理页尚未建立
    → 分配页、读文件或从 swap 换入，再建立页表

写只读 COW 页
    → 复制物理页并建立可写私有映射

真正权限违规
    → 发送相应信号
```

因此 page fault 既可能是正常的按需分页，也可能是真正的非法访问。

### 4.2 minor fault 和 major fault

```text
minor fault
    解决缺页不需要从磁盘读取目标页
    例如首次匿名页分配、已有 page cache 映射

major fault
    通常需要从存储读取文件页或 swap 页
    延迟显著更高
```

分类细节随路径而异，但面试重点是“是否需要昂贵 I/O”。

### 4.3 按需分页

```text
mmap 或 malloc 获得虚拟范围
    ↓
不立即为所有地址分配物理页
    ↓
进程首次访问某页
    ↓
page fault
    ↓
内核分配/查找物理页并建立映射
```

这样可以降低启动成本，并避免为从未访问的地址浪费物理内存。

### 4.4 fork() 的 COW

`fork()` 后父子进程需要逻辑独立，但内核不立即复制所有数据页：

```text
父进程页表 ──┐
              ├── 暂时指向相同物理页
子进程页表 ──┘
      页表项设置为只读/COW 语义
```

某一方写入时：

```text
发生写保护 page fault
    ↓
内核分配新物理页
    ↓
复制旧页内容
    ↓
修改写入方页表指向新页并恢复写权限
```

所以 `fork()` 的物理数据页主要采用 COW，但仍需要建立子进程的地址空间、VMA 和页表等管理状态。

## 5. Linux 怎样描述物理内存

核心关系：

```text
system
└── node：一个 NUMA 内存节点，常用 pg_data_t 描述
    └── zone：满足特定寻址/迁移约束的物理内存区域
        └── page frame：固定大小物理页帧
            └── struct page：内核为页帧维护的元数据
```

### 5.1 node 与 NUMA

NUMA 机器中，不同 CPU 访问不同内存节点的代价可能不同：

```text
本地 node：通常延迟更低、带宽更好
远端 node：可能通过互连访问，代价更高
```

内核默认倾向于就近分配，但实际结果还受内存策略、cpuset、节点水位和 fallback 影响。

### 5.2 zone

zone 用于表达体系结构或用途约束，常见概念包括：

```text
ZONE_DMA / ZONE_DMA32：受设备寻址能力约束的区域
ZONE_NORMAL：内核可正常直接使用的内存
ZONE_HIGHMEM：主要见于部分 32 位架构，不能永久直接映射
ZONE_MOVABLE：尽量放置可迁移页面
```

不是每种体系结构都具有所有 zone，也不要把 zone 当成用户进程的虚拟地址分区。

### 5.3 struct page 和 PFN

PFN 是物理地址除以页大小得到的页帧编号：

```text
physical address = PFN × PAGE_SIZE + offset
```

`struct page` 是物理页的管理元数据，可能记录或复用：

```text
引用和映射状态
LRU/链表信息
匿名页或文件映射信息
slab、buddy、compound page 等状态
```

`struct page` 不是物理页内容本身。

## 6. buddy：整页分配器

buddy system（伙伴系统）按 2 的幂次管理连续物理页块：

```text
order 0：1 页
order 1：2 页
order 2：4 页
...
order n：2^n 页
```

分配时如果目标 order 没有空闲块，就拆分更大的块；释放时如果伙伴块也空闲，就逐级合并。

### 6.1 为什么使用 buddy

```text
分配和释放整页较快
容易合并相邻空闲块
能提供一定规模的物理连续页
结构适合按 order 管理
```

### 6.2 内存很多为何高阶分配仍失败

系统可能有很多空闲页，但它们不连续：

```text
空闲总量足够
    ≠
存在足够大的连续物理页块
```

高阶分配会受外部碎片、不可迁移页、pin 页和 zone 约束影响。内核可尝试 compaction，把可迁移页搬走以形成连续区域，但不保证成功。

### 6.3 per-CPU pageset

频繁的低阶页分配通常先访问 Per-CPU Pageset（PCP），再批量与 buddy 的全局 free area 交换页面，以减少锁竞争并提高多核扩展性。

面试中可把它理解成 buddy 前面的 per-CPU 快速缓存，而不是另一套独立物理内存来源。

## 7. SLUB：小对象分配器

如果一个内核对象只有几十或几百字节，直接分配整页会严重浪费。
SLUB 在 buddy 提供的页上切分对象：

```text
buddy 提供一个或多个页
    ↓
组成 slab
    ↓
slab 切成多个同类型或同尺寸 object
    ↓
kmem_cache / kmalloc cache 管理这些 object
```

### 7.1 性能来源

```text
对象复用，减少反复初始化和整页分配
per-CPU 当前 slab/freelist，降低公共锁竞争
按尺寸或类型组织，快速找到可用对象
部分空闲 slab 可继续服务分配
```

### 7.2 kmem_cache 和 kmalloc

```text
kmem_cache_create/alloc/free
    为特定对象类型建立专用 cache

kmalloc/kfree
    使用内核预建的通用尺寸 cache
```

大多数普通驱动和子系统先考虑 `kmalloc()`；只有确实需要构造、对齐、统计或复用特性的对象才考虑专用 cache。

### 7.3 buddy 与 SLUB 的关系

```text
buddy：管理物理页块
SLUB：从 buddy 取得页，再管理页内小对象
```

二者不是竞争关系，而是上下层关系。

## 8. kmalloc、vmalloc 与 GFP flags

### 8.1 kmalloc 和 vmalloc

| 接口           | 虚拟地址连续 |                       物理地址连续 | 典型用途                                   |
| -------------- | -----------: | ---------------------------------: | ------------------------------------------ |
| `kmalloc()`  |           是 |                             通常是 | 小到中等内核对象、需要直接映射属性的缓冲区 |
| `vmalloc()`  |           是 |                                 否 | 较大且只要求虚拟连续的内核缓冲区           |
| `kvmalloc()` |           是 | 先尝试 kmalloc，必要时退到 vmalloc | 可接受两种后端的大块普通内存               |

`vmalloc()` 需要单独建立页表映射，访问局部性和映射管理成本通常高于 `kmalloc()`；它也不能替代 DMA API。

大块 `kmalloc()` 需要高阶连续物理页，运行时间越长越容易受碎片影响，所以不要无理由申请巨大连续块。

### 8.2 GFP_KERNEL

```text
允许阻塞
可以进行直接回收
可能触发文件系统或 I/O 相关路径
适用于普通可睡眠进程上下文
```

### 8.3 GFP_ATOMIC

```text
不能睡眠
只进行非常有限的回收或使用保留资源
适用于 hardirq、持有自旋锁等原子上下文
更容易分配失败
```

`GFP_ATOMIC` 的意思不是“分配动作由 CPU 原子完成”，也不保证成功。

### 8.4 如何选择

先问当前上下文能否睡眠：

```text
普通进程/线程上下文：通常 GFP_KERNEL
hardirq、spinlock 临界区等不可睡眠上下文：GFP_ATOMIC
```

实际代码还要考虑 DMA、zeroing、movable、reclaim 等约束，不要只凭对象大小选 flag。

## 9. page cache、dirty page 与 writeback

### 9.1 page cache

page cache 缓存文件内容：

```text
第一次 read：存储设备 → page cache → 用户缓冲区
后续 read：page cache → 用户缓冲区

普通 write：用户数据 → page cache，页面标 dirty
稍后 writeback：dirty page → 存储设备
```

它利用原本闲置的内存减少 I/O，因此 Cached 很高通常是正常现象。

### 9.2 clean 和 dirty 文件页

```text
clean page cache
    内容与后备文件一致
    内存紧张时可以直接丢弃，以后重新读取

dirty page cache
    内存内容比磁盘新
    通常要先写回，之后才能安全回收
```

dirty page 太多可能引发 writeback 压力和业务写入节流。

### 9.3 write()、fsync() 和 close()

普通 `write()` 返回时，数据可能只进入 page cache；`close()` 也不等价于保证数据已经持久化。
需要持久化语义时通常使用 `fsync()`、`fdatasync()` 或应用/文件系统规定的同步方式，并理解磁盘、控制器缓存及文件系统语义。

### 9.4 buffered I/O 与 mmap

普通 buffered I/O 和文件 `mmap()` 都可能使用同一套 page cache，只是用户访问路径不同：

```text
read/write：通过系统调用复制数据
mmap：把文件页映射进进程地址空间，通过 page fault 建立映射
```

## 10. MemFree 低为什么不等于内存不足

Linux 会积极使用空闲内存做 page cache 和可回收内核 cache。
重点字段：

```text
MemTotal：内核可管理的内存总量，不一定等于内存条标称容量
MemFree：当前完全空闲的页
MemAvailable：估算在不引起明显压力时还能提供的内存
Cached：主要包括文件 page cache 的相关统计
Buffers：块设备相关缓存统计
SReclaimable：可回收 slab
SUnreclaim：不易回收 slab
Dirty/Writeback：脏页和正在回写的页
SwapTotal/SwapFree：swap 容量与剩余量
Committed_AS/CommitLimit：提交量与策略限制
```

基础判断：

```text
MemFree 低、MemAvailable 高：通常只是 cache 使用充分
MemAvailable 持续很低：存在真实内存压力
Swap 持续换入换出：可能发生抖动
SUnreclaim 持续异常增长：关注内核对象或驱动泄漏
Dirty/Writeback 长期很高：关注存储回写瓶颈
```

## 11. 页面回收 reclaim

### 11.1 watermark

每个 zone 维护水位，简化理解：

```text
空闲页低于 low：唤醒 kswapd 后台回收
kswapd 努力把 zone 恢复到较安全水位
分配压力更高或无法满足请求：分配者可能进入 direct reclaim
```

具体判断还涉及 order、zone、reserve、watermark boost、分配 flags 和内核版本，不能把“全机 free 数字”当成唯一条件。

### 11.2 kswapd 和 direct reclaim

```text
kswapd
    后台内核线程
    提前补充空闲页
    业务进程不必每次亲自回收

direct reclaim
    申请内存的 task 自己扫描回收
    task 的分配延迟明显增加
    频繁出现通常说明内存压力或回收效率差
```

### 11.3 回收哪些页

```text
clean file page：可直接从 page cache 丢弃
dirty file page：通常需要先 writeback
anonymous page：若可交换，可写入 swap 后释放物理页
reclaimable slab：通过 shrinker 等机制回收
mlock/pinned/部分内核页：通常难以或不能回收
```

### 11.4 LRU 的正确理解

Linux 会根据访问情况区分冷热页，优先扫描更可能不再使用的页面。
传统讲解常使用 active/inactive、file/anon LRU；现代内核也可能启用 Multi-Gen LRU（MGLRU，多代 LRU）。

面试重点是：

```text
识别冷热
平衡文件页与匿名页
避免回收活跃页
控制扫描、回写和 swap 成本
```

不要把某个版本的链表和函数名当成永恒接口。

### 11.5 reclaim 为什么导致卡顿

```text
direct reclaim 阻塞业务分配
回收 dirty page 触发或等待 I/O
匿名页换出/换入产生存储访问
扫描大量不可回收页却释放很少
高阶分配同时要求 compaction
多个任务并发回收造成抖动
```

## 12. swap、thrashing 和 zRAM

### 12.1 swap 做什么

匿名页没有普通文件作为后备。内存紧张时，可把不活跃匿名页写入 swap：

```text
匿名物理页 → swap slot
PTE 改为 swap entry
释放物理页
以后访问 → page fault → swap in
```

swap 能提高容量弹性，但磁盘 swap 延迟远高于 RAM，不能当成等价内存。

### 12.2 thrashing

thrashing（内存抖动）指工作集明显大于可用内存，系统不断换出又马上换入：

```text
大量 major fault
swap in/out 持续很高
磁盘繁忙
业务 CPU 利用率或吞吐反而下降
响应延迟剧增
```

加 swap 可能推迟 OOM，但无法从根本上解决工作集长期超过物理内存的问题。

### 12.3 zRAM

zRAM 用 RAM 中的压缩块设备作为 swap 等用途：

```text
收益：用 CPU 换取更高有效内存容量，通常比磁盘 swap 快
代价：压缩本身占 CPU，压缩率依数据而异，仍占用物理内存
```

面试知道它是“压缩内存上的 swap 设备”，不是无限内存即可。

## 13. overcommit 与 OOM

### 13.1 为什么允许 overcommit

程序可能申请很大虚拟空间但只使用一小部分；`fork()` 的 COW 也使最坏情况内存需求远大于当前实际占用。
如果所有申请都按最坏情况预留物理内存，会浪费资源，所以 Linux 支持 overcommit。

### 13.2 vm.overcommit_memory

```text
0：启发式判断，拒绝明显不合理的申请
1：总是允许提交，真正用尽时再处理
2：严格提交记账，限制在 CommitLimit 规则内
```

模式 2 的限制与 swap、物理内存比例或 `overcommit_kbytes` 等配置有关。

### 13.3 malloc 成功为何以后仍可能失败

```text
malloc/mmap 获得虚拟地址和提交许可
    ↓
程序首次写入
    ↓
page fault 请求真实物理页
    ↓
此时才可能遭遇回收失败、memcg 限制或 OOM
```

因此“申请虚拟地址成功”和“所有页面都有物理内存保证”不是同一件事。

### 13.4 OOM 何时发生

当某次分配在其允许的 node、zone、cpuset、memory cgroup、order 和 GFP 约束内，经过回收/压缩等尝试仍无法取得内存时，可能进入 OOM 处理。

OOM 有不同范围：

```text
global OOM：整个系统或相关允许节点无法满足
memcg OOM：某个 memory cgroup 达到限制
NUMA/cpuset 约束下的局部失败：全机有内存也未必可用
```

### 13.5 OOM killer 如何选进程

内核使用启发式评分，倾向于选择能释放较多内存且适合作为牺牲者的任务；`oom_score_adj` 可调整保护或优先级。

不要简单回答“永远杀 RSS 最大的进程”，实际还会考虑共享、权限、调整值和 OOM 范围等因素。

### 13.6 看 OOM 日志

优先找：

```text
触发分配的进程、order 和 gfp_mask
是 global OOM 还是 memcg OOM
内存与 swap 状态
各进程的 RSS、页表、swap 和 oom_score_adj
最终 Killed process
```

被杀进程不一定是根因；它只是当时评分选择的牺牲者。

## 14. 内存问题排查顺序

### 14.1 第一步：判断是否真的有压力

```bash
free -h
cat /proc/meminfo
vmstat 1
cat /proc/pressure/memory
```

重点观察：

```text
MemAvailable 是否持续低
swap si/so 是否持续发生
是否存在 direct reclaim、进程阻塞或 memory PSI
Dirty/Writeback 是否异常
```

### 14.2 第二步：定位用户进程

```bash
ps aux --sort=-rss
cat /proc/<pid>/status
cat /proc/<pid>/smaps_rollup
pmap -x <pid>
```

区分：

```text
VSZ/VmSize：虚拟地址空间大小
RSS/VmRSS：驻留在物理内存中的页面规模
PSS：共享页按共享者比例分摊
Anonymous：匿名内存
File：文件映射相关内存
Swap：该进程换出规模
```

共享内存会让简单相加 RSS 重复计算，跨进程归因时 PSS 往往更有参考价值。

### 14.3 第三步：定位内核内存

```bash
slabtop
cat /proc/slabinfo
grep -E 'Slab|SReclaimable|SUnreclaim|PageTables|KernelStack' /proc/meminfo
```

如果某类 slab 对象持续增长，要结合对象所属子系统、工作负载和释放路径判断，不能只看总 Slab。

### 14.4 第四步：看回收和 OOM

```bash
vmstat 1
dmesg -T | grep -i -E 'oom|out of memory|page allocation failure'
```

关注：

```text
kswapd/direct reclaim 是否频繁
swap in/out 是否持续
是否有高阶 page allocation failure
OOM 的范围和被杀进程
是否存在 cgroup memory.max 限制
```

### 14.5 cache 高是不是泄漏

先分类：

```text
page cache 高：通常可回收，结合 MemAvailable 判断
SReclaimable 高：部分内核 cache 可回收
SUnreclaim 持续增长：可能需要查内核对象泄漏
某进程 anonymous RSS 持续增长：查用户态 heap/mmap
共享内存增长：查 tmpfs、shmem、容器或 IPC
```

“used 很高”只是现象，必须找到具体内存类型和是否可回收。

## 15. 驱动与调试追问级概念

### 15.1 copy_to_user() / copy_from_user()

内核不能把用户指针当普通可信内核指针直接 `memcpy()`：

```text
用户地址可能未映射
可能缺页
权限可能不允许
地址可能在检查后被并发改变
体系结构需要异常修复机制
```

应使用：

```c
not_copied = copy_from_user(kernel_buf, user_ptr, size);
not_copied = copy_to_user(user_ptr, kernel_buf, size);
```

返回值是“尚未复制的字节数”，不是普通的负 errno。返回 0 才表示全部复制成功。

这些接口可能因用户页缺页而睡眠，通常不能在 hardirq 或持有自旋锁时调用。

### 15.2 DMA mapping

设备看到的 DMA address 不一定等于 CPU virtual address 或物理地址：

```text
CPU virtual address
    ↓ 内核映射
physical memory
    ↓ DMA API / IOMMU
device DMA address
```

驱动应使用 DMA API，而不是自行猜测 `virt_to_phys()` 后交给设备。

```text
coherent DMA：CPU 和设备可并发观察，仍需正确同步所有权和内存顺序
streaming DMA：短期映射，必须使用正确方向并配对 map/unmap 或 sync
```

### 15.3 CMA

CMA 预留一段主要由可迁移页临时使用的区域；设备需要大块连续物理内存时，内核迁移普通可移动页以形成连续区域。

CMA 仍可能因为不可迁移页、长期 pin、碎片或并发压力分配失败，不是绝对保证。

### 15.4 KASAN

KASAN 通过编译器插桩和 shadow/tag 等机制检查内核内存访问，常用于发现：

```text
越界访问
use-after-free
部分无效访问和对象生命周期错误
```

它会增加内存和性能开销，通常用于测试、调试或特定部署，而不是把生产性能问题都归给它解决。

## 16. 高频面试问答

### 16.1 为什么用户进程要使用虚拟地址？

虚拟内存提供进程隔离、权限保护、受控共享和按需分配，并让每个进程看到独立且较连续的地址空间，避免直接管理复杂物理地址。

### 16.2 虚拟地址怎样转换成物理地址？

MMU 先查询 TLB；未命中时按虚拟地址的多级索引遍历页表，取得物理页号和权限，再加页内 offset 形成物理地址。

### 16.3 TLB 是什么，为什么修改页表后要 flush？

TLB 缓存地址转换和权限。页表修改后旧缓存可能继续被 CPU 使用，因此必须使对应 TLB 项失效；多核时还可能需要通知其他 CPU。

### 16.4 page fault 一定是非法访问吗？

不一定。首次匿名页访问、文件 mmap、swap in 和 COW 写入都会正常触发 page fault；只有地址无合法 VMA或权限无法修复等情况才通常发送信号。

### 16.5 minor fault 和 major fault 有什么区别？

核心区别是解决 fault 是否需要读取目标页的存储 I/O。minor fault 通常不需要，major fault 通常需要文件或 swap I/O，延迟更高。

### 16.6 malloc 成功后是否已经获得物理内存？

不一定。它通常先获得虚拟范围和提交许可，物理页可能在首次访问触发缺页时才分配；overcommit 下以后仍可能遇到内存压力。

### 16.7 fork() 为什么不复制全部物理内存？

父子页表暂时映射相同物理页并使用 COW；某一方写入时才通过写保护 fault 分配并复制该页，从而避免复制从未修改的页面。

### 16.8 mm_struct 和 VMA 是什么关系？

`mm_struct` 描述进程整个用户地址空间及页表等状态；VMA 描述其中一段权限和后备存储属性相同的虚拟范围。VMA 存在不代表每页已有物理映射。

### 16.9 node、zone、struct page、PFN 分别是什么？

node 表示 NUMA 内存节点；zone 表示具有特定寻址或迁移约束的物理范围；PFN 是页帧编号；`struct page` 是内核管理一个物理页帧的元数据。

### 16.10 buddy 为什么按 2 的幂次分配？

这样可以用 order 管理连续页块，并在分配时快速拆分、释放时根据伙伴关系快速合并，降低整页管理复杂度。

### 16.11 内存总量充足为何高阶分配仍失败？

高阶分配要求连续物理页。空闲页可能分散，或被不可迁移、pin 页隔断；compaction 也不一定能形成所需连续块。

### 16.12 buddy 和 SLUB 有什么区别？

buddy 管理整页和连续页块；SLUB 从 buddy 获取页后切成较小对象，通过 cache 和 per-CPU freelist 提高小对象分配效率。

### 16.13 kmalloc 和 vmalloc 怎么选？

`kmalloc()` 提供虚拟连续且通常物理连续的内存，适合较小对象；`vmalloc()` 只保证虚拟连续，适合较大普通缓冲区，但映射成本更高且不能替代 DMA API。

### 16.14 GFP_KERNEL 和 GFP_ATOMIC 有什么区别？

`GFP_KERNEL` 可睡眠和进行更充分回收，用于普通进程上下文；`GFP_ATOMIC` 用于不可睡眠上下文，只能有限尝试并可能使用保留资源，更容易失败。

### 16.15 为什么 MemFree 低不一定是问题？

Linux 会把空闲内存用于 page cache 和可回收 cache。应优先结合 `MemAvailable`、swap、回收活动和业务延迟判断真实压力。

### 16.16 page cache 有什么作用？

它缓存文件数据，减少重复存储 I/O，并承接普通 buffered read/write 和文件 mmap 的页。clean 页可直接回收，dirty 页通常要先写回。

### 16.17 write() 返回是否意味着数据已经落盘？

通常不意味着。数据可能只写入 page cache 并标为 dirty；需要持久化时要使用 `fsync()` 等接口并理解具体文件系统和设备语义。

### 16.18 kswapd 和 direct reclaim 有什么区别？

kswapd 是后台回收线程，尽量提前恢复水位；direct reclaim 由申请内存的 task 自己执行，会直接增加该业务路径的分配延迟。

### 16.19 文件页和匿名页如何回收？

clean 文件页可直接丢弃，dirty 文件页需回写；匿名页没有文件后备，通常需要 swap 才能释放内容仍需保留的物理页。

### 16.20 swap 很大能否解决内存不足？

只能提供容量缓冲并推迟 OOM。工作集长期超出 RAM 时会频繁换入换出，引发高延迟和 thrashing，不能替代足够物理内存或应用治理。

### 16.21 overcommit 是什么？

它允许承诺的虚拟内存超过当前物理内存和 swap 的直接可用量，以适应稀疏使用和 COW；策略由 `vm.overcommit_memory` 等配置控制。

### 16.22 OOM 是否一定杀内存占用最大的进程？

不一定。内核根据 OOM 范围和启发式评分选择牺牲者，并受 `oom_score_adj`、共享关系、权限和 memcg 等因素影响。

### 16.23 如何区分 cache 和内存泄漏？

先看 `MemAvailable` 和可回收性，再区分 page cache、SReclaimable、SUnreclaim、进程 anonymous RSS 与共享内存。持续不可回收增长并与工作负载不匹配才值得重点怀疑泄漏。

### 16.24 copy_from_user() 为什么不能换成 memcpy()？

用户地址不可信，可能缺页、无权限或在并发中变化。`copy_from_user()` 配合体系结构异常处理安全访问，并以“未复制字节数”报告部分失败。

### 16.25 DMA 地址为什么不一定等于物理地址？

设备可能经过 IOMMU、总线地址转换或受 DMA mask 限制。驱动必须使用 DMA mapping API 获取设备可用地址并维护 cache/所有权同步。

## 17. 一页背诵级总结

### 17.1 地址主线

```text
虚拟地址 → TLB → 多级页表 → 物理页 + offset
页表无有效映射 → page fault
合法 fault → 按需分配、文件读入、swap in 或 COW
非法地址/权限 → 通常 SIGSEGV
```

### 17.2 核心结构

```text
mm_struct：进程地址空间
VMA：一段属性相同的虚拟范围
node：NUMA 内存节点
zone：满足特定约束的物理范围
PFN：物理页帧编号
struct page：物理页元数据
```

### 17.3 分配器

```text
PCP：低阶页 per-CPU 快速路径
buddy：管理 2^order 个连续物理页
SLUB：在页上管理小对象
kmalloc：虚拟连续，通常物理连续
vmalloc：虚拟连续，物理可不连续
GFP_KERNEL：可睡眠
GFP_ATOMIC：不可睡眠，更易失败
```

### 17.4 文件与回收

```text
page cache：缓存文件页
dirty：内存比磁盘新
writeback：脏页写回后备存储
低水位：唤醒 kswapd
高压力：分配者可能 direct reclaim
clean file page：可直接丢弃
anon page：通常需要 swap 才能保留内容并释放物理页
```

### 17.5 OOM 与排障

```text
overcommit：虚拟提交不等于物理页保证
OOM：在本次分配约束内回收仍无法满足
MemFree 低不等于没内存，优先看 MemAvailable
用户进程：status/smaps_rollup
内核 slab：slabtop、SReclaimable/SUnreclaim
压力：vmstat、memory PSI、swap si/so
OOM：dmesg，区分 global 和 memcg
```

### 17.6 最终口诀

```text
进程拿虚址，MMU 查页表；
TLB 缓映射，改表要失效；
合法缺页按需补，fork 写时才复制；
node 下分 zone，page 对应页帧；
整页找 buddy，小对象找 SLUB；
kmalloc 要物理连续，vmalloc 只保虚拟连续；
文件先进 page cache，脏页稍后 writeback；
低水位唤醒 kswapd，业务自救叫 direct reclaim；
匿名页靠 swap，实在分不到才 OOM；
别只盯 MemFree，先看 Available、回收和内存类型。
```

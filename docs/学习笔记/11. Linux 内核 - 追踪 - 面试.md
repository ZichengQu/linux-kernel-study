# Linux 内核追踪：一小时面试版

> 目标：面向通用 Linux 岗，在一小时内建立“问题—证据—工具”的追踪知识框架。
>
> 阅读方法：先掌握第 1～3 节的选型主线，再理解核心工具和五类排障场景，最后用问答与一页速记复习。

## 0. 面试需要掌握到什么程度

必须讲清楚：

```text
1. profiling、tracing 和 vmcore 分析分别回答什么问题
2. perf、tracepoint、ftrace、bpftrace、动态探针和 crash 如何选择
3. tracepoint 与 kprobe、ftrace 与 perf 的核心区别
4. perf stat、record、report 大致做什么
5. tracefs、trace_pipe、trace-cmd 的关系
6. bpftrace/eBPF 为什么适合在线聚合和事件关联
7. CPU 高、调度延迟、锁竞争、IRQ 干扰、panic 如何建立证据链
8. 如何控制追踪开销、过滤范围和生产风险
```

只需知道定位，不必深入实现：

```text
fprobe：面向函数 entry/exit 的较新动态事件能力
eprobe：基于已有 trace event 派生新事件
libbpf CO-RE：利用 BTF 提高 BPF 程序跨内核适配能力
drgn：用 Python API 读取 live kernel 或 vmcore 对象
```

通用 Linux 面试通常不需要背：

```text
tracefs 所有控制文件和 trigger 语法
kprobe 在各架构上的寄存器取参规则
BPF verifier、JIT、map 和 ring buffer 的逐行实现
crash/drgn 的完整对象导航命令
所有 CONFIG_TRACING/CONFIG_BPF 配置项
```

## 1. 第一原则：先问需要什么证据

不要从“我会哪个工具”出发，而要从问题需要哪种证据出发。

### 1.1 五类常见证据

| 需要回答的问题                | 证据类型                       | 常用工具                       |
| ----------------------------- | ------------------------------ | ------------------------------ |
| CPU 时间花在哪里              | 周期采样、调用栈、硬件计数     | perf                           |
| 哪些事件按什么顺序发生        | 带时间戳事件时间线             | tracepoint、trace-cmd、tracefs |
| 某函数调用了谁、耗时多久      | 函数入口/返回和嵌套            | ftrace function_graph          |
| 两个事件如何关联、分布如何    | 在线状态关联、聚合、直方图     | bpftrace/eBPF                  |
| panic 时对象和 CPU 是什么状态 | 冻结的栈、task、runqueue、内存 | crash、drgn                    |

### 1.2 profiling 与 tracing

profiling 通常通过周期性采样回答：

```text
哪些函数占用 CPU 最多？
调用栈热点在哪里？
cycles、instructions、cache-misses 是否异常？
```

tracing 记录离散事件，回答：

```text
任务何时 wakeup、何时真正运行？
IRQ 是否在关键窗口打断 CPU？
函数什么时候进入、何时返回？
一次 I/O 经过了哪些阶段？
```

一句话：

> profiling 擅长找“时间花在哪里”，tracing 擅长还原“发生了什么以及先后顺序”。

### 1.3 运行时追踪与 vmcore 分析

运行时追踪需要在问题发生时已经开始采集，才能得到事件时间线。

vmcore 是系统崩溃时的内存快照，适合回答：

```text
哪个 CPU panic？
各 CPU 当时栈是什么？
哪些任务处于 D 状态？
runqueue、锁和对象当时是什么状态？
```

crash 不能回到过去补出 `sched_switch` 频率；trace-cmd 也不能在 panic 后补采崩溃前未记录的时间线。

### 1.4 统计、时间线和快照不要混用

```text
统计：一段时间内多少次、占比多少、分布如何
时间线：每个事件的时间戳、CPU、PID 和先后关系
快照：某一时刻对象、寄存器、栈和内存状态
```

优秀的排障往往组合三者，而不是指望一个工具回答所有问题。

## 2. 一张工具选型图

```text
系统是否已经崩溃，只留下 vmcore？
├── 是：crash 首轮看 sys/log/bt/runq；批量对象检查考虑 drgn
└── 否
    ↓
主要问题是 CPU 热点或硬件计数吗？
├── 是：perf stat → perf record/report
└── 否
    ↓
内核是否已有合适的静态事件？
├── 是：tracepoint + trace-cmd/tracefs；需要关联聚合时用 bpftrace
└── 否
    ↓
要看函数调用图吗？
├── 是：ftrace function/function_graph
└── 否
    ↓
要补函数参数、返回值或用户函数边界吗？
├── 内核函数：kprobe/kretprobe、fprobe 或 bpftrace
├── 用户函数：uprobe/uretprobe
└── 长期可维护工具：新增 tracepoint 或 libbpf CO-RE
```

### 2.1 高频场景首选表

| 场景              | 首选                                         | 常见补充                      |
| ----------------- | -------------------------------------------- | ----------------------------- |
| 全系统 CPU 高     | perf record/report                           | tracepoint、bpftrace          |
| 调度延迟          | sched tracepoint、perf sched                 | IRQ 事件、bpftrace 延迟直方图 |
| 锁竞争            | perf lock                                    | lockstat、bpftrace 调用栈     |
| IRQ/softirq 干扰  | `/proc/interrupts`、irq/softirq tracepoint | perf、CPU affinity 对照       |
| 函数返回异常      | kretprobe/fprobe return                      | bpftrace 聚合返回值           |
| 用户态锁慢        | uprobe + futex tracepoint                    | 用户栈、off-CPU 分析          |
| panic/hung 后分析 | crash                                        | drgn 脚本化检查               |
| 长期部署观测      | tracepoint、libbpf CO-RE                     | ring buffer、map 聚合         |

### 2.2 为什么优先已有 tracepoint

tracepoint 是内核源码中显式定义的静态事件，字段语义相对清晰，通常比探测内部函数更稳定。

如果已有合适 tracepoint，应先用它；只有字段不足时，才考虑 kprobe/fprobe 等动态探针。

## 3. 追踪系统的共同概念

### 3.1 event、probe 和 sample

```text
event：一次有语义的事件，例如 sched_switch
probe：附着点，命中时执行记录或程序
sample：按周期或事件概率取得的一份样本
```

tracepoint 本身是稳定事件定义；kprobe 是动态函数探测点；perf record 可以按频率采样 CPU 调用栈。

### 3.2 时间戳、CPU、PID 与上下文

一条追踪记录通常至少要关注：

```text
timestamp：何时发生
CPU：在哪个 CPU 发生
current/PID：当时哪个任务上下文
event fields：事件特有字段
call stack：从哪里触发，可选
```

不要把 `common_pid` 与事件中的 `prev_pid`、`next_pid`、`pid` 混为一谈。前者通常表示记录事件时的 current，后者由具体事件定义。

### 3.3 调度事件三兄弟

```text
sched_waking：开始尝试唤醒目标任务
sched_wakeup：目标任务进入可运行状态
sched_switch：CPU 实际从 prev 切换到 next
```

简化的 wakeup latency：

```text
目标任务 sched_wakeup 的时间
        ↓ 等待 CPU
目标任务成为 sched_switch.next
        ↓
两者时间差约等于一段可运行等待延迟
```

需要排除任务已运行、迁移、重复 wakeup 等情况时，应按实际事件语义完善关联逻辑。

### 3.4 调用栈的价值与代价

调用栈能把“某事件很多”推进到“从哪条路径触发”。但采集栈会增加开销和数据量，还依赖符号、frame pointer、DWARF 或 BPF 栈能力。

因此先聚合事件，确认异常范围后再为少量目标采栈。

### 3.5 观测会扰动系统

追踪不是零成本：

```text
事件触发要执行记录逻辑
写 buffer 消耗内存带宽
采集调用栈开销更高
大量输出到终端会产生严重扰动
用户态频繁读取会增加调度与复制开销
```

面试应主动说出：先限时、限事件、限 PID、限 CPU，优先在内核聚合，逐步扩大范围。

## 4. perf：计数与 CPU 采样

### 4.1 perf 主要回答什么

perf 基于 perf events 框架，常用于：

```text
硬件/软件事件计数
CPU 周期采样和调用栈热点
调度时间线与延迟统计
锁竞争统计
tracepoint 事件采集
```

### 4.2 perf stat

`perf stat` 做计数，不记录每次事件的完整时间线。

```bash
sudo perf stat -e cycles,instructions,context-switches,cpu-migrations \
  -a -- sleep 10
```

常见解读：

```text
cycles/instructions：粗看 CPU 执行效率，需结合 workload
context-switches：上下文切换规模
cpu-migrations：任务迁移规模
page-faults：缺页次数
```

计数异常只是线索，不能仅凭一个指标直接下根因结论。

### 4.3 perf record/report

最小的全系统热点采样：

```bash
sudo perf record -F 99 -g -a -- sleep 10
sudo perf report
```

含义：

```text
-F 99：目标采样频率约 99 Hz
-g：采集调用图
-a：全系统所有 CPU
-- sleep 10：明确采集窗口
```

只看目标进程或 CPU：

```bash
sudo perf record -F 99 -g -p 1234 -- sleep 10
sudo perf record -F 99 -g -C 7 -- sleep 10
```

### 4.4 perf report 中的比例

`Overhead` 表示样本占比，不直接等于函数自身执行时间。调用图模式、children/self 展示、采样事件和栈展开质量都会影响解读。

面试回答要强调：

```text
先确认采样事件是什么
区分函数自身热点与子调用累计热点
看调用栈而不只看单个符号
确认 unknown、符号缺失和栈断裂比例
```

### 4.5 perf sched 与 perf lock

```bash
sudo perf sched record -- sleep 10
sudo perf sched latency
```

用于观察调度事件和任务延迟统计。

```bash
sudo perf lock record -- sleep 10
sudo perf lock report
```

用于锁事件支持下的竞争分析，依赖内核能力和工具版本。

### 4.6 perf 的边界

适合：CPU 热点、PMU 计数、采样栈、部分调度与锁统计。

不适合：任意复杂事件状态机、未暴露结构字段的自由读取、panic 后补采历史事件。

## 5. tracepoint、tracefs 与 trace-cmd

### 5.1 tracepoint 是什么

tracepoint 是内核代码中预先定义的静态事件点，例如：

```text
sched:sched_switch
sched:sched_wakeup
irq:irq_handler_entry
irq:softirq_entry
kmem:mm_page_alloc
block:block_rq_issue
```

优点：字段有明确语义、开销相对可控、比内部函数名更稳定。

限制：只能观察内核已暴露的事件和字段；不同版本仍可能存在事件或字段差异。

### 5.2 tracefs 是什么

tracefs 是内核 tracing 框架的控制和数据接口，常见路径：

```bash
TR=/sys/kernel/tracing
[ -d "$TR" ] || TR=/sys/kernel/debug/tracing
```

面试常见文件：

| 文件                               | 作用                         |
| ---------------------------------- | ---------------------------- |
| `available_events`               | 当前内核可用事件             |
| `events/<system>/<event>/format` | 事件字段和打印格式           |
| `events/<system>/<event>/enable` | 启停某个事件                 |
| `events/<system>/<event>/filter` | 按该事件字段过滤             |
| `trace`                          | buffer 的静态视图            |
| `trace_pipe`                     | 实时消费数据流               |
| `tracing_on`                     | tracing 总开关               |
| `current_tracer`                 | 当前 function/latency tracer |

### 5.3 最小 tracefs 采集流程

仅在无其他 tracing 使用者的测试环境执行：

```bash
echo 0 | sudo tee "$TR/tracing_on"
echo 1 | sudo tee "$TR/events/sched/sched_switch/enable"
: | sudo tee "$TR/trace"
echo 1 | sudo tee "$TR/tracing_on"
sleep 3
echo 0 | sudo tee "$TR/tracing_on"
sudo head -100 "$TR/trace"
echo 0 | sudo tee "$TR/events/sched/sched_switch/enable"
```

生产环境应优先使用 trace instance 或明确保存并恢复本次修改，不要粗暴清空全局 tracing 状态。

### 5.4 trace 与 trace_pipe

```text
trace：读取当前 buffer 快照，通常不会像流一样持续消费
trace_pipe：阻塞式读取新记录，并消费读出的数据
```

如果读取端太慢，buffer 仍可能覆盖旧数据；`trace_pipe` 不是无限容量消息队列。

### 5.5 format 与 filter

写过滤器前先读事件的 `format`：

```bash
cat "$TR/events/sched/sched_switch/format"
echo 'next_pid == 1234' | \
  sudo tee "$TR/events/sched/sched_switch/filter"
```

过滤表达式只能使用该事件实际提供的字段。不要凭其他版本示例猜字段名。

### 5.6 trace-cmd 做什么

trace-cmd 是 ftrace/tracefs 的用户态前端，方便统一配置、采集多 CPU buffer 并保存 `trace.dat`。

```bash
sudo trace-cmd record -o sched.dat \
  -e sched:sched_wakeup \
  -e sched:sched_switch \
  sleep 10
sudo trace-cmd report -i sched.dat
```

`trace.dat` 可供离线报告和 KernelShark 时间线查看，比手工操作多个 tracefs 文件更适合一次完整实验。

### 5.7 tracepoint 的边界

适合：已有稳定事件、需要时间线、低到中等频率采集。

不适合：事件没有所需字段、需要任意函数局部变量、需要复杂在线跨事件关联。后两者可考虑动态探针或 eBPF。

## 6. ftrace：函数与延迟追踪框架

### 6.1 ftrace 与 tracefs 的关系

ftrace 是内核追踪框架和一组 tracer；tracefs 是控制这些能力的文件接口。tracepoint event tracing 也通过 tracefs 暴露。

不要把 ftrace 仅理解为一个命令行程序。

### 6.2 function tracer

function tracer 记录函数入口，适合确认某函数是否被调用以及调用频率的大致情况。

```bash
echo schedule | sudo tee "$TR/set_ftrace_filter"
echo function | sudo tee "$TR/current_tracer"
sudo timeout 3 cat "$TR/trace_pipe"
echo nop | sudo tee "$TR/current_tracer"
```

必须先过滤函数；不加过滤直接追全内核函数，数据量和扰动都可能很大。

### 6.3 function_graph tracer

function_graph 记录函数进入、返回、嵌套和耗时：

```bash
echo schedule | sudo tee "$TR/set_graph_function"
echo function_graph | sudo tee "$TR/current_tracer"
sleep 2
echo nop | sudo tee "$TR/current_tracer"
sudo head -100 "$TR/trace"
```

它适合看调用路径和长函数，但输出与开销通常高于只记入口的 function tracer。

显示的函数耗时可能包含抢占、中断等影响，需要结合输出标志和其他事件理解。

### 6.4 latency tracer

常见 latency tracer：

```text
irqsoff：寻找中断关闭过久的区间
preemptoff：寻找抢占关闭过久的区间
preemptirqsoff：组合观察
wakeup/wakeup_rt：观察调度唤醒延迟的特定路径
```

它们是否可用取决于内核配置，可先查看：

```bash
cat "$TR/available_tracers"
```

### 6.5 ftrace 的边界

适合：函数调用路径、函数耗时、IRQ/preempt 关闭延迟。

不适合：长时间无过滤全函数追踪、复杂在线聚合、panic 后补历史。需要统计分布时常结合 bpftrace/eBPF，需要保存事件时间线时可用 trace-cmd。

## 7. bpftrace 与 eBPF：关联、聚合和直方图

### 7.1 为什么使用 bpftrace

bpftrace 是面向动态追踪的高级语言，常把 BPF 程序附着到 tracepoint、kprobe、uprobe 等位置。

它擅长：

```text
按 PID、comm、CPU、cgroup 过滤
在 map 中关联两个事件
在内核侧 count/sum/avg/min/max/hist 聚合
按需记录内核栈或用户栈
快速验证排障假设
```

### 7.2 最小 tracepoint 聚合

```bash
sudo timeout 10 bpftrace -e '
tracepoint:sched:sched_switch
{
    @[args->next_comm] = count();
}'
```

这里每次事件只更新 map，结束时才输出聚合结果，比逐事件 `printf()` 更适合高频路径。

### 7.3 wakeup latency 关联

简化示例：

```bash
sudo timeout 10 bpftrace -e '
tracepoint:sched:sched_wakeup
{
    @start[args->pid] = nsecs;
}

tracepoint:sched:sched_switch
/@start[args->next_pid]/
{
    @lat_us = hist((nsecs - @start[args->next_pid]) / 1000);
    delete(@start[args->next_pid]);
}'
```

思路：第一个事件按 PID 保存时间，第二个事件找到同一任务并计算差值，最后画直方图。

生产级脚本还要处理重复 wakeup、任务退出、map 清理、迁移和事件语义差异。

### 7.4 聚合优先于逐条打印

高频事件中逐条 `printf()` 会增加用户态输出和数据传输压力，还可能改变被观测系统行为。

优先：

```text
count：次数
sum：总量
avg：平均值
hist/lhist：分布
kstack/ustack：只对异常条件采集栈
```

### 7.5 eBPF 的安全与限制

BPF 程序加载前通常经过 verifier 检查，限制非法内存访问、不可证明安全的控制流等。

运行还可能受以下因素限制：

```text
root/capability
kernel lockdown
CONFIG_BPF、CONFIG_BPF_SYSCALL
BTF 和调试信息
符号可见性
bpftrace 与内核版本
```

### 7.6 bpftrace 与 libbpf

```text
bpftrace：临时排障、快速原型、短脚本
libbpf：长期工具、结构化工程、精细错误处理和发布
```

一个常见路径是先用 bpftrace 验证指标有价值，再用 libbpf CO-RE 工程化。

### 7.7 bpftrace 的边界

适合：在线过滤、跨事件关联、分布统计、异常栈聚合。

不适合：未经评估直接长期运行复杂脚本、无限增长 map、高频逐事件打印，以及把不稳定内部函数探针当跨版本稳定接口。

## 8. kprobe、kretprobe 与 uprobe

### 8.1 动态探针解决什么问题

当内核没有合适 tracepoint，动态探针可附着到函数入口、返回或用户程序地址，补充参数、返回值和调用次数。

```text
kprobe：内核函数入口或指令位置
kretprobe：内核函数返回
uprobe：用户空间函数或地址
uretprobe：用户空间函数返回
```

### 8.2 最小 kprobe 示例

先确认符号和当前机器支持：

```bash
grep -w try_to_wake_up /proc/kallsyms
sudo timeout 10 bpftrace -e '
kprobe:try_to_wake_up { @[comm] = count(); }'
```

观察返回值：

```bash
sudo timeout 10 bpftrace -e '
kretprobe:vfs_read { @[retval] = count(); }'
```

函数可能被内联、重命名、优化或列入黑名单，参数位置也受版本与架构 ABI 影响。

### 8.3 最小 uprobe 思路

```bash
sudo timeout 10 bpftrace -e '
uprobe:/path/to/app:target_function { @[comm] = count(); }'
```

uprobe 需要正确的二进制、符号或偏移；PIE、ASLR、被剥离符号、不同库版本和内联都会影响附着。

### 8.4 tracepoint 与 kprobe

| 对比     | tracepoint       | kprobe                   |
| -------- | ---------------- | ------------------------ |
| 定义方式 | 内核源码显式定义 | 运行时动态附着函数/地址  |
| 字段语义 | 相对稳定、明确   | 依赖函数签名、ABI 和版本 |
| 灵活性   | 仅有预定义字段   | 可补未暴露位置和参数     |
| 首选场景 | 已有合适事件     | tracepoint 不足时        |

### 8.5 动态探针的边界

动态探针适合验证假设，不应默认视为长期稳定接口。上线前必须验证目标内核的函数、签名、符号、可探测性和触发频率。

## 9. crash 与 drgn：事后对象分析

### 9.1 crash 主要回答什么

crash 使用匹配的 `vmlinux` 和 vmcore 分析崩溃时的内存状态：

```bash
crash /path/to/vmlinux /path/to/vmcore
```

首轮常用命令：

```text
sys：系统和 panic 摘要
log：内核日志
bt：当前 panic task 栈
bt -a：所有 CPU 当前 task 栈
ps：任务状态
runq：runqueue 摘要
```

### 9.2 crash 的典型证据链

```text
log 确认 panic/oops/hung 报告
    ↓
bt / bt -a 定位 CPU 与调用栈
    ↓
ps / runq 确认任务和调度状态
    ↓
struct / list 等检查关键对象
    ↓
结合源码解释对象为何处于该状态
```

### 9.3 符号和版本必须匹配

vmcore 与 `vmlinux` 不匹配会导致符号、结构偏移和栈解析错误。还可能需要对应模块符号和调试信息。

不能因为 crash 能启动就假定所有对象解释都可靠，应核对 kernel release、build-id、模块和 debuginfo。

### 9.4 drgn 做什么

drgn 是可编程调试器，可通过 Python API 读取 live kernel 或 vmcore 中的内核对象。

适合：

```text
批量遍历 task、链表、树和 Per-CPU 对象
把重复的 crash 手工检查固化成脚本
对大量对象做一致性检查和统计
```

不适合：低开销采集运行时事件时间线。

### 9.5 crash 与 drgn

```text
crash：交互式首轮分析成熟，命令适合快速查看栈和对象
drgn：Python 脚本能力强，适合批量、自动化和可审计检查
```

二者读取的都是当前 live 状态或 dump 快照，不会自动还原未采集的历史事件。

## 10. fprobe、eprobe 与 libbpf CO-RE 的定位

### 10.1 fprobe

fprobe 面向函数入口/返回追踪，较新内核可通过 dynamic events 等接口使用。它适合函数级事件，但仍受内核版本、符号和接口能力影响。

面试只需知道：它与 kprobe 都能补函数观测，但具体能力与语法应以目标内核文档和 tracefs 文件为准。

### 10.2 eprobe

eprobe 基于已有 trace event 派生事件，可裁剪或重新提取事件字段。

它不是任意函数探针，也不能替代 kprobe 获取任意寄存器或局部变量。

### 10.3 libbpf CO-RE

CO-RE 可理解为 Compile Once – Run Everywhere。BPF 程序结合目标内核 BTF，在加载时重定位结构字段访问，减少为每个内核重新编译的需求。

它提高可移植性，但不保证所有内核都兼容：仍要考虑 BTF 是否存在、字段语义变化、程序 attach 点和内核特性。

### 10.4 面试选型

```text
临时一行统计：bpftrace
已有稳定事件：tracepoint
补内部函数：kprobe/fprobe
基于事件裁剪字段：eprobe
长期部署的 BPF 工具：libbpf CO-RE
```

## 11. 数据丢失、开销和生产安全

### 11.1 ring buffer 有限

追踪 buffer 容量有限。生产速度超过消费速度时，旧数据可能被覆盖或出现 lost events。

看到“没有某事件”时，先排除：

```text
事件未启用
过滤条件错误
目标路径没发生
buffer 太小或被覆盖
读取端太慢
权限、配置或 attach 失败
```

### 11.2 过滤要尽量靠近数据源

```text
差：全系统采所有事件，再在用户态 grep
好：在 event filter/BPF predicate 中限制 PID、CPU、字段
更好：只启用回答当前问题所需的最少事件
```

源头过滤减少 buffer、复制和后处理压力。

### 11.3 限时、限 PID、限 CPU、限事件

生产采集前至少明确：

```text
采多久，例如 timeout 10 或 sleep 10
看哪些 PID/cgroup
看哪些 CPU
启用哪些事件和调用栈
输出保存到哪里
如何停止并恢复状态
```

先在测试机估算事件频率和开销，再进入生产环境。

### 11.4 不要高频逐条打印

终端打印或 perf buffer/ring buffer 逐条上送可能成为主要开销。高频场景优先在内核侧聚合，只把计数、直方图或少量异常栈送到用户态。

### 11.5 权限与安全策略

常见限制：

```text
perf_event_paranoid
kptr_restrict
root/capability
kernel lockdown
tracefs 文件权限
BPF LSM/安全策略
容器 namespace 与宿主机权限
```

权限失败不等于工具或事件不存在，应把权限、内核能力和命令语法分层判断。

### 11.6 版本与符号

执行动态探针前确认：

```bash
uname -r
grep -w target_function /proc/kallsyms
test -e /sys/kernel/btf/vmlinux
grep 'sched:sched_switch' "$TR/available_events"
```

命令示例必须以目标机器实际的 `available_events`、`format`、符号和工具版本为准。

### 11.7 保留证据链

每次采集记录：

```text
绝对时间和采集时长
内核与工具版本
完整命令和过滤范围
原始输出文件
已确认事实、推断和待验证假设
```

不要只保存截图或最终一句结论。

## 12. 五类生产故障最短路径

### 12.1 CPU 高

#### 现象

单个或多个 CPU 使用率持续升高，业务吞吐下降或延迟上升。

#### 证据与工具

```text
1. top/pidstat 确认 CPU、进程、用户态/内核态
2. perf stat 粗看 cycles、instructions、切换和缺页
3. perf record/report 找热点函数与调用栈
4. 若热点指向调度、IRQ 或锁，再启用对应 tracepoint/bpftrace
```

最小采集：

```bash
sudo perf record -F 99 -g -C 7 -- sleep 10
sudo perf report
```

#### 判断

```text
业务函数栈集中：继续分析具体热点
大量 spin/lock 慢路径：进入锁竞争路径
IRQ/softirq 栈集中：检查中断分布和事件时间线
调度函数占比高：检查切换、迁移和 runnable 压力
```

不要只看到某内核函数占比高就断言它是根因；它可能只是所有路径共同经过的汇聚点。

### 12.2 调度延迟

#### 现象

任务已经可运行，但较晚才获得 CPU，表现为尾延迟、卡顿或周期任务超时。

#### 证据与工具

```text
1. 记录 sched_wakeup/sched_switch
2. 按 PID 关联 wakeup 到实际切入时间
3. 同时记录 irq/softirq，判断 CPU 是否被中断占用
4. 对照 CPU runqueue 压力、迁移和 cgroup throttling
```

最小采集：

```bash
sudo trace-cmd record -o latency.dat \
  -e sched:sched_wakeup \
  -e sched:sched_switch \
  -e irq:* -e softirq:* \
  sleep 10
```

#### 判断

```text
wakeup 后 CPU 长时间运行其他任务：调度竞争或优先级问题
窗口中 IRQ/softirq 密集：中断干扰
任务频繁迁移：检查 affinity、负载均衡和 NUMA
固定周期出现空档：检查 cgroup quota/throttling
```

### 12.3 锁竞争

#### 现象

CPU 消耗在自旋，或大量任务睡眠等待同一同步对象，吞吐下降。

#### 证据与工具

```text
1. perf report 看 spinlock/mutex/futex 等等待路径
2. perf lock 或 lockstat 确认高竞争锁
3. bpftrace 只对慢路径聚合内核栈
4. function_graph 检查锁内是否执行过长工作
```

最小命令：

```bash
sudo perf lock record -- sleep 10
sudo perf lock report
```

#### 判断

```text
同一锁等待次数和总等待时间高：锁热点
持锁路径有慢 I/O/长计算：缩短临界区
多个 CPU 争同一 cacheline：考虑分片或 Per-CPU
调用栈显示锁顺序异常：结合 lockdep 检查死锁风险
```

### 12.4 IRQ/softirq 干扰

#### 现象

某 CPU system time 高、业务线程被频繁打断，或 `ksoftirqd/N` 占用高。

#### 证据与工具

```text
1. /proc/interrupts 看 IRQ 速率和 CPU 分布
2. /proc/softirqs 看 softirq 类型和 CPU 分布
3. 采集 irq_handler_entry/exit、softirq_entry/exit 与 sched_switch
4. 对照设备队列、IRQ affinity 和业务线程 CPU
```

最小观察：

```bash
watch -n 1 cat /proc/interrupts
sudo trace-cmd record -e irq:* -e softirq:* -e sched:sched_switch \
  sleep 10
```

#### 判断

```text
单 IRQ 在单 CPU 高速增长：检查 affinity、队列和是否风暴
NET_RX_SOFTIRQ 集中：检查网卡队列、RSS/RPS 与流量
IRQ handler 很短但 softirq 很重：压力主要在下半部
计数高但业务正常：可能是正常吞吐，不能直接定性为风暴
```

### 12.5 panic/vmcore

#### 现象

系统已经 panic、oops 或通过 kdump 取得 vmcore，无法回到现场重新采集。

#### 证据与工具

```text
1. 用匹配 vmlinux 打开 vmcore
2. sys/log 确认 panic 类型和触发信息
3. bt/bt -a 找触发 CPU 与其他 CPU 状态
4. ps/runq 看任务和调度状态
5. 检查栈中涉及的锁、task、rq 或其他对象
6. 需要批量一致性检查时写 drgn 脚本
```

最小首轮：

```text
crash> sys
crash> log
crash> bt
crash> bt -a
crash> ps
crash> runq
```

#### 判断

先陈述栈、日志和对象中的事实，再结合源码推断根因。单个异常字段可能是内存破坏的结果，而非最初原因。

## 14. 高频面试问答

### 14.1 profiling 和 tracing 有什么区别？

profiling 常用采样和计数找热点及资源消耗；tracing 记录事件时间戳和字段，还原事件顺序与因果线索。

### 14.2 perf 主要解决什么问题？

perf 主要用于硬件/软件事件计数、CPU 采样热点、调用栈，以及部分调度、锁和 tracepoint 分析。

### 14.3 perf stat 与 perf record 有什么区别？

`perf stat` 汇总事件计数；`perf record` 保存样本或事件记录，之后用 `perf report/script` 分析热点与调用栈。

### 14.4 perf report 的 Overhead 就是函数自身耗时吗？

不一定。它是样本占比，受采样事件、调用图展示和 children/self 统计影响，应结合调用栈解释。

### 14.5 tracepoint 是什么？

tracepoint 是内核源码显式定义的静态事件点，具有特定字段和语义，通常比探测内部函数更稳定。

### 14.6 tracepoint 和 kprobe 有什么区别？

tracepoint 预定义且相对稳定；kprobe 可动态附着内部函数或地址，更灵活，但依赖版本、符号、函数签名和 ABI。

### 14.7 ftrace 是什么？

ftrace 是内核追踪框架和 tracer 集合，可进行函数入口、function graph、延迟追踪等；它通常通过 tracefs 控制。

### 14.8 function 与 function_graph 有什么区别？

function tracer 主要记录函数入口；function_graph 还记录返回、嵌套和耗时，因此信息和开销通常更多。

### 14.9 tracefs 与 ftrace 是什么关系？

ftrace 提供追踪能力，tracefs 暴露控制文件和 buffer；trace event 等其他 tracing 能力也共享 tracefs 接口。

### 14.10 trace 与 trace_pipe 有什么区别？

`trace` 用于读取 buffer 当前视图；`trace_pipe` 实时等待并消费新数据。两者都受有限 buffer 和覆盖行为影响。

### 14.11 trace-cmd 有什么作用？

它是 tracefs/ftrace 的用户态前端，负责配置事件、采集多 CPU 数据、保存 `trace.dat` 并离线报告。

### 14.12 bpftrace 为什么适合排障？

它能快速附着多类 probe，在内核侧过滤、关联事件、聚合分布和采集栈，适合验证临时假设。

### 14.13 为什么高频事件不应逐条 printf？

逐条输出会增加数据传输、格式化和用户态消费压力，可能丢事件并显著扰动系统；应优先内核侧聚合。

### 14.14 BTF 有什么作用？

BTF 提供紧凑的类型信息，帮助 BPF 工具理解内核类型和实现 CO-RE 字段重定位；但它不消除 attach 点和语义变化。

### 14.15 CO-RE 是什么？

CO-RE 利用目标内核 BTF 在加载时重定位结构字段访问，提高 BPF 程序跨内核版本的适配能力。

### 14.16 kprobe 为什么可能跨版本失效？

内部函数可能改名、内联、签名变化或不可探测，参数还依赖架构 ABI，因此必须在目标内核验证。

### 14.17 uprobe 用来做什么？

uprobe 动态探测用户态二进制或库函数，可观察应用函数、glibc、pthread 等边界；需要正确符号或偏移。

### 14.18 crash 能观察运行时 sched_switch 吗？

不能。crash 分析冻结的 live 状态或 vmcore，不会还原崩溃前未采集的事件时间线。

### 14.19 crash 和 drgn 有什么区别？

crash 适合成熟的交互式首轮分析；drgn 用 Python 读取对象，适合批量遍历、自动化和一致性检查。

### 14.20 调度延迟应该观察哪些事件？

核心是 `sched_wakeup` 到目标任务成为 `sched_switch.next` 的时间，并结合 CPU、IRQ/softirq、迁移和 cgroup 状态分析。

### 14.21 CPU 高为什么先用 perf？

因为首要问题是 CPU 周期花在哪些函数和调用栈。找到热点类别后，再用 tracing 深挖事件时间线或参数。

### 14.22 如何判断发生了追踪数据丢失？

检查工具报告的 lost events、buffer 覆盖状态和事件速率；同时缩小范围、增大合理 buffer、降低输出并做对照实验。

### 14.23 如何降低生产追踪风险？

限时、限 PID/CPU/事件，先过滤再记录，优先聚合，避免高频栈和逐条打印，并保存和恢复 tracing 状态。

### 14.24 没有输出是否说明目标路径没执行？

不能直接判断。还要排查事件名、字段过滤、权限、内核配置、符号、attach 状态和 buffer 丢失。

### 14.25 为什么结论要区分事实、推断和假设？

追踪输出只覆盖特定窗口和字段。明确证据等级能避免把相关性当因果，并指导下一次最小化验证。

## 15. 面试中的典型追问链

### 15.1 从“CPU 高”继续追问

```text
Q：CPU 高先用什么？
A：先用 perf record/report 找热点函数和调用栈。

Q：热点在调度函数怎么办？
A：再采 sched tracepoint，看切换、wakeup、迁移和 runnable 压力。

Q：发现 IRQ 栈很多呢？
A：对照 /proc/interrupts 和 irq/softirq 事件，查看速率与 CPU 分布。

Q：为什么不一开始全开 tracing？
A：问题尚未收敛，全量采集开销大、噪声多，也更容易丢事件。
```

### 15.2 从“tracepoint 与 kprobe”继续追问

```text
Q：已有 tracepoint 为什么优先用它？
A：字段语义明确、相对稳定，通常比内部函数探针更可维护。

Q：字段不够怎么办？
A：确认函数与签名后使用 kprobe/fprobe，或用 bpftrace 读取所需数据。

Q：要长期部署呢？
A：优先稳定 tracepoint；BPF 工具可用 libbpf CO-RE 工程化。

Q：CO-RE 是否保证完全跨版本？
A：不保证，它主要解决结构字段重定位，语义和 attach 点仍可能变化。
```

### 15.3 从“调度延迟”继续追问

```text
Q：如何量 wakeup latency？
A：记录 sched_wakeup 时间，再等同一 PID 成为 sched_switch.next。

Q：延迟大就是调度器 bug 吗？
A：不一定，可能是 CPU 繁忙、IRQ 干扰、优先级、迁移或 cgroup 限流。

Q：怎么分辨 IRQ 干扰？
A：在同一时钟和采集窗口加入 irq/softirq entry/exit 事件。

Q：如何看延迟分布？
A：用 bpftrace/eBPF 在内核侧关联事件并生成直方图。
```

## 16. 容易说错的十句话

### 错误 1：perf 就是看 CPU 使用率

正确：perf 还能计数 PMU/软件事件、采样调用栈，并分析调度、锁和 tracepoint 数据。

### 错误 2：tracepoint 和 kprobe 都是随便插入的动态探针

正确：tracepoint 是源码预定义静态事件；kprobe 才是运行时动态函数/地址探针。

### 错误 3：ftrace 只是一个用户态命令

正确：ftrace 是内核追踪框架和 tracer 集合，通常通过 tracefs 或 trace-cmd 控制。

### 错误 4：trace_pipe 会永久保存所有事件

正确：它消费有限 ring buffer 中的新数据，生产速度过高时仍可能覆盖或丢失。

### 错误 5：bpftrace 使用 eBPF，所以没有开销

正确：probe 执行、map 更新、采栈和数据输出都有成本，只是可以高效过滤和聚合。

### 错误 6：有 BTF，BPF 程序就一定跨版本运行

正确：BTF/CO-RE 主要帮助类型和字段重定位，attach 点、字段语义和内核能力仍可能不兼容。

### 错误 7：crash 可以还原 panic 前所有调度事件

正确：crash 看冻结状态；历史时间线必须在故障前已由 tracing、pstore 等机制记录。

### 错误 8：追不到事件就说明代码没有执行

正确：还可能是事件未启用、过滤错误、权限不足、探针失败、版本差异或数据丢失。

### 错误 9：生产排障应该尽可能多开事件

正确：应围绕假设启用最少事件，限时限范围，并逐步扩大采集。

### 错误 10：看到相关时间点就证明存在因果关系

正确：时间相关只是线索，需要更多字段、调用栈、源码路径或对照实验验证因果。

## 17. 一页背诵级总结

### 17.1 五类证据

```text
CPU 花在哪里：perf 采样
事件如何发生：tracepoint/trace-cmd 时间线
函数如何调用：ftrace function_graph
事件如何关联：bpftrace/eBPF 聚合
崩溃时什么状态：crash/drgn 读 vmcore
```

### 17.2 核心工具

```text
perf stat：汇总计数
perf record/report：样本与热点调用栈
tracepoint：内核静态语义事件
tracefs：tracing 控制文件与 buffer
trace-cmd：配置并保存 trace.dat
ftrace：函数和延迟 tracer
bpftrace：快速过滤、关联、聚合和栈
kprobe/kretprobe：内核动态入口/返回探针
uprobe/uretprobe：用户函数动态探针
crash：vmcore 交互分析
drgn：Python 批量读取内核对象
```

### 17.3 选型口诀

```text
CPU 热点先 perf；
已有事件用 tracepoint；
函数路径用 ftrace；
关联聚合用 bpftrace；
字段不够补 kprobe；
用户函数用 uprobe；
系统已崩看 crash；
批量对象用 drgn；
长期部署考虑 tracepoint 或 libbpf CO-RE。
```

### 17.4 五类故障

```text
CPU 高：perf 找热点，再按热点类别深挖
调度延迟：wakeup → switch，叠加 IRQ 和限流证据
锁竞争：perf lock/lockstat + 慢路径调用栈
IRQ 干扰：interrupts/softirqs + 同时间线事件
panic：sys/log/bt/bt -a/ps/runq + 关键对象
```

### 17.5 生产安全

```text
限时、限 PID、限 CPU、限事件
先过滤，后记录；先聚合，后采栈
高频路径不要逐条打印
检查 lost events 和 buffer 覆盖
核对权限、配置、符号、BTF 和版本
保存完整命令、环境、原始证据和恢复步骤
```

### 17.6 最终回答模板

拿到追踪问题，按六步回答：

```text
1. 现象是什么，发生在运行中还是已经崩溃？
2. 需要统计、时间线、调用栈还是对象快照？
3. 选择能直接提供该证据的最小工具。
4. 限定时间、PID、CPU、事件和输出量。
5. 检查丢失、权限、符号、版本与观测开销。
6. 区分已确认事实、合理推断和待验证假设。
```

面试官更看重能否建立可验证的证据链，而不是背出最多命令。

# Linux 内核中断：一小时面试版

> 目标：面向通用 Linux 岗，在一小时内建立能应付常见面试追问的中断知识框架。
>
> 阅读方法：先掌握第 1～8 节的主线，再看排障和高频问答，最后用末尾速记复习。

**缩写约定：** CPU（Central Processing Unit，中央处理器）、IRQ（Interrupt Request，中断请求）、MSI（Message Signaled Interrupt，消息信号中断）、GIC（Generic Interrupt Controller，通用中断控制器）、APIC（Advanced Programmable Interrupt Controller，高级可编程中断控制器）、IPI（Inter-Processor Interrupt，处理器间中断）、NAPI（New API，Linux 网络收包机制）、RCU（Read-Copy Update）、CMWQ（Concurrency Managed Workqueue）、NUMA（Non-Uniform Memory Access，非统一内存访问）、RSS/RPS/XPS（Receive Side Scaling/Receive Packet Steering/Transmit Packet Steering）首次出现时均按此含义理解。

## 1. 先背下一次中断的完整主线

```text
外设产生事件
    ↓
外设置位状态寄存器，并拉高中断线或发送 MSI
    ↓
中断控制器收集、屏蔽、仲裁并选择目标 CPU
    ↓
CPU 检测到 IRQ，暂停当前执行流
    ↓
硬件和入口代码保存必要现场，进入内核中断入口
    ↓
读取硬件中断号 hwirq
    ↓
irq_domain：hwirq → Linux IRQ number（virq）
    ↓
通过 virq 找到 irq_desc
    ↓
irq_desc 的 flow handler 处理 mask/ack/eoi 等流控
    ↓
调用驱动通过 request_irq() 注册的 handler
    ↓
handler 清设备中断源，必要时调度下半部
    ↓
处理 pending softirq，或稍后由线程执行延后工作
    ↓
恢复被中断现场，返回用户态或内核态
```

面试时可以压缩为一句话：

> 设备先通知中断控制器，控制器把 IRQ 投递给某个 CPU；CPU 进入内核中断入口，通过 irq_domain 把硬件号转换为 Linux IRQ number，再由 irq_desc 的流控处理函数调用驱动 handler，完成确认、清中断源和必要的下半部调度，最后恢复现场。

### 1.1 中断不会让被打断的进程凭空消失

假设用户进程 A 正在 CPU0 上运行：

```text
用户进程 A
    ↓
硬件中断到来
    ↓
CPU 保存 A 的必要寄存器
    ↓
在 A 当前内核栈或体系结构规定的中断栈上处理中断
    ↓
中断处理结束
    ↓
可能继续运行 A，也可能因 need_resched 调度到 B
```

中断是一次控制流打断，不等同于进程切换。
只有中断退出路径发现需要调度，并且当前处于可调度点时，才可能发生任务切换。

## 2. interrupt、exception、system call、softirq 的区别

### 2.1 硬件中断 interrupt

硬件中断通常来自当前指令之外的异步事件：

```text
网卡收到数据
磁盘完成 I/O
键盘按键
定时器到期
GPIO 电平变化
```

特点：

```text
异步
通常来自外设或中断控制器
与当前正在执行的指令没有直接因果关系
```

### 2.2 异常 exception

异常是 CPU 执行当前指令时同步产生的事件：

```text
缺页异常 page fault
除零
非法指令
访问权限错误
断点
```

特点：

```text
同步
与当前指令直接相关
同一条指令在相同条件下通常会再次触发
```

### 2.3 系统调用 system call

系统调用是用户程序通过体系结构规定的 syscall 指令主动进入内核的受控入口，例如 `read()`、`write()`；它是同步、主动的，不是外设异步中断。

### 2.4 Linux softirq

SoftIRQ 全称可理解为 software interrupt，但 Linux 的 softirq 是内核下半部机制，不是 CPU 异常意义上的“软件触发中断指令”。

```text
hardirq：硬件中断到来后立即执行的部分
softirq：把部分工作标记为 pending，稍后在软中断上下文执行
```

### 2.5 面试对比表

| 类型               | 来源             | 同步性   | 典型例子                              | 是否由当前指令直接导致 |
| ------------------ | ---------------- | -------- | ------------------------------------- | ---------------------- |
| hardware interrupt | 外设/中断控制器  | 异步     | 网卡、磁盘、时钟                      | 否                     |
| exception          | CPU              | 同步     | 缺页、除零、非法指令                  | 是                     |
| system call        | 用户程序         | 同步     | `read()`、`write()`               | 是，主动请求           |
| Linux softirq      | 内核软件 pending | 延后执行 | `NET_RX_SOFTIRQ`、`TIMER_SOFTIRQ` | 通常由内核路径触发     |

## 3. 中断与轮询如何取舍

纯轮询会在设备无事件时浪费 CPU；中断让设备按需通知 CPU，通常更节能、响应也更及时。
中断也并非越多越好。高速网络常结合两者，例如 NAPI 在低流量时用中断保证延迟，高流量时暂时抑制中断并批量 poll，避免 CPU 被中断淹没。

## 4. 中断控制器和 Linux IRQ 编号体系

### 4.1 中断控制器做什么

中断控制器位于外设和 CPU 之间，典型职责包括：

```text
接收多个中断源
enable/disable 或 mask/unmask
记录 pending 状态
设置触发类型和优先级
选择目标 CPU
向 CPU 投递中断
接收 ack/eoi
```

ARM 平台常见 GIC（Generic Interrupt Controller），x86 常见 APIC/MSI 体系。
面试不需要背寄存器，只需知道控制器负责“收集、仲裁、投递”。

### 4.2 hwirq、virq 和 irq_domain

```text
hwirq
    硬件中断控制器内部使用的编号
virq / Linux IRQ number
    Linux 通用中断层和驱动使用的逻辑编号
irq_domain
    负责 hwirq 和 virq 的映射
```

第一张必会关系图：

```text
设备描述（设备树/ACPI/PCI）
            ↓
       hwirq + 触发类型
            ↓
        irq_domain
            ↓
    Linux IRQ number（virq）
            ↓
          irq_desc
```

为什么不让驱动直接使用 hwirq？

```text
系统可能串联多个中断控制器
不同控制器的 hwirq 可能重复
硬件编号只在所属控制器内部有意义
Linux 需要统一编号供通用层和驱动使用
```

驱动从平台总线、PCI、设备树解析等接口取得的 `irq`，通常已经是 Linux IRQ number。

### 4.3 irq_desc、irq_chip、irqaction

第二张必会关系图：

```text
irq_desc：某个 Linux IRQ 的总描述
├── irq_data：hwirq、irq_domain、chip 等硬件相关信息
├── irq_chip：mask/ack/eoi/set_affinity 等控制器操作
├── handle_irq：level/edge/fasteoi 等通用流控函数
└── action 链表：驱动通过 request_irq() 注册的 handler
```

一句话区分：

```text
irq_desc 管一个 IRQ 的总体状态
irq_chip 操作中断控制器硬件
flow handler 管通用中断流控
irqaction 保存设备驱动 handler
```

不要混淆：

```text
irq_chip handler ≠ 驱动业务 handler
handle_level_irq() ≠ 驱动自己注册的 handler
```

## 5. 中断上下文到底是什么

### 5.1 hardirq 不是普通进程上下文

中断可能打断任意任务。处理中断时，`current` 往往仍指向被打断的 task，但当前控制流不是在替这个 task 执行业务逻辑。
因此不能因为 `current` 非空，就认为可以睡眠。
hardirq 上下文的核心限制：

```text
不能睡眠
不能调用可能阻塞的函数
不能获取 mutex、semaphore 等睡眠锁
不能进行可能使用 GFP_KERNEL 睡眠的分配
不能做长时间计算
必须尽快确认和清除中断源
```

常用判断辅助接口包括：

```c
in_interrupt();
in_irq();
in_softirq();
```

理解语义即可，不建议用它们替代正确的接口设计。

### 5.2 为什么 hardirq 不能睡眠

睡眠意味着：

```text
把当前 task 设置成不可运行状态
调用 schedule()
切换到另一个 task
以后再恢复当前 task
```

但 hardirq 是借用被打断任务的执行现场，并不是一个可独立调度的普通 task。
如果在 hardirq 中睡眠：

```text
没有一个合法的“中断任务”可供调度器挂起和恢复
可能破坏被打断 task 的状态
可能在持有自旋锁或禁止抢占时调用 schedule()
```

内核通常会报告类似：

```text
BUG: sleeping function called from invalid context
scheduling while atomic
```

### 5.3 中断上下文可以使用什么锁

可使用不会睡眠的自旋锁，但必须考虑同一数据是否也被中断访问。
典型场景：进程上下文和本 CPU hardirq 共享数据：

```c
spin_lock_irqsave(&lock, flags);
/* critical section */
spin_unlock_irqrestore(&lock, flags);
```

只使用 `spin_lock()` 可能出现：

```text
进程上下文拿到锁
    ↓
本 CPU 发生中断
    ↓
中断 handler 再拿同一把锁
    ↓
中断无法返回，原执行流无法释放锁，自锁死
```

如果数据只会被进程上下文和 softirq 访问，常见形式是：

```c
spin_lock_bh(&lock);
/* critical section */
spin_unlock_bh(&lock);
```

### 5.4 上下文能力表

| 上下文        | 能睡眠 | 能用 mutex |    能用 spinlock | 典型用途                  |
| ------------- | -----: | ---------: | ---------------: | ------------------------- |
| hardirq       |     否 |         否 | 是，注意 irqsave | 紧急硬件处理              |
| softirq       |     否 |         否 |     是，注意并发 | 网络、timer、RCU 等       |
| tasklet       |     否 |         否 |               是 | 老驱动下半部              |
| threaded IRQ  |     是 |         是 |               是 | 与某 IRQ 紧密相关的慢处理 |
| workqueue     |     是 |         是 |               是 | 通用异步任务              |
| kernel thread |     是 |         是 |               是 | 长期后台任务              |

## 6. 为什么要分上半部和下半部

中断处理存在两个相反目标：

```text
硬件要求尽快响应、确认、清状态
复杂业务又可能耗时甚至睡眠
```

因此拆成：

```text
上半部 top half / hardirq
    立即执行
    做最紧急、最少的工作
    读取状态、清中断源、搬少量数据、唤醒下半部
下半部 bottom half / deferred work
    延后执行
    做协议处理、复杂状态机、可能阻塞的操作
```

以网卡收包为例：

```text
网卡 IRQ
    ↓
hardirq 确认中断并安排 NAPI
    ↓
NET_RX_SOFTIRQ 中批量 poll 数据包
    ↓
进入网络协议栈
```

以慢速 I2C 设备为例：

```text
GPIO IRQ
    ↓
primary handler 快速返回 IRQ_WAKE_THREAD
    ↓
thread_fn 中通过可能睡眠的 I2C 接口读取设备
```

“上半部/下半部”是设计思想，不是只有一种固定 API。

## 7. 四种延后机制怎么选

### 7.1 softirq

softirq 是内核预定义的高性能下半部机制。
特点：

```text
运行在软中断上下文
不能睡眠
同一种 softirq 可以在不同 CPU 并发执行
类型数量固定，普通驱动通常不会新增一种 softirq
适合网络、定时器、RCU、块设备等核心子系统
```

典型类型：

```text
NET_RX_SOFTIRQ
NET_TX_SOFTIRQ
TIMER_SOFTIRQ
SCHED_SOFTIRQ
RCU_SOFTIRQ
BLOCK_SOFTIRQ
```

触发与执行：

```text
raise_softirq()
    ↓
设置当前 CPU pending 位
    ↓
hardirq 返回路径或 local_bh_enable() 等位置检查
    ↓
执行 softirq
    ↓
预算耗尽或压力过大时交给 ksoftirqd/N
```

注意：`ksoftirqd` 是内核线程，但它处理的 softirq 逻辑仍需遵守不能睡眠的 softirq 约束。

### 7.2 tasklet

tasklet 是建立在 softirq 之上的老式下半部封装。
特点：

```text
不能睡眠
同一个 tasklet 不会在多个 CPU 上同时执行
不同 tasklet 仍可能并发
历史驱动中常见
新设计一般优先考虑 threaded IRQ、workqueue 或子系统专用机制
```

面试回答重点：

> tasklet 比直接使用 softirq 更方便，并串行化同一个 tasklet，但它仍运行在 softirq 上下文，不能睡眠；维护旧代码需要认识，新代码通常不优先选它。

### 7.3 workqueue

Workqueue 是通用异步执行机制。普通 threaded workqueue 由 worker/kworker 在线程上下文执行 work item。
特点：

```text
可以睡眠
可以拿 mutex
可以调用阻塞式 I/O
适合不必紧贴某个 IRQ 的通用延后工作
调度延迟通常高于直接 softirq
```

最小使用形式：

```c
static void demo_workfn(struct work_struct *work)
{
    /* process context: may sleep */
}
static DECLARE_WORK(demo_work, demo_workfn);
/* 可从合适的上半部路径安排 */
schedule_work(&demo_work);
```

设备移除时要处理生命周期：

```c
cancel_work_sync(&dev->work);
```

否则 work 可能在设备内存释放后继续访问，形成 use-after-free。

### 7.4 threaded IRQ

`request_threaded_irq()` 把一个 IRQ 的处理拆成两段：

```text
primary handler
    hardirq 上下文
    快速确认并返回 IRQ_WAKE_THREAD
thread_fn
    IRQ 内核线程上下文
    可以睡眠、拿 mutex、访问 I2C/SPI
```

典型形式：

```c
static irqreturn_t demo_irq(int irq, void *data)
{
    /* 快速读取/确认必要状态 */
    return IRQ_WAKE_THREAD;
}
static irqreturn_t demo_irq_thread(int irq, void *data)
{
    /* may sleep */
    return IRQ_HANDLED;
}
request_threaded_irq(irq, demo_irq, demo_irq_thread,
                     IRQF_ONESHOT, "demo", dev);
```

如果 `handler == NULL` 且 `thread_fn != NULL`，内核可以安装默认 primary handler，它主要负责唤醒线程。

### 7.5 选择表

| 机制           | 执行上下文                                 | 能睡眠 | 并发特点            | 优先适用场景     |
| -------------- | ------------------------------------------ | -----: | ------------------- | ---------------- |
| softirq        | interrupt context                          |     否 | 同类型可跨 CPU 并发 | 核心高性能子系统 |
| tasklet        | softirq context                            |     否 | 同一 tasklet 不并发 | 维护旧驱动       |
| workqueue      | worker thread CFS（NORMAL_BATCH NICE -20） |     是 | 由 worker pool 管理 | 通用异步工作     |
| threaded IRQ   | IRQ thread（RT FIFO 50）                   |     是 | 与 IRQ 生命周期紧密 | 慢速设备中断处理 |
| 面试选择口诀： |                                            |        |                     |                  |

```text
必须极快且不能睡：子系统已有 softirq/NAPI 机制
与某个 IRQ 强相关且需要睡：threaded IRQ
通用延后工作且需要睡：workqueue
看到旧 tasklet：知道不能睡，通常不建议新写
```

官方参考：

- [Linux generic IRQ handling](https://docs.kernel.org/core-api/genericirq.html)
- [Linux Workqueue](https://docs.kernel.org/core-api/workqueue.html)

## 8. 驱动申请中断的高频 API

### 8.1 request_irq()

```c
int request_irq(unsigned int irq,
                irq_handler_t handler,
                unsigned long flags,
                const char *name,
                void *dev_id);
```

参数：

```text
irq
    Linux IRQ number，通常不是 hwirq
handler
    hardirq 上下文执行的处理函数
flags
    触发类型、共享、oneshot 等标志
name
    /proc/interrupts 中显示的设备名
dev_id
    传给 handler 的设备私有指针
    共享 IRQ 时也用于区分 irqaction
```

handler 原型：

```c
static irqreturn_t demo_handler(int irq, void *dev_id)
{
    struct demo_dev *dev = dev_id;
    if (!demo_irq_pending(dev))
        return IRQ_NONE;
    demo_clear_irq(dev);
    return IRQ_HANDLED;
}
```

返回值：

```text
IRQ_NONE
    不是本设备产生的中断，尤其用于共享 IRQ 判断
IRQ_HANDLED
    本设备已处理该中断
IRQ_WAKE_THREAD
    请求唤醒 threaded handler
```

### 8.2 request_threaded_irq()

```c
int request_threaded_irq(unsigned int irq,
                         irq_handler_t handler,
                         irq_handler_t thread_fn,
                         unsigned long flags,
                         const char *name,
                         void *dev_id);
```

`request_irq()` 可以理解为没有 `thread_fn` 的普通封装。

### 8.3 IRQF_SHARED

多个设备共享一条 IRQ 时：

```c
request_irq(irq, handler, IRQF_SHARED, "demo", dev);
```

要求：

```text
所有共享者都同意共享
dev_id 必须能唯一标识本设备，通常不能为 NULL
每个 handler 都必须读取设备状态判断是否为自己的中断
不是自己的中断要返回 IRQ_NONE
释放时 free_irq(irq, dev_id) 必须传回同一个标识
```

共享 IRQ 不代表多个 handler 同时并行处理；通用层会遍历该 IRQ 的 action 链表。

### 8.4 IRQF_ONESHOT

threaded IRQ 常配合 `IRQF_ONESHOT`：

```text
中断到来
    ↓
唤醒 thread_fn
    ↓
thread_fn 运行期间保持该 IRQ line masked
    ↓
所有相关线程处理完成后再 unmask
```

适用于设备中断源只有在线程中完成慢速操作后才能安全清除的场景。
它不是“中断只触发一次”，而是“一次线程化处理完成前不重新开放这条 IRQ”。

### 8.5 free_irq() 与同步

```c
free_irq(irq, dev_id);
```

驱动退出时必须保证：

```text
设备不再产生新中断
已经开始的 handler 不再访问即将释放的资源
下半部 work/thread 等也完成或取消
```

常见 remove 顺序要结合设备手册设计，不能只机械调用 `free_irq()`。

### 8.6 devm_request_irq()

`devm_request_irq()` 使用 device-managed 资源管理，在设备 detach 时自动释放 IRQ 注册。
它能减少错误路径和 remove 路径的资源释放代码，但不会自动解决：

```text
设备仍在产生中断
已排队 work 的生命周期
硬件关闭顺序
驱动私有并发状态
```

## 9. level、edge、mask、ack、eoi

### 9.1 电平触发 level-triggered

只要中断线维持有效电平，中断条件就持续存在。

```text
设备置位 status
    ↓
中断线保持高/低电平
    ↓
CPU 进入 handler
    ↓
驱动必须清除设备中断源
    ↓
中断线恢复无效
```

如果没有清设备状态，中断会在返回后立即再次到来，形成中断风暴。

### 9.2 边沿触发 edge-triggered

边沿触发关注电平跳变，例如低到高的一瞬间。

```text
优点：不会因为线一直保持有效而不停触发
风险：短边沿或处理期间的新边沿需要控制器 pending 机制正确保存
```

### 9.3 四个术语

```text
mask
    暂时禁止该 IRQ 继续向 CPU 投递
unmask
    重新允许该 IRQ 投递
ack
    确认控制器已经接收到/开始处理该中断
eoi（End Of Interrupt）
    告诉控制器本次中断处理结束
```

最容易答错的一点：

> ack/eoi 是中断控制器层面的操作；清设备中断源是访问外设状态寄存器。二者不是一回事。
> 不同控制器和触发类型的具体顺序不同，通用 flow handler 会封装这些差异，驱动通常只负责设备自身状态。

## 10. 多核、中断亲和性和 per-CPU IRQ

### 10.1 IRQ affinity

IRQ affinity 表示某个可路由中断允许投递到哪些 CPU。
查看：

```bash
cat /proc/irq/<irq>/smp_affinity
cat /proc/irq/<irq>/smp_affinity_list
```

设置示例：

```bash
echo 2 > /proc/irq/<irq>/smp_affinity_list
```

可能收益：

```text
把中断负载分散到多个 CPU
让 IRQ 与处理相关数据的任务靠近，提高 cache locality
隔离实时 CPU 上的普通设备中断
配合网卡多队列、RSS/RPS/XPS 优化吞吐
```

风险：

```text
把大量 IRQ 集中到一个 CPU 会形成瓶颈
跨 NUMA 节点可能增加远程内存访问
irqbalance 可能覆盖手工设置
并非所有 IRQ 都支持任意 affinity
```

affinity 是允许集合，实际投递还受控制器能力、IRQ 类型、CPU 在线状态、managed IRQ 和 irqbalance 等约束。per-CPU IRQ（如本地定时器和部分 IPI）在每个 CPU 上有独立实例，不能像普通共享外设 IRQ 一样任意迁移。

IRQ、softirq 和最终消费数据的用户进程也可能位于不同 CPU。性能调优需要综合考虑 affinity、设备队列、softirq、cache/NUMA 和应用线程，而不是只修改一个 mask。

## 12. 如何看 /proc/softirqs 和 ksoftirqd

```bash
cat /proc/softirqs
```

示意输出：

```text
# cat /proc/softirqs
                    CPU0       CPU1       CPU2       CPU3
          HI:          0          0          0          0
       TIMER:    1127660     849962     908633     912690
      NET_TX:         45         47       9867        464
      NET_RX:      10771       7563    2785078     400045
       BLOCK:          0          0          0          0
    IRQ_POLL:          0          0          0          0
     TASKLET:         14         10      23875       6341
       SCHED:    1370946    1047470    1079207    1104306
     HRTIMER:          0          0          0          0
         RCU:     728819     743002     757228     740854
```

分析方法：

```text
先看哪一种 softirq 增长快
再看是否集中在某个 CPU
把 /proc/softirqs 和 /proc/interrupts 对照
结合网络、块设备、timer 或 RCU 的具体负载
```

### 12.1 为什么会出现 ksoftirqd/N

如果一直在 hardirq 返回路径中处理 softirq，用户任务可能长期得不到运行。
内核会对一次 softirq 处理设置时间或轮次预算。处理不完时，剩余工作交给每 CPU 的：

```text
ksoftirqd/0
ksoftirqd/1
...
```

### 12.2 ksoftirqd 高占用意味着什么

它表示该 CPU 上 softirq 压力大，不等于 `ksoftirqd` 自己有 bug。
常见来源：

```text
大量网络收包，NET_RX 高
网络发送完成处理，NET_TX 高
块设备完成事件多，BLOCK 高
timer 数量或频率异常
RCU callback 堆积
IRQ/队列 affinity 过度集中
```

基础排查：

```bash
cat /proc/softirqs
cat /proc/interrupts
mpstat -P ALL 1
pidstat -w 1
perf top
```

网络问题再结合：

```bash
ethtool -S eth0
ethtool -l eth0
ethtool -x eth0
```

## 13. 中断风暴怎么回答

### 13.1 定义

中断风暴是某个或某类 IRQ 以异常高频率持续触发，CPU 大量时间消耗在 hardirq/softirq 中，正常任务受影响。

### 13.2 常见原因

```text
level IRQ 的设备中断源没有清除
触发类型或极性配置错误
handler 清状态顺序错误
设备硬件或线路异常
共享 IRQ handler 错误判断或返回
过早 unmask
真实业务流量超过系统处理能力
```

### 13.3 现象

```text
/proc/interrupts 某行快速增长
CPU irq/soft 很高
ksoftirqd 高
系统响应变慢
日志被重复错误刷屏
网络丢包或任务延迟增大
```

### 13.4 排查顺序

```text
1. 连续采样 /proc/interrupts，定位增长最快的 IRQ
2. 确认 IRQ 对应的设备和驱动
3. 查看 Level/Edge、极性和 affinity
4. 查看设备 status/mask/enable 寄存器
5. 确认 handler 是否清了正确的设备中断源
6. 对照 /proc/softirqs 判断压力是否延伸到下半部
7. 必要时短时间屏蔽该 IRQ 做验证，但要评估业务风险
8. 结合 perf/ftrace/设备统计进一步定位
```

不要一看到计数高就认定是风暴。高吞吐网卡的 IRQ 很高可能完全正常，关键看增长率、CPU 占用、处理能力和业务症状。

## 14. 丢中断怎么回答

### 14.1 表现

```text
设备报告发生了事件
但驱动 handler 没有执行，或处理次数少于预期
```

### 14.2 分层定位

```text
设备层
    事件是否真的发生
    status 是否置位
    interrupt enable 是否打开
连线/描述层
    pinmux 是否正确
    设备树/ACPI 信息是否正确
    interrupt-parent、hwirq、触发类型是否正确
控制器层
    IRQ 是否被 mask
    pending 是否存在
    affinity 目标 CPU 是否在线
Linux 通用层
    是否获得正确 virq
    request_irq() 是否成功
    IRQ 是否被 disable
驱动层
    handler 是否误判为 IRQ_NONE
    是否过早清除状态
    并发和关闭顺序是否正确
```

### 14.3 边沿和电平的不同风险

```text
电平触发：不清状态容易重复触发
边沿触发：边沿很短，配置或 pending 处理错误可能漏掉事件
```

排障时要先确认硬件实际信号与软件配置匹配。

## 15. 高频面试问答

### 15.1 中断和异常有什么区别？

中断通常由外设异步产生，与当前指令无直接关系；异常由 CPU 执行当前指令同步产生，例如缺页、除零和非法指令。系统调用也是同步进入内核，但属于用户主动请求。

### 15.2 中断发生时一定会进程切换吗？

不一定。CPU 保存当前现场后执行中断处理，结束后可以直接恢复原任务。只有退出路径发现需要调度且满足调度条件时，才会切换到其他 task。

### 15.3 为什么中断处理函数不能睡眠？

hardirq 不是可独立调度的普通 task，它借用被打断任务的现场，常处于禁止抢占或原子上下文。睡眠会调用调度器，破坏上下文和锁语义。

### 15.4 为什么要区分上半部和下半部？

上半部必须快速响应硬件、确认并清中断源；耗时或可能阻塞的工作延后，避免长时间占用中断上下文、增加系统延迟。

### 15.5 softirq 在什么时候执行？

常见于 hardirq 返回路径、重新启用 bottom half 的路径，或压力过大时由每 CPU 的 `ksoftirqd/N` 继续处理。

### 15.6 softirq 能睡眠吗？

不能。即使某些 softirq 由 `ksoftirqd` 线程触发执行，softirq handler 本身仍按软中断上下文设计，不能调用可能睡眠的接口。

### 15.7 softirq 为什么并发复杂？

同一种 softirq 可以在多个 CPU 上同时执行，因此共享数据需要 per-CPU 设计、锁、RCU 或其他同步机制。

### 15.8 tasklet 和 softirq 有什么区别？

tasklet 基于 softirq，是更易用的动态封装；同一个 tasklet 不会跨 CPU 并发，但不同 tasklet 可以并发。二者都不能睡眠。tasklet 多见于旧代码，新代码通常优先其他机制。

### 15.9 workqueue 和 softirq 最大区别是什么？

普通 workqueue 由 worker 线程在进程上下文执行，可以睡眠和使用 mutex；softirq 在中断上下文执行，不能睡眠，但延迟更低、性能路径更直接。

### 15.10 threaded IRQ 和 workqueue 怎么选？

慢处理与某一 IRQ 强相关时优先 threaded IRQ；通用异步任务、多个触发源、需要延迟或自定义队列属性时使用 workqueue。

### 15.11 hwirq 和 virq 有什么区别？

`hwirq` 是某个中断控制器内部编号；`virq` 是 Linux 通用中断层使用的 IRQ number；`irq_domain` 负责映射二者。

### 15.12 irq_desc、irq_chip、irqaction 分别是什么？

`irq_desc` 管理一个 Linux IRQ；`irq_chip` 提供控制器的 mask/ack/eoi 等操作；`irqaction` 保存驱动注册的 handler、name、dev_id 和 flags。

### 15.13 request_irq() 传入的是 hwirq 吗？

通常不是。驱动通过平台、PCI 等接口取得的 IRQ 一般已经是 Linux IRQ number。

### 15.14 IRQ_NONE 和 IRQ_HANDLED 有什么区别？

`IRQ_NONE` 表示当前 handler 判断该中断不是自己的；`IRQ_HANDLED` 表示本设备识别并处理了中断。共享 IRQ 尤其依赖这个判断。

### 15.15 共享 IRQ 为什么需要 dev_id？

它既传递设备私有数据，也用于在同一 IRQ 的 action 链表中唯一标识注册者；`free_irq()` 依靠相同的 `dev_id` 删除对应 handler。

### 15.16 IRQF_ONESHOT 是不是中断只触发一次？

不是。它表示 threaded handler 运行期间保持 IRQ masked，线程处理完成后重新开放，防止线程尚未处理完时同一 IRQ 再次进入。

### 15.17 ack、eoi 和清设备中断源一样吗？

不一样。ack/eoi 是中断控制器层面的确认和结束操作；清设备中断源是驱动访问外设寄存器，使设备撤销中断条件。

### 15.18 电平触发为什么容易产生中断风暴？

只要设备状态未清，中断线就持续有效；handler 返回后控制器会再次投递，于是形成高速重复中断。

### 15.19 为什么边沿触发可能丢中断？

边沿只在电平跳变瞬间存在。如果硬件、控制器 pending 机制、触发配置或驱动处理不正确，处理期间出现的新边沿可能无法被可靠记录。

### 15.20 IRQ affinity 有什么作用？

它限制可路由 IRQ 投递到哪些 CPU，用于分散负载、改善 cache/NUMA locality 或隔离 CPU。是否生效还取决于 IRQ 类型、控制器、驱动和 irqbalance。

### 15.21 /proc/interrupts 主要看什么？

看每个 IRQ 在各 CPU 上的累计次数、触发类型和设备名。计数不增长用于查未触发；异常高速增长用于查风暴；单 CPU 集中用于查 affinity 和队列分布。

### 15.22 ksoftirqd 占用高说明什么？

说明该 CPU 的 softirq 工作量超过直接处理预算，剩余工作被线程化继续处理。常见于网络、块设备、timer、RCU 压力或 IRQ 分布不均。

### 15.23 如何快速定位中断风暴？

连续采样 `/proc/interrupts` 找增长最快的 IRQ，确认设备、触发类型和 affinity，再检查设备 status、清中断逻辑以及 `/proc/softirqs` 是否同步暴涨。

### 15.24 spin_lock() 和 spin_lock_irqsave() 怎么选？

如果同一数据可能在进程上下文和本 CPU hardirq 中访问，进程路径通常需要 `spin_lock_irqsave()`，避免持锁期间被该中断打断后自锁死。具体选择取决于共享数据会出现在哪些上下文。

### 15.25 disable_irq() 和 local_irq_disable() 有什么区别？

`disable_irq(irq)` 针对某条 Linux IRQ，并会涉及等待正在执行的 handler 等同步语义；`local_irq_disable()` 只关闭当前 CPU 的本地硬中断响应，不等于在全系统禁用某条设备 IRQ。

## 16. 一页背诵级总结

### 16.1 总流程

```text
设备产生事件
→ 中断控制器仲裁并投递 CPU
→ CPU 保存现场进入 IRQ
→ hwirq 经 irq_domain 映射为 virq
→ virq 找 irq_desc
→ flow handler 调 irqaction 中的驱动 handler
→ 驱动清设备中断源并安排下半部
→ ack/eoi/unmask 完成流控
→ 恢复现场，必要时调度
```

### 16.2 核心对象

```text
hwirq：控制器内部编号
virq：Linux IRQ number
irq_domain：hwirq → virq
irq_desc：一个 IRQ 的总描述
irq_data：硬件映射信息
irq_chip：操作中断控制器
irqaction：驱动注册的 handler
```

### 16.3 上下文

```text
hardirq：不能睡，必须快
softirq：不能睡，可跨 CPU 并发
tasklet：不能睡，同一 tasklet 不并发，老机制
threaded IRQ：可以睡，与 IRQ 强相关
workqueue：可以睡，通用异步工作
```

### 16.4 API

```text
request_irq()：注册 hardirq handler
request_threaded_irq()：primary + thread_fn
IRQF_SHARED：共享 IRQ，handler 必须判断来源
IRQF_ONESHOT：thread_fn 完成前保持 IRQ masked
free_irq()：释放对应 irqaction
```

### 16.5 流控

```text
mask/unmask：禁止/允许投递
ack：确认控制器收到中断
eoi：告诉控制器处理结束
清设备中断源：驱动清外设 status
```

### 16.6 排障

```text
/proc/interrupts：看 IRQ 次数、CPU 分布、设备和触发类型
/proc/softirqs：看 softirq 类型和 CPU 分布
ksoftirqd 高：softirq 压力大，继续查具体类型和来源
中断风暴：先查计数、level 状态、触发类型和清中断逻辑
丢中断：从设备、连线、控制器、通用层、驱动逐层查
```

### 16.7 最终口诀

```text
设备发事件，控制器来管；
硬号经 domain，映射 Linux 号；
desc 管全局，chip 控硬件，action 挂驱动；
hardirq 必须快，慢活一定往后放；
softirq、tasklet 不能睡，threaded IRQ、workqueue 可以睡；
共享中断先辨来源，电平中断记得清状态；
看风暴查 interrupts，看软压查 softirqs；
ack/eoi 管控制器，清 status 才是管设备。
```

## 1. 先建立完整主线

Linux 内核中，同一份数据可能同时被多个 CPU 上的进程、内核线程、hardirq、softirq、定时器和 workqueue 访问。

同步问题可以压缩成四类：

```text
原子性：一个操作执行到一半，另一个执行流插了进来
可见性：CPU0 已写入，CPU1 未必立刻按预期观察到
顺序性：编译器和 CPU 观察到的访问顺序可能不同
生命周期：读者仍在使用对象，写者却已经释放对象
```

内核通常通过局部数据或 Per-CPU 避免共享，用 atomic 完成简单更新，用锁建立临界区，再用 seqlock、RCU 优化特定的读多写少场景。

面试时最重要的不是罗列锁，而是说出选择依据：访问者所处上下文、能否睡眠、临界区长度、读写比例，以及是否涉及对象生命周期。

一句话总括：

> 先尽量消除共享；必须共享时，再根据执行上下文、临界区长度、读写比例和对象生命周期选择同步机制。

## 2. 四个基础概念

### 2.1 竞态条件 race condition

程序结果依赖多个执行流不可预测的先后顺序，就是竞态条件。

例如两个 CPU 同时执行：

```c
counter++;
```

它可能被拆成“读取、加 1、写回”三个步骤。

如果两个 CPU 都先读到 0，最后可能都写回 1，而不是得到 2。

### 2.2 临界区 critical section

临界区是访问共享状态、不能被其他执行流并发破坏的一段操作。

```c
spin_lock(&lock);
list_add(&node->list, &head);
count++;
spin_unlock(&lock);
```

这里需要保持的是链表和计数的一致性，因此两次更新必须放在同一临界区。

锁真正保护的是数据及其不变量：不是“这一行代码需要锁”，而是所有访问这份共享状态的路径必须遵守同一同步协议。

只给写路径加锁、读路径不加锁，通常仍然存在竞态。

### 2.3 原子性不等于顺序性

原子操作保证某次操作不可分割，但不自动表达所有相关内存访问的先后关系。

```c
data = 100;
atomic_set(&ready, 1);
```

如果代码要求另一个 CPU 看到 `ready == 1` 时一定看到新 `data`，还需要正确的发布/获取语义，不能只因为 `ready` 是 atomic 就认为顺序已保证。

### 2.4 数据竞争与生命周期问题不同

锁常用于阻止同时修改；RCU、引用计数等还要解决对象何时可以释放。

```text
reader 找到节点 A
writer 将 A 从链表删除
writer 立即 kfree(A)
reader 继续访问 A → use-after-free
```

“从数据结构中删除”与“内存可以释放”是两个不同事件。

## 3. 先判断执行上下文

### 3.1 进程上下文

系统调用、内核线程、workqueue 等通常运行在进程上下文。

特点：

```text
有明确的 task
在条件允许时可以调度和睡眠
可以使用 mutex、semaphore、rwsem 等睡眠锁
```

但“处于进程上下文”不代表任何时刻都能睡眠。持有 spinlock、关闭抢占或关闭中断后，仍处于原子上下文语义。

### 3.2 硬中断上下文 hardirq

硬中断会打断当前执行流，必须快速完成，不能睡眠。

hardirq 中不能使用 mutex、rwsem、可能阻塞的 I/O 或 `GFP_KERNEL` 等可能睡眠的操作。

常见选择是合适的 spinlock 变体、atomic 或 Per-CPU；慢工作应延后到 threaded IRQ 或 workqueue。

### 3.3 软中断上下文 softirq

softirq 也不能睡眠，而且同一种 softirq 可能在多个 CPU 上并发执行。

如果共享数据同时被进程上下文和 softirq 访问，进程侧常使用 `spin_lock_bh()`，防止持锁期间被本 CPU 的 softirq 打断后再次抢同一把锁。

### 3.4 上下文能力表

| 上下文                | 能否睡眠   | 常用同步方式                        |
| --------------------- | ---------- | ----------------------------------- |
| 普通进程上下文        | 通常可以   | mutex、rwsem，也可短暂使用 spinlock |
| workqueue             | 可以       | mutex、rwsem                        |
| threaded IRQ          | 可以       | mutex，仍需关注设备停用和并发       |
| hardirq               | 不可以     | spinlock、atomic、Per-CPU           |
| softirq/tasklet/timer | 不可以     | spinlock、atomic、Per-CPU           |
| NMI                   | 限制最严格 | 只能使用明确标注 NMI-safe 的机制    |

面试口诀：

```text
先看上下文，再谈锁；
不能睡眠，用自旋或无锁；
可以睡眠，通常优先 mutex。
```

## 4. 一张同步机制选择树

```text
是否真的需要共享？
├── 否：局部变量 / Per-CPU / 分片
└── 是
    ↓
是否只是单变量简单更新？
├── 是：atomic / bit operation / refcount_t
└── 否
    ↓
当前上下文能否睡眠？
├── 否：短临界区用 spinlock；按 hardirq/softirq 选择变体
└── 是：普通互斥优先 mutex；读写并发可考虑 rwsem
    ↓
是否读多写少？
├── 读者可重试、数据是小快照：seqlock
├── 指针型数据且涉及生命周期：RCU
└── 普通共享数据：mutex / spinlock / rwsem
```

还要补充两个判断：

```text
临界区很长或可能阻塞：不能用 spinlock
对象会被删除和释放：仅保证字段原子性不够，还要管理生命周期
```

表格中的几个术语容易混淆：

- `rdlock` 在本文语境中按内核 rwlock 的 `read_lock()` 理解；对应写侧是 `write_lock()`。
- `readwrite_once` 不是标准内核 API，正确名称是 `READ_ONCE()` / `WRITE_ONCE()`。
- `irq`、`irqsave`、`bh` 变体只控制当前 CPU 的 hardirq 或 softirq；跨 CPU 互斥仍由 spinlock 本身完成。
- rwlock 也有 irq、irqsave 和 bh 变体，选择原则与 spinlock 相同：先列出共享数据可能出现的全部上下文。
- `barrier()`、`smp_*()` 屏障和 acquire/release 只处理编译器或 CPU 的顺序与可见性，不提供临界区互斥，也不保护对象生命周期。

## 6. atomic、refcount 与 Per-CPU

### 6.1 atomic 解决什么问题

`atomic_t` 适合对一个整数做简单、不可分割的读改写。

```c
atomic_t pending = ATOMIC_INIT(0);

atomic_inc(&pending);
if (atomic_dec_and_test(&pending))
    wake_up_worker();
```

典型用途是简单计数、状态位和单变量更新。它不能保护复杂数据结构或多个字段的一致性，原子读改写也不等于自动提供所需的内存顺序。

如果要同时更新 `state`、`list` 和 `count`，通常应使用锁建立一个临界区。

### 6.2 引用计数优先使用 refcount_t

引用计数的语义是：对象仍被多少使用者持有，归零后才能销毁。

现代内核代码中，纯对象引用计数通常优先使用 `refcount_t`，因为它比通用 `atomic_t` 更能表达用途，并提供针对溢出、下溢等误用的保护。

引用计数也有代价：每次获取和释放都会更新共享 cacheline；尝试增加引用时必须保证对象仍存在，而且它不会自动解决循环引用。

### 6.3 Per-CPU 的核心思想

Per-CPU 不是让一次共享更新变得更快，而是让各 CPU 更新自己的副本，尽量不共享。

```text
全局计数器：所有 CPU 竞争同一 cacheline
Per-CPU 计数器：CPU0 改副本0，CPU1 改副本1
汇总时：遍历所有 CPU 的副本求和
```

典型场景包括网络统计、分配器局部缓存、每 CPU runqueue 和高频计数。其限制是全局值需要汇总且未必是强一致快照，同时要正确处理任务迁移并遵守 `this_cpu` 等 API 的语义。

一句话对比：

> atomic 是让大家安全地改同一份数据；Per-CPU 是尽量让大家不要改同一份数据。

## 7. spinlock：不能睡眠时的短临界区锁

### 7.1 核心行为

拿不到 spinlock 的执行流会忙等，不主动睡眠让出 CPU。

```c
spin_lock(&lock);
/* 很短、不会睡眠的临界区 */
update_shared_state();
spin_unlock(&lock);
```

它适合 hardirq/softirq 等原子上下文中的短临界区，以及不能拆成简单 atomic 的更新；不适合慢 I/O、可能调度的函数、长时间计算或等待事件。

### 7.2 为什么持有 spinlock 不能睡眠

如果持锁任务睡眠，其他 CPU 可能一直自旋浪费算力；更严重的是，唤醒路径可能也需要这把锁，从而形成死锁。

因此：

```text
spin_lock()
    ↓
临界区内只能调用明确不会睡眠的函数
    ↓
spin_unlock()
```

### 7.3 三个常见变体

#### `spin_lock()`

适用于不需要额外关闭本地 hardirq/softirq 的场景。

它能阻止其他 CPU 同时持有同一把锁，但不会自动解决“本 CPU 持锁时被中断，中断处理函数又来拿同一把锁”的自死锁。

#### `spin_lock_irqsave()`

```c
unsigned long flags;

spin_lock_irqsave(&lock, flags);
/* 与 hardirq 共享的短临界区 */
spin_unlock_irqrestore(&lock, flags);
```

它保存当前 CPU 的中断状态、关闭本地硬中断并获取锁，退出时再恢复原状态。

典型场景：同一数据可能在进程上下文和 hardirq 中访问。

注意：关闭的是当前 CPU 的本地中断，其他 CPU 仍靠 spinlock 互斥。

#### `spin_lock_bh()`

```c
spin_lock_bh(&lock);
/* 与 softirq 共享的短临界区 */
spin_unlock_bh(&lock);
```

它在本 CPU 禁止 softirq/bottom half，再获取锁，常用于进程上下文与网络 softirq 共享数据。

### 7.4 变体选择表

| 共享双方               | 进程侧常见选择                          | 中断侧常见选择 |
| ---------------------- | --------------------------------------- | -------------- |
| 进程 ↔ 进程           | spin_lock 或更常用 mutex                | 不适用         |
| 进程 ↔ hardirq        | spin_lock_irqsave                       | spin_lock      |
| 进程 ↔ softirq        | spin_lock_bh                            | spin_lock      |
| hardirq ↔ hardirq     | 根据中断嵌套和架构约束选择 irqsave 变体 | 同左           |
| CPU ↔ CPU，无中断共享 | spin_lock                               | spin_lock      |

这张表是常见模式，不是脱离代码上下文的机械规则。最终要看所有访问路径以及调用者是否已经关闭中断或 bottom half。

### 7.5 spinlock 隐含内存顺序

锁不仅提供互斥，还带有 acquire/release 类的顺序保证：

```text
成功加锁：后续临界区访问不能跑到加锁之前
解锁：临界区此前的访问要在释放锁前完成到所需程度
```

因此正常受同一把锁保护的数据，通常不需要再手工添加 memory barrier。

## 8. mutex、semaphore 与 rwsem

### 8.1 mutex：普通进程上下文的默认互斥锁

```c
mutex_lock(&lock);
ret = update_device_state(); /* 可以调用可能睡眠的操作 */
mutex_unlock(&lock);
```

竞争时，mutex 可以让当前任务睡眠，之后再被唤醒。

mutex 适合进程上下文中可能较长或可能阻塞的互斥操作。它不能用于 hardirq、softirq 等原子上下文，通常要求加锁者自己解锁，并且仍须遵守统一锁顺序。

### 8.2 spinlock 与 mutex

| 对比       | spinlock             | mutex                        |
| ---------- | -------------------- | ---------------------------- |
| 等待方式   | 忙等                 | 睡眠等待，可能先短暂乐观自旋 |
| 中断上下文 | 可按变体使用         | 不可使用                     |
| 临界区     | 必须短且不能睡眠     | 可以较长、可以睡眠           |
| 主要成本   | 竞争时消耗 CPU       | 调度和上下文切换             |
| 典型场景   | 中断共享数据、短路径 | 配置、设备状态、普通内核对象 |

面试结论：

> 不能睡眠且临界区短，用 spinlock；可以睡眠的普通进程上下文，通常优先 mutex。

### 8.3 semaphore 什么时候出现

semaphore 是计数型睡眠同步机制，计数大于 1 时可允许有限数量的执行流同时进入。

```text
mutex：表达所有权和一对一互斥
semaphore：表达有限资源数量或较老代码中的互斥
```

新代码如果只是互斥，通常优先 mutex；面试不必深挖 semaphore 内部实现。

### 8.4 rwsem：可睡眠的读写锁

```c
down_read(&sem);
read_shared_state();
up_read(&sem);

down_write(&sem);
update_shared_state();
up_write(&sem);
```

语义：

```text
多个 reader 可以并发
writer 必须独占
竞争者可以睡眠
```

适用于进程上下文中读临界区较长、读操作明显多于写操作的场景。

读写锁并非读多就一定更快。管理 reader 状态也有开销，writer 还可能面临较长等待；简单、短小的临界区常常使用 mutex 更清晰。

## 9. rwlock 与 seqlock

### 9.1 rwlock：自旋型读写锁

```c
read_lock(&lock);
read_shared_state();
read_unlock(&lock);

write_lock(&lock);
update_shared_state();
write_unlock(&lock);
```

特点：

```text
多个 reader 可同时进入
writer 独占
等待方式是自旋，不能在临界区睡眠
适合非常短的读写临界区
```

限制：

```text
读者多时 writer 可能等待较久
共享的读锁状态本身也会产生 cacheline 竞争
很多读多写少场景会考虑 RCU 等方案
```

### 9.2 rwlock 与 rwsem

| 对比                   | rwlock           | rwsem              |
| ---------------------- | ---------------- | ------------------ |
| 等待方式               | 自旋             | 睡眠               |
| 是否可在原子上下文使用 | 可按变体使用     | 不可               |
| 临界区                 | 必须短、不能睡眠 | 可以较长、可以睡眠 |
| reader 并发            | 可以             | 可以               |
| writer                 | 独占             | 独占               |

### 9.3 seqlock：读者无锁读取，冲突后重试

seqlock 适合读非常频繁、写很少，而且 reader 能够重新读取的小型数据快照。

读侧思想：

```c
unsigned int seq;

do {
    seq = read_seqbegin(&lock);
    x = state.x;
    y = state.y;
} while (read_seqretry(&lock, seq));
```

写侧思想：

```c
write_seqlock(&lock);
state.x = new_x;
state.y = new_y;
write_sequnlock(&lock);
```

序列号通常表达：

```text
读前记录版本
writer 更新期间版本发生变化
读后版本不同或处于写入状态 → reader 丢弃结果并重试
```

适合：

```text
时间数据
少量相关标量组成的一致快照
读侧允许重试且没有副作用
```

不适合：

```text
reader 不能重复执行
writer 频繁，导致 reader 反复失败
数据包含可能被 writer 删除并释放的指针
```

为什么不能随便保护可释放指针？reader 可能已经取出旧指针，writer 随后释放对象；即使 reader 最后发现序列号变化，解引用旧指针时伤害已经发生。

## 10. READ_ONCE、WRITE_ONCE 与 memory barrier

### 10.1 为什么源码顺序不等于观察顺序

为了优化性能，编译器和 CPU 都可能调整内存访问，只要单线程语义看起来不变。

```c
data = 100;
ready = 1;
```

另一个 CPU：

```c
if (ready)
    use(data);
```

并发代码若没有同步协议，不能仅凭源码顺序断言看到 `ready == 1` 时一定看到新 `data`。

### 10.2 READ_ONCE/WRITE_ONCE 做什么

```c
WRITE_ONCE(flag, 1);

if (READ_ONCE(flag))
    do_something();
```

它们主要约束编译器对这一次访问的合并、拆分、消除或重复读取，让源码明确发生一次指定访问。

它们不保证复合操作原子，不建立多个变量间的完整顺序，也不提供复杂数据的互斥或对象生命周期安全。

因此 `READ_ONCE/WRITE_ONCE` 不是锁，也不是通用的完整内存屏障。

### 10.3 acquire/release 的直觉

常见发布—订阅模式：

```c
/* writer */
initialize_object(obj);
smp_store_release(&global_obj, obj);

/* reader */
obj = smp_load_acquire(&global_obj);
if (obj)
    use_initialized_object(obj);
```

直觉：

```text
release：发布标志或指针之前，先完成前面的初始化
acquire：观察到发布结果之后，再执行后面的对象访问
```

二者配对后，reader 观察到新指针时，也能按协议观察到发布前的初始化结果。

### 10.4 常见屏障概念

```text
barrier()：主要约束编译器，不等同于 SMP 硬件屏障
smp_rmb()：约束读与读的顺序
smp_wmb()：约束写与写的顺序
smp_mb()：更强的通用内存屏障
acquire/release：围绕一次加载或存储建立单向顺序
```

面试不必背每个体系结构映射，但必须知道：屏障解决访问顺序与可见性，不提供临界区互斥。

### 10.5 优先使用已有同步原语

锁、RCU 指针 API、completion、wait queue 等已经包含相应同步语义。

手写无锁协议很容易缺少屏障。普通业务路径应优先选择能直接表达意图的同步原语，而不是随意堆叠 `smp_mb()`。

## 11. RCU：读多写少与对象生命周期

### 11.1 RCU 是什么

RCU 可以理解为 Read-Copy-Update。它让读者用很低的开销访问旧版或新版对象，写者负责发布更新，并延迟回收旧对象。

基本过程：

```text
reader 进入 RCU 读侧临界区并读取对象
writer 创建或准备新状态
writer 让后续 reader 看见新状态
writer 将旧对象从数据结构中移除
等待一个 grace period
确认旧 reader 已离开后，再释放旧对象
```

RCU 的重点不是“reader 永远看到最新值”，而是 reader 看到的对象在临界区内仍然有效。

### 11.2 典型读取模式

```c
rcu_read_lock();
obj = rcu_dereference(global_obj);
if (obj)
    use(obj);
rcu_read_unlock();
```

`rcu_read_lock()`/`unlock()` 标记读侧临界区；`rcu_dereference()` 按 RCU 规则读取被保护指针。

不要把 RCU 指针当普通指针随意读取，否则可能破坏编译器/CPU 顺序和生命周期协议。

### 11.3 典型替换与释放模式

```c
old = rcu_dereference_protected(global_obj,
                                lockdep_is_held(&update_lock));
rcu_assign_pointer(global_obj, new);

synchronize_rcu();
kfree(old);
```

也可以异步回收：

```c
call_rcu(&old->rcu, free_old_object);
```

常见便捷方式：

```c
kfree_rcu(old, rcu);
```

三者区别：

```text
synchronize_rcu()：调用者同步等待 grace period，之后再继续
call_rcu()：注册回调，grace period 后异步执行
kfree_rcu()：grace period 后释放包含 rcu_head 的对象
```

### 11.4 grace period 是什么

grace period 表示：在更新发生前已经进入读侧临界区的那些旧 reader，都已经离开。

它不意味着：

```text
所有 CPU 都停止运行
所有 reader 都看到了最新版本
整个系统没有新的 RCU reader
```

新的 reader 可以继续进入，但它们应通过已发布的结构访问新状态。

### 11.5 RCU 解决什么，不解决什么

RCU 擅长：

```text
读多写少的链表、哈希表、查找表
指针替换
删除对象后的延迟回收
极低开销的短读侧访问
```

RCU 不自动保证：

```text
多个 writer 之间互斥
对象内部所有字段永远不变
reader 一定看到最新数据
任意 RCU 读侧都能调用阻塞函数
```

writer 常常还要用 mutex 或 spinlock 彼此串行化。

普通面试可以回答：经典 RCU 读侧不要调用可能阻塞的 API；确需可睡眠的读侧时，应使用适合该场景的机制，例如 SRCU，并遵守对应 API 规则。不要依赖“某个内核配置下 reader 是否可被抢占”来推导可以随意睡眠。

### 11.6 RCU 与引用计数

| 对比     | RCU                          | 引用计数                         |
| -------- | ---------------------------- | -------------------------------- |
| 读侧成本 | 通常很低                     | 每次持有都要增减计数             |
| 释放条件 | 旧 reader 经过 grace period  | 引用计数归零                     |
| 适合     | 短时间查找和访问             | 对象可能被长期持有               |
| 主要问题 | 更新和回收协议复杂、释放延迟 | 共享计数竞争、获取引用本身需安全 |

二者可以组合使用：RCU 负责安全查找到对象，成功增加引用后，引用计数负责让对象脱离 RCU 临界区后仍然存活。

## 12. 四组高频对比

### 12.1 atomic 与 spinlock

| 对比         | atomic         | spinlock            |
| ------------ | -------------- | ------------------- |
| 保护范围     | 单变量简单操作 | 任意短临界区        |
| 多字段一致性 | 不适合         | 适合                |
| 是否睡眠     | 不睡眠         | 不睡眠              |
| 典型用途     | counter、flag  | list、queue、状态机 |

口诀：

```text
一个变量一次改，考虑 atomic；
多个状态一起改，建立临界区。
```

### 12.2 spinlock 与 mutex

```text
spinlock：等待时占着 CPU 转，适合不能睡眠的短临界区
mutex：竞争时可以睡，适合普通进程上下文和较长临界区
```

判断的第一标准是上下文能否睡眠，而不是武断地用某个固定时间阈值区分长短。

### 12.3 rwlock、rwsem 与 seqlock

| 机制    | reader             | writer       | 能否睡眠     | 适合场景               |
| ------- | ------------------ | ------------ | ------------ | ---------------------- |
| rwlock  | 加读锁，可并发     | 加写锁，独占 | 不能         | 很短的读写临界区       |
| rwsem   | 加读锁，可并发     | 加写锁，独占 | 可以         | 进程上下文较长读写操作 |
| seqlock | 无锁读取，冲突重试 | 串行更新     | 读侧不应阻塞 | 小型一致快照、写少     |

### 12.4 seqlock 与 RCU

| 对比            | seqlock        | RCU                      |
| --------------- | -------------- | ------------------------ |
| reader 冲突行为 | 重试           | 通常继续读取某个有效版本 |
| 主要目标        | 得到一致快照   | 低成本读取和安全生命周期 |
| 指针释放        | 不擅长         | 擅长延迟回收             |
| 典型数据        | 时间、少量标量 | 链表、哈希表、配置对象   |

口诀：

```text
读者能重试、读小快照，用 seqlock；
读多写少、对象可延迟释放，用 RCU。
```

## 13. 三个必须会讲的代码场景

### 13.1 普通进程上下文保护设备状态

```c
int set_mode(struct my_device *dev, int mode)
{
    int ret;

    mutex_lock(&dev->lock);
    if (!dev->enabled) {
        ret = -ENODEV;
        goto out;
    }

    ret = program_hardware(dev, mode); /* 可能睡眠 */
    if (!ret)
        dev->mode = mode;
out:
    mutex_unlock(&dev->lock);
    return ret;
}
```

为什么用 mutex：

```text
调用路径是进程上下文
硬件操作可能睡眠
enabled 和 mode 需要一致地检查、更新
```

### 13.2 进程与 hardirq 共享队列

```c
void process_done_items(struct my_device *dev)
{
    unsigned long flags;

    spin_lock_irqsave(&dev->lock, flags);
    detach_done_items(dev);
    spin_unlock_irqrestore(&dev->lock, flags);

    handle_detached_items(); /* 慢工作放到锁外 */
}

irqreturn_t my_irq(int irq, void *data)
{
    struct my_device *dev = data;

    spin_lock(&dev->lock);
    record_completion(dev);
    spin_unlock(&dev->lock);
    return IRQ_HANDLED;
}
```

关键点：进程侧 irqsave 防止本 CPU 的中断自死锁，其他 CPU 由 spinlock 互斥；中断处理和持锁区必须短，慢工作放在锁外。

### 13.3 RCU 删除对象

```c
/* reader */
rcu_read_lock();
entry = find_entry_rcu(key);
if (entry)
    consume(entry);
rcu_read_unlock();

/* writer，writer 之间另有锁 */
spin_lock(&update_lock);
entry = remove_entry_rcu(key);
spin_unlock(&update_lock);

if (entry)
    kfree_rcu(entry, rcu);
```

关键点：更新锁串行化 writer，RCU 保护 reader 访问期间的对象生命周期；从表中删除后不能立即 `kfree()`。

## 14. 死锁与常见同步错误

### 14.1 ABBA 锁顺序死锁

```text
CPU0：拿到锁 A → 等锁 B
CPU1：拿到锁 B → 等锁 A
```

解决原则：全系统或子系统内建立固定锁顺序，例如永远先 A 后 B。

如果确实需要嵌套锁，要在设计和注释中明确顺序，不能由调用路径临时决定。

### 14.2 中断自死锁

```text
进程上下文拿到 lock
本 CPU hardirq 到来
handler 也尝试拿 lock
handler 一直等，但被打断的进程无法运行和解锁
```

若同一锁确实在进程与 hardirq 间共享，进程侧通常使用 `spin_lock_irqsave()`。

### 14.3 持有 spinlock 时睡眠

典型错误：

```c
spin_lock(&lock);
mutex_lock(&other_lock); /* 可能睡眠 */
spin_unlock(&lock);
```

以及持锁后调用不知道是否会睡眠的函数。

解决办法：缩短临界区、调整数据流，或在允许睡眠的上下文中改用合适的睡眠锁。

### 14.4 重复加非递归锁

Linux 的 spinlock 和 mutex 通常不是递归锁。同一执行流重复获取同一把锁会把自己锁死。

常见原因是调用层级不清：外层已经持锁，又调用一个内部也会拿锁的函数。常用做法是拆分 `_locked` 或要求调用者持锁的内部辅助函数，并用 lockdep 断言表达前置条件。

### 14.5 锁粒度过大或过小

```text
过大：竞争严重、延迟高、持锁路径难审查
过小：状态无法整体保持一致、锁数量和顺序复杂
```

锁粒度应围绕数据不变量决定，而不是简单追求“锁越细越快”。

### 14.6 忘记所有访问路径

下面不是安全发布：

```text
writer 加锁修改
reader 不加锁直接读取
```

除非 reader 明确使用与 writer 配套的无锁协议，例如 RCU、seqlock 或 release/acquire，否则这是数据竞争。

### 14.7 lockdep 能做什么

lockdep 是内核锁依赖检查器，能够根据运行时观察到的锁获取关系发现潜在的锁顺序反转、递归加锁和部分上下文误用。

它很有价值，但不是完整证明：未运行到的路径不会被观察到，数据竞争和生命周期错误也不一定都属于 lockdep 的检测范围。

## 15. futex 只需掌握一句主线

futex 是用户态同步原语与内核等待队列之间的桥梁：无竞争时通过用户态原子指令完成加锁或解锁；有竞争时才进入内核等待或唤醒。

pthread mutex 常以类似思想实现快路径和慢路径。

面试不要说“futex 就是一把内核 mutex”。更准确的说法是：futex 根据一个用户态地址的值提供等待/唤醒能力，具体锁语义由用户态库与内核协议共同组成。

## 16. 高频面试问答

### 16.1 为什么 Linux 内核需要同步机制？

因为多个 CPU、进程、内核线程和中断可能并发访问共享数据；没有同步会出现丢失更新、数据结构损坏、乱序可见性和 use-after-free。

### 16.2 什么是临界区？

临界区是访问共享状态并需要保持某个不变量的一段操作。锁保护的是共享数据和访问协议，不只是某几行代码。

### 16.3 atomic 和 spinlock 有什么区别？

atomic 适合单变量的简单原子读改写；spinlock 可以保护多个字段、链表或状态转换组成的短临界区。

### 16.4 atomic 操作是否天然等于完整 memory barrier？

不能一概而论。原子性和内存顺序是不同概念，具体 API 具有何种 ordering 要查对应语义；需要发布—获取关系时应使用合适的 acquire/release 或已有同步原语。

### 16.5 Per-CPU 为什么快？

它让每个 CPU 主要更新自己的副本，减少共享 cacheline 争用。代价是全局读取需要汇总，而且当前任务迁移和访问 API 必须处理正确。

### 16.6 spinlock 和 mutex 最大区别是什么？

spinlock 竞争时忙等，临界区不能睡眠；mutex 竞争时可以让任务睡眠，只能用于允许睡眠的上下文。

### 16.7 为什么中断上下文不能使用 mutex？

mutex 竞争时可能睡眠和触发调度，而 hardirq/softirq 不是允许阻塞的普通进程执行环境。

### 16.8 为什么持有 spinlock 时不能睡眠？

其他 CPU 会持续自旋，且唤醒路径可能依赖同一把锁，造成死锁。持有 spinlock 时必须保持原子上下文语义并尽快退出。

### 16.9 spin_lock() 和 spin_lock_irqsave() 怎么选？

如果同一数据会在进程上下文和本 CPU hardirq 中访问，进程侧通常用 irqsave 变体，避免持锁时被中断后自死锁。若没有 hardirq 共享，则不应机械地关闭中断。

### 16.10 spin_lock_bh() 有什么作用？

它在当前 CPU 禁止 bottom half/softirq 后加锁，常用于进程上下文与 softirq 共享数据，防止本 CPU 的 softirq 在持锁期间再次获取同一把锁。

### 16.11 关闭本地中断能替代 spinlock 吗？

不能。在 SMP 系统中，关闭本地中断只影响当前 CPU，其他 CPU 仍可并发访问；跨 CPU 互斥仍需要锁或其他同步协议。

### 16.12 rwlock 与 rwsem 有什么区别？

二者都允许 reader 并发、writer 独占；rwlock 是自旋型，临界区不能睡眠；rwsem 是睡眠型，用于进程上下文和较长操作。

### 16.13 读多写少是否一定要使用读写锁？

不一定。读锁状态也有竞争和管理成本，writer 可能等待更久。要结合临界区长度、竞争程度和数据类型比较 mutex、rwsem、seqlock、RCU。

### 16.14 seqlock 为什么读得快？

reader 不获取传统读锁，只读取版本号和数据；若读期间 writer 修改过，再丢弃结果重试。因此 reader 不阻塞 writer。

### 16.15 seqlock 为什么不适合保护会释放的指针？

reader 可能取出旧指针后，writer 将对象释放；reader 即使随后发现版本变化，也可能已经解引用了失效内存。

### 16.16 RCU 是什么？

RCU 是面向读多写少场景的同步机制。reader 低成本访问，writer 发布新状态并把旧对象的释放推迟到 grace period 之后。

### 16.17 grace period 是什么？

它表示更新前已经进入的旧 RCU reader 都已离开读侧临界区，因此旧对象不再被这些 reader 使用，可以进入回收阶段。

### 16.18 synchronize_rcu() 与 call_rcu() 有什么区别？

前者同步等待 grace period 返回；后者登记回调，在 grace period 后异步执行，调用者无需原地等待。

### 16.19 RCU 是否保护对象字段不被并发修改？

不会自动保护。RCU主要保护访问路径和对象生命周期；多个 writer 或可变字段通常还要使用锁、原子操作或不可变对象替换等协议。

### 16.20 RCU reader 能否睡眠？

不能笼统回答“能”。普通代码应遵守所用 RCU flavor 的规则，经典面试场景下不要在普通 RCU 读侧调用阻塞 API；需要睡眠时考虑 SRCU 等适当机制。

### 16.21 READ_ONCE/WRITE_ONCE 是锁吗？

不是。它们主要约束编译器对单次访问的优化，不提供临界区互斥，也不自动建立多个变量间的完整顺序。

### 16.22 memory barrier 和锁有什么区别？

屏障约束内存访问的顺序与可见性，不阻止其他执行流进入代码；锁提供互斥，并通常自带相应的 acquire/release 顺序语义。

### 16.23 如何避免 ABBA 死锁？

为多把锁规定并遵守全局一致的获取顺序，避免持锁等待不受控资源，并使用 lockdep 检查运行到的锁依赖关系。

### 16.24 RCU 与引用计数如何选择？

短时间查找、读多写少可用 RCU；对象需要跨越查找临界区被长期持有时常用引用计数。实际代码可以用 RCU 安全查找，再增加引用延长生命周期。

### 16.25 futex 为什么快？

无竞争时常通过用户态原子操作完成，不必系统调用；发生竞争时才进入内核等待和唤醒。

## 17. 面试中的典型追问链

### 17.1 从“spinlock 和 mutex”继续追问

```text
Q：中断上下文该用哪个？
A：不能用 mutex，短临界区考虑 spinlock 或原子操作。

Q：进程和 hardirq 共享数据呢？
A：进程侧通常用 spin_lock_irqsave，避免本 CPU 中断自死锁。

Q：irqsave 已经关中断，为什么还需要锁？
A：它只关当前 CPU 的本地中断，其他 CPU 仍能并发访问。

Q：临界区要做慢 I/O 呢？
A：不能持有 spinlock，应重构为锁内摘取状态、锁外处理，或转到可睡眠上下文。
```

### 17.2 从“RCU 读得快”继续追问

```text
Q：writer 删除节点后能立即 kfree 吗？
A：不能，旧 reader 可能还持有指针。

Q：什么时候能释放？
A：经过 grace period 后，用 synchronize_rcu、call_rcu 或 kfree_rcu。

Q：多个 writer 还需要锁吗？
A：通常需要，RCU 不自动串行化 writer。

Q：reader 一定看到最新对象吗？
A：不保证，重点是读到的版本在协议允许范围内且生命周期安全。
```

### 17.3 从“内存屏障”继续追问

```text
Q：READ_ONCE 是完整屏障吗？
A：不是，它主要保证一次明确的编译器可见访问。

Q：如何发布初始化完成的对象？
A：使用配对的 release/acquire，或更高层的锁、RCU 指针 API。

Q：锁内还要手工 smp_mb 吗？
A：普通锁保护协议通常不需要，锁已经提供相应顺序；特殊无锁算法才按严格证明添加。
```

## 18. 容易说错的十句话

### 错误 1：用了 atomic_t，相关代码就线程安全了

正确：atomic 只保证特定单变量操作；多个字段和对象生命周期仍需其他同步。

### 错误 2：volatile 可以代替锁和 memory barrier

正确：内核通常用明确的 `READ_ONCE/WRITE_ONCE`、屏障和同步原语；C `volatile` 不提供通用互斥或跨 CPU 顺序保证。

### 错误 3：spinlock 比 mutex 快，所以能用 spinlock 就不用 mutex

正确：选择首先取决于上下文和临界区是否可能睡眠；竞争和临界区较长时自旋可能更差。

### 错误 4：关闭中断就能解决所有并发

正确：关闭本地中断不能阻止其他 CPU，也不能替代完整的共享数据协议。

### 错误 5：进程上下文一定可以睡眠

正确：持有 spinlock、关闭抢占或处于其他原子区域时，即使有 `current` 也不能睡眠。

### 错误 6：读多写少一定用 rwlock

正确：还要看临界区长度、reader 状态竞争、writer 延迟和数据类型，RCU、seqlock、rwsem 或 mutex 可能更合适。

### 错误 7：RCU 就是没有锁

正确：RCU 是完整的读取、发布和延迟回收协议；writer 之间通常仍需锁。

### 错误 8：从 RCU 链表删除后就能释放节点

正确：删除只让新 reader 找不到它，旧 reader 仍可能使用，必须等待 grace period。

### 错误 9：加一个 smp_mb() 就能修复所有并发问题

正确：屏障不提供互斥或生命周期管理；必须先明确并发协议和配对关系。

### 错误 10：lockdep 没报警就证明没有同步问题

正确：lockdep 主要检查执行到的锁依赖与部分锁用法，不能证明所有路径、数据竞争和生命周期都正确。

## 19. 一页背诵级总结

### 19.1 四类问题

```text
原子性：操作不能被并发拆开
可见性：一个 CPU 的写何时被另一个 CPU 观察到
顺序性：访问不能按错误顺序被观察
生命周期：对象在 reader 使用期间不能释放
```

### 19.2 上下文

```text
hardirq/softirq：不能睡眠
普通进程上下文：条件允许时可以睡眠
持有 spinlock：不能睡眠
workqueue/threaded IRQ：运行在线程上下文，通常可以睡眠
```

### 19.3 核心机制

```text
atomic：单变量简单原子操作
refcount_t：对象引用计数
Per-CPU：减少共享和 cacheline 竞争
spinlock：不能睡眠的短临界区
mutex：可睡眠进程上下文的普通互斥
rwlock：自旋型读写锁
rwsem：睡眠型读写锁
seqlock：reader 无锁读取，冲突重试
RCU：低成本读取，grace period 后回收旧对象
futex：无竞争用户态完成，有竞争进入内核等待
```

### 19.4 spinlock 变体

```text
spin_lock：普通跨 CPU 互斥
spin_lock_irqsave：与 hardirq 共享，保存并关闭本地中断
spin_lock_bh：与 softirq 共享，关闭本地 bottom half
```

### 19.5 内存顺序

```text
READ_ONCE/WRITE_ONCE：约束一次编译器访问，不是锁
release：发布前面的初始化
acquire：观察发布后再访问后续数据
memory barrier：管顺序与可见性，不管互斥
锁：既互斥，也带相应 acquire/release 语义
```

### 19.6 选型口诀

```text
能不共享，优先 Per-CPU 或分片；
单变量简单改，用 atomic；
不能睡眠、临界区短，用 spinlock；
可以睡眠，普通互斥用 mutex；
可睡眠且读多写少，考虑 rwsem；
读者能重试的小快照，用 seqlock；
读多写少且涉及指针生命周期，用 RCU；
涉及对象长期持有，考虑引用计数；
发布与观察跨 CPU，考虑 acquire/release；
多把锁统一顺序，避免 ABBA 死锁。
```

### 19.7 最终面试回答模板

拿到一个同步问题，按以下顺序回答：

```text
1. 共享数据和不变量是什么？
2. 谁会访问：进程、hardirq、softirq、多个 CPU？
3. 当前路径能否睡眠，临界区是否可能阻塞？
4. 是单变量更新、普通互斥，还是读多写少？
5. 是否涉及对象删除和释放？
6. 据此选择机制，并说明它的限制和锁顺序。
```

只要能沿这六步分析，面试官继续换场景，也不容易把锁选乱。

# Linux 内核常用维测命令：从现象到证据的实战手册

> 目标：遇到 CPU 高、调度延迟、中断集中、内存压力、I/O 卡顿、网络丢包、
> hung task 或内核报错时，能够知道先看哪个入口、关键字段代表什么，以及下一步如何缩小范围。
>
> 本文以稳定、低成本的系统接口为主，只介绍 tracing 的最小使用方式。
> 复杂的 ftrace、tracepoint、kprobe、eBPF 和离线分析见
> [《11. Linux 内核 - 追踪.md》](<./11.%20Linux%20内核%20-%20追踪.md>)。

---

## 0. 阅读约定、安全等级与实测环境

### 0.1 四类操作标签

本文为命令和接口标注以下风险等级：

| 标签             | 含义                                         | 使用原则                         |
| ---------------- | -------------------------------------------- | -------------------------------- |
| `[只读]`       | 只读取已有统计或状态                         | 通常适合首先使用                 |
| `[采集有开销]` | 不主动改变业务逻辑，但会消耗 CPU、内存或 I/O | 限时、限 CPU、限 PID、限事件     |
| `[修改状态]`   | 写 sysfs、procfs、debugfs、tracefs 或 sysctl | 保存原值，确认影响范围，准备恢复 |
| `[高风险]`     | 可能触发崩溃、重启、丢数据或严重扰动         | 仅在隔离实验机按明确方案使用     |

“文件看起来可写”不代表可以随便写。`/proc`、`/sys`、debugfs 和 tracefs 中的文件，
往往直接连接内核变量或操作函数，写入后可能立即改变系统行为。

### 0.2 本文使用的证据层次

排障时应先区分自己拿到的是什么证据：

| 证据类型   | 例子                                                | 能回答什么                             | 不能单独回答什么            |
| ---------- | --------------------------------------------------- | -------------------------------------- | --------------------------- |
| 累计计数   | `/proc/interrupts`、`/proc/softirqs`            | 从启动以来发生了多少次、分布在哪些 CPU | 当前速率、每次处理耗时      |
| 时间占比   | `mpstat` 的 `%irq/%soft`、`top` 的 CPU 百分比 | 一段时间内 CPU 花在哪里                | 是哪个具体 IRQ 或函数造成的 |
| 当前快照   | `ps`、`/proc/<pid>/stack`、`sched/debug`      | 此刻谁在运行、等待或排队               | 过去的完整因果链            |
| 事件时间线 | tracepoint、`trace-cmd`                           | 事件顺序、时间戳、CPU、PID、延迟       | 未启用之前发生的历史事件    |
| 采样画像   | `perf top/record`                                 | CPU 热点和调用栈分布                   | 每一次事件的精确时间线      |
| 日志/转储  | `dmesg`、journal、vmcore                          | 报错、告警和崩溃现场                   | 未被记录的运行时细节        |

必须避免三个常见误判：

1. 累计次数多，不等于当前仍然很忙。
2. 次数多，不等于 CPU 时间一定高；一次回调可能很短。
3. 时间点接近，只能说明相关，需要更多证据才能证明因果。

### 0.3 虚拟机实测基线

本文的路径与工具经过一台测试虚拟机只读核验：

```text
发行版：openEuler 24.03 (LTS-SP3)
架构：aarch64
CPU：4 个
内核：Linux 7.2.0-rc6-qzc，SMP PREEMPT
```

实际能力：

| 项目          | 实测结果                                                           | 影响                                         |
| ------------- | ------------------------------------------------------------------ | -------------------------------------------- |
| procfs        | 挂载在`/proc`                                                    | 常用统计可直接读取                           |
| sysfs         | 挂载在`/sys`                                                     | CPU、设备、IRQ 元数据可读取                  |
| debugfs       | 挂载在`/sys/kernel/debug`                                        | 存在调度、碎片、时钟、电源等调试接口         |
| tracefs       | 同时挂载在`/sys/kernel/tracing` 和 `/sys/kernel/debug/tracing` | 本文统一优先使用前者                         |
| tracepoint    | sched、irq、ipi、timer、workqueue、block、vmscan 等事件存在        | 可以进行事件级采集                           |
| ftrace tracer | `available_tracers` 仅显示 `nop`                               | 不能假设 function tracer 一定可用            |
| sysstat       | `mpstat`、`pidstat`、`iostat`、`sar` 已安装                | 可以直接进行周期统计                         |
| perf          | 工具存在，版本为 6.6 系列                                          | 与 7.2-rc6 内核不完全同版本，能力以实测为准  |
| trace-cmd     | 已安装，版本 3.2.0                                                 | 可作为 tracefs 用户态前端                    |
| bpftrace      | 已安装，版本 0.19.1                                                | 本文不展开语法，复杂用法见追踪专篇           |
| cgroup        | cgroup v1                                                          | 与 cgroup v2 文件名不同                      |
| PSI           | 没有`/proc/pressure`                                             | 不能依赖 PSI；其他机器应先检查接口是否存在   |
| irqbalance    | 服务不存在                                                         | IRQ 分布主要由内核、驱动或手工 affinity 决定 |

版本相关接口必须先发现、后使用：

```bash
# [只读] 先确认系统、挂载点和工具。
uname -a
cat /etc/os-release
findmnt -t proc,sysfs,debugfs,tracefs
command -v mpstat perf trace-cmd bpftrace bpftool
```

## 1. Linux 根目录：每个目录负责什么

### 1.1 根目录总表

| 目录       | 核心目的                       | 典型内容                             | 维测时常见用途                     |
| ---------- | ------------------------------ | ------------------------------------ | ---------------------------------- |
| `/boot`  | 启动所需文件                   | 内核镜像、initramfs、bootloader 配置 | 核对启动内核、initramfs、启动参数  |
| `/dev`   | 设备节点和内核对象入口         | 块设备、字符设备、`null`、`kmsg` | 确认设备节点、主次设备号、设备权限 |
| `/etc`   | 主机级静态配置                 | systemd、网络、服务、sysctl 配置     | 判断配置来源、服务启动参数         |
| `/home`  | 普通用户主目录                 | 用户文件和配置                       | 查看用户空间占用，不是内核接口     |
| `/media` | 可移动介质自动挂载点           | U 盘、光盘                           | 检查桌面环境自动挂载               |
| `/mnt`   | 管理员临时挂载点               | 临时磁盘、NFS                        | 临时挂载和文件系统排障             |
| `/opt`   | 附加或第三方软件               | 厂商独立目录                         | 查第三方代理、驱动配套工具         |
| `/proc`  | 进程和内核运行状态的 procfs    | PID 目录、CPU、内存、中断统计        | 内核维测第一入口之一               |
| `/root`  | root 用户主目录                | root 的脚本和配置                    | 不等于文件系统根目录`/`          |
| `/run`   | 本次启动的易失运行时状态       | PID 文件、socket、lock、systemd 状态 | 检查守护进程 socket 和运行状态     |
| `/srv`   | 服务对外提供的数据             | Web、FTP 等服务数据                  | 使用情况取决于发行版和部署规范     |
| `/sys`   | 内核对象、设备和属性的 sysfs   | CPU、NUMA、设备、驱动、电源          | 查看对象属性，部分文件可调参       |
| `/tmp`   | 临时文件                       | 短生命周期中间文件                   | 通常带 sticky bit；可能是 tmpfs    |
| `/usr`   | 大部分用户态程序和只读共享数据 | bin、sbin、lib、share、include       | 查命令、库、文档、工具版本         |
| `/var`   | 持续变化的数据                 | log、lib、cache、spool、tmp          | 日志、数据库、包缓存、崩溃文件     |

### 1.2 `/bin`、`/sbin`、`/lib*` 与 merged-usr

现代发行版常采用 merged-usr：

```text
/bin   -> /usr/bin
/sbin  -> /usr/sbin
/lib   -> /usr/lib
/lib64 -> /usr/lib64
```

历史语义是：

| 路径          | 历史定位                       |
| ------------- | ------------------------------ |
| `/bin`      | 启动和救援也需要的基本用户命令 |
| `/sbin`     | 系统管理命令                   |
| `/lib*`     | 基本命令所需共享库和动态加载器 |
| `/usr/bin`  | 普通用户命令                   |
| `/usr/sbin` | 非基本系统管理命令             |

merged-usr 后，物理文件主要位于 `/usr`，旧路径保留为兼容链接。
查命令真实位置可使用：

```bash
# [只读]
command -v mpstat
readlink -f /bin
readlink -f /sbin
```

### 1.3 `/proc`、`/sys`、`/dev`、`/run` 不是普通静态目录

这些路径更多是运行时视图：

```text
内核状态与对象
    ├── procfs   → /proc
    ├── sysfs    → /sys
    ├── devtmpfs → /dev
    ├── debugfs  → /sys/kernel/debug
    └── tracefs  → /sys/kernel/tracing

用户态运行时状态
    └── tmpfs    → /run（多数发行版）
```

- `/proc` 中很多文件由读取回调现场生成，没有普通磁盘文件的数据块。
- `/sys` 将设备、驱动、CPU、NUMA node 等内核对象表示成目录和属性文件。
- `/dev` 的设备节点通过主设备号、次设备号连接驱动，不保存设备内容本身。
- `/run` 通常位于内存中，重启后重新创建。
- debugfs 用于调试，接口不承诺稳定 ABI。
- tracefs 是 tracing 框架的控制面和数据面。

确认文件系统类型：

```bash
# [只读]
findmnt /proc
findmnt /sys
findmnt /sys/kernel/debug
findmnt /sys/kernel/tracing
findmnt /run
```

### 1.4 `/var` 中最值得关注的路径

| 路径           | 用途                                       |
| -------------- | ------------------------------------------ |
| `/var/log`   | 文本日志或日志服务持久化数据               |
| `/var/lib`   | 服务的持久状态，例如包管理和 systemd 数据  |
| `/var/cache` | 可重建缓存                                 |
| `/var/spool` | 队列数据，例如邮件、打印、cron             |
| `/var/tmp`   | 比`/tmp` 更适合跨重启保留的临时文件      |
| `/var/crash` | 部分发行版存放 vmcore 或用户态 core 的位置 |

systemd-journald 可能把日志保存在 `/run/log/journal` 或 `/var/log/journal`，
因此“`/var/log` 没有目标文本文件”不等于没有日志，应使用 `journalctl` 查询。

### 1.5 当前虚拟机中的特殊项

- `/afs` 当前不是挂载点，只是一个空的预留目录；AFS 环境中它也可能作为 Andrew File System 的挂载点。
- `/grub.cfg` 是该虚拟机镜像根目录中的普通文件，不属于通用 Linux 根目录规范。
- 判断目录语义不能只看名字，应结合 `findmnt`、`stat`、`readlink`：

```bash
# [只读]
findmnt /afs
stat /afs /grub.cfg
readlink -f /bin /lib64
```

## 2. 总体维测地图：从现象选择第一入口

### 2.1 高频故障首选表

| 现象               | 第一入口`[只读]`                               | 重点字段                              | 下一步                                  | 风险     |
| ------------------ | ------------------------------------------------ | ------------------------------------- | --------------------------------------- | -------- |
| 单核或全机 CPU 高  | `top`、`mpstat -P ALL 1`                     | `%usr/%sys/%irq/%soft`、每 CPU 分布 | `pidstat`、`perf top`               | 低到中   |
| load 高但 CPU 不高 | `uptime`、`vmstat 1`、`ps`                 | load、`r/b`、D 状态                 | 进程 stack、I/O、锁等待                 | 低       |
| 调度延迟           | `pidstat -w`、`/proc/schedstat`              | cswch、nvcswch、等待时间              | sched tracepoint、`perf sched`        | 中       |
| hardirq 集中       | `/proc/interrupts`、`mpstat`                 | IRQ 增速、CPU 列、`%irq`            | `/proc/irq/N`、irq tracepoint         | 低到中   |
| softirq 高         | `/proc/softirqs`、`mpstat`                   | 类型增速、`%soft`、CPU 分布         | `ksoftirqd`、NAPI、softirq tracepoint | 低到中   |
| 内存不足           | `free -h`、`vmstat 1`、`/proc/meminfo`     | available、si/so、reclaim、swap       | slab、smaps、vmscan event               | 低到中   |
| 高阶分配失败/碎片  | `buddyinfo`、`pagetypeinfo`、debugfs extfrag | 高 order 空闲块、迁移类型             | compaction tracepoint                   | 中       |
| 磁盘延迟           | `iostat -xz 1`、`pidstat -d 1`               | await、aqu-sz、util、进程吞吐         | block tracepoint、设备日志              | 低到中   |
| 网络丢包           | `ip -s link`、`ethtool -S`、`ss -s`        | drop/error、队列、重传                | IRQ、NET_RX、NAPI tracepoint            | 低到中   |
| 锁竞争             | `perf lock`、任务 stack                        | wait、contention、锁路径              | lock tracepoint、专门 tracing           | 中       |
| hung task          | `dmesg -T`、任务 stack、wchan                  | D 状态、阻塞函数、持锁者              | SysRq task dump、vmcore                 | 中到高   |
| RCU stall          | `dmesg`、`/proc/softirqs`                    | stall CPU、RCU 增速、IRQ 状态         | sched/irq/RCU 事件                      | 中       |
| 驱动 probe 失败    | `dmesg`、`devices_deferred`                  | errno、deferred reason                | sysfs driver binding、dynamic debug     | 低到中   |
| suspend 失败       | `journalctl -k`、`suspend_stats`             | failed step、device、errno            | power tracepoint、wakeup_sources        | 中       |
| panic/oops         | console、pstore、kdump/vmcore                    | RIP/PC、call trace、CPU、task         | crash/drgn                              | 事后分析 |

### 2.2 推荐的排障顺序

不要一上来就打开所有 tracepoint。通常按以下顺序成本最低：

```text
1. 确认时间、主机、内核、现象和复现窗口
2. 看全局概况：uptime、top、vmstat、mpstat、free、iostat
3. 找到子系统和异常 CPU/进程/设备
4. 连续采样累计接口，计算增量而不是只看绝对值
5. 查看对象级状态：/proc/<pid>、/proc/irq/N、sysfs
6. 再开启限时 tracepoint、perf 或其他采集
7. 保存原始证据、命令、时间戳和版本信息
```

基础证据包：

```bash
# [只读] 建议逐条执行，并记录时间戳。
date -Ins
uname -a
uptime
cat /proc/cmdline
top -b -n 1
vmstat 1 5
mpstat -P ALL 1 5
free -h
iostat -xz 1 5
```

### 2.3 `watch` 的正确用法

`watch` 周期执行一条命令，正确参数是 `-n`：

```bash
# [只读] 每 1 秒刷新。
watch -n 1 cat /proc/interrupts

# 每 0.5 秒刷新，并高亮变化。
watch -d -n 0.5 cat /proc/softirqs

# 显示命令执行失败和退出状态。
watch -e -n 1 'your-command'
```

注意：

- `watch n 1` 缺少连字符，是错误写法。
- `watch` 展示的是每次命令的完整结果，不会自动计算计数差值。
- 很短的周期会增加系统扰动，生产机通常从 1～5 秒开始。
- 通过 shell 管道或重定向时，应把完整命令放在引号中。

### 2.4 连续采样为什么比单次读取更重要

假设 `/proc/softirqs` 中 CPU2 的 `NET_RX` 为 2,785,078：

```text
只能证明：从统计起点到现在，CPU2 累计处理过很多 NET_RX。
不能证明：现在仍然每秒增长很快。
```

应计算两个时间点的差：

```text
速率 ≈（第二次计数 - 第一次计数）/ 采样间隔
```

随后用 `mpstat %soft` 判断它是否真正消耗了显著 CPU 时间。

## 3. `/proc`：进程与内核运行状态

### 3.1 `/proc` 的两类内容

```text
/proc
├── 1234/              某个进程的视图
├── 1234/task/1235/    某个线程的视图
├── interrupts         全局硬中断统计
├── softirqs           全局软中断统计
├── meminfo            全局内存概况
└── sys/               sysctl 参数文件接口
```

数字目录以 PID/TID 为键，任务退出后目录消失。读取多个文件时要接受进程可能并发退出。

### 3.2 `/proc/stat`

`/proc/stat` 汇总 CPU 时间和若干系统累计计数：

```bash
# [只读]
cat /proc/stat
```

CPU 行字段顺序通常为：

```text
cpu  user nice system idle iowait irq softirq steal guest guest_nice
```

| 字段                 | 含义                                                           |
| -------------------- | -------------------------------------------------------------- |
| `user`             | 普通用户态时间                                                 |
| `nice`             | nice 值非默认的用户态时间                                      |
| `system`           | 普通内核态时间                                                 |
| `idle`             | 空闲时间                                                       |
| `iowait`           | CPU 空闲且系统存在待完成 I/O 的时间，不是进程精确 I/O 等待时间 |
| `irq`              | hardirq 时间                                                   |
| `softirq`          | softirq 时间                                                   |
| `steal`            | 虚拟机被宿主机拿走的可运行时间                                 |
| `guest/guest_nice` | 运行虚拟 CPU 的时间，解释总量时注意与 user 的核算关系          |

其他高频行：

| 行                | 含义                         |
| ----------------- | ---------------------------- |
| `intr`          | 中断累计次数及分项           |
| `ctxt`          | 上下文切换累计次数           |
| `btime`         | 启动时间的 Unix 时间戳       |
| `processes`     | 累计 fork/clone 创建任务数量 |
| `procs_running` | 当前可运行任务数量           |
| `procs_blocked` | 当前等待 I/O 完成的任务数量  |

累计 CPU 时间要通过两次采样的差值换算百分比，`mpstat` 已替你完成该计算。

### 3.3 `/proc/loadavg`

```bash
# [只读]
cat /proc/loadavg
```

示意：

```text
0.10 0.15 0.20 2/310 12345
```

| 字段      | 含义                                     |
| --------- | ---------------------------------------- |
| 前三项    | 1、5、15 分钟 load average               |
| `2/310` | 2 个 runnable，系统当前共 310 个调度实体 |
| 最后一项  | 最近创建任务的 PID                       |

Linux load 不只统计正在占用 CPU 的任务，还包括部分不可中断睡眠任务。
因此 load 高可能来自 CPU 排队，也可能来自大量 D 状态 I/O 等待。

### 3.4 `/proc/uptime`

```bash
# [只读]
cat /proc/uptime
```

第一项是系统启动后的秒数。第二项是所有 CPU 累计 idle 秒数，
多核机器上可能明显大于系统运行时间。

### 3.5 `/proc/schedstat`

`/proc/schedstat` 暴露每 CPU 调度统计和调度域信息：

```bash
# [只读]
cat /proc/schedstat
```

它适合：

- 观察每 CPU 运行时间、等待时间和调度次数的累计差异。
- 查看 sched domain 和 CPU mask。
- 为调度延迟分析提供低成本累计证据。

字段会随内核版本变化，必须先看内核随附文档或对应源码，
不要跨版本硬套固定列号。高层工具如 `sar`、`pidstat` 更适合日常使用。

### 3.6 `/proc/meminfo`

```bash
# [只读]
cat /proc/meminfo
free -h
```

高频字段：

| 字段                | 含义                                           | 排障提示                    |
| ------------------- | ---------------------------------------------- | --------------------------- |
| `MemTotal`        | 系统可管理物理内存总量                         | 不一定等于硬件标称容量      |
| `MemFree`         | 完全未使用的内存                               | 低不等于内存不足            |
| `MemAvailable`    | 在不触发严重回收的前提下可供新负载使用的估计值 | 比 MemFree 更适合判断余量   |
| `Buffers`         | 块设备元数据等 buffer cache                    | 通常不是主要大头            |
| `Cached`          | 文件页缓存等可回收缓存                         | 可在压力下回收              |
| `SwapCached`      | 同时仍在 swap 和内存中的页                     | 不等于当前 swap I/O 速率    |
| `Active/Inactive` | 活跃与非活跃页                                 | 需结合匿名页/文件页观察     |
| `Active(anon)`    | 活跃匿名页                                     | 常来自堆、栈、匿名 mmap     |
| `Active(file)`    | 活跃文件页                                     | 常来自 page cache           |
| `Dirty`           | 已修改、尚未写回的文件页                       | 持续上升需看 writeback      |
| `Writeback`       | 正在写回的页                                   | 与磁盘性能、脏页限流相关    |
| `AnonPages`       | 匿名页                                         | 进程私有内存的重要组成      |
| `Mapped`          | 文件映射页                                     | 共享库和 mmap 文件等        |
| `Slab`            | slab/slub 管理的内核对象                       | 分为可回收与不可回收        |
| `SReclaimable`    | 有机会回收的 slab                              | 不能保证立刻全部释放        |
| `SUnreclaim`      | 通常不可回收的 slab                            | 异常增长需找具体 cache      |
| `PageTables`      | 页表占用                                       | 大量进程/VMA 可能推高       |
| `KernelStack`     | 内核栈占用                                     | 线程数量异常时可能增长      |
| `CommitLimit`     | overcommit 模型下提交上限                      | 受模式、RAM、swap、比例影响 |
| `Committed_AS`    | 已承诺虚拟内存总量                             | 不等于已实际使用物理内存    |
| `HugePages_*`     | hugetlb 大页池                                 | 与 THP 不是同一套统计       |

判断内存压力至少联合观察：

```text
MemAvailable
swap 当前使用量与 si/so 速率
direct reclaim / kswapd 活动
major page fault
OOM 或分配失败日志
业务延迟是否同步升高
```

### 3.7 `/proc/vmstat`

```bash
# [只读]
cat /proc/vmstat
vmstat 1
```

`/proc/vmstat` 是大量虚拟内存累计事件的底层来源。常见分组：

| 前缀/字段                 | 含义                                  |
| ------------------------- | ------------------------------------- |
| `pgpgin/pgpgout`        | 页面层面的输入输出统计                |
| `pswpin/pswpout`        | swap in/out 累计量                    |
| `pgfault`               | 缺页累计次数，包括 minor fault        |
| `pgmajfault`            | major fault，通常需要外部存储参与     |
| `pgscan_*`              | 页回收扫描量                          |
| `pgsteal_*`             | 页回收成功取走的页量                  |
| `allocstall_*`          | 分配路径因回收而停顿                  |
| `compact_*`             | 内存规整尝试与结果                    |
| `thp_*`                 | Transparent Huge Page 相关事件        |
| `oom_kill`              | OOM killer 触发计数，若内核提供该字段 |
| `nr_dirty/nr_writeback` | 当前脏页和写回页快照                  |

重点看增量而不是绝对值。比如 `pgmajfault` 从启动以来很大，
但当前每秒不增长，就不能据此认定正在发生 major fault 风暴。

### 3.8 `/proc/buddyinfo`

```bash
# [只读]
cat /proc/buddyinfo
```

每一行按 node、zone 展示 buddy allocator 各 order 的空闲块数量：

```text
Node 0, zone Normal  123 456 78 9 2 1 0 ...
```

- 第 0 列是 order-0，即单页块。
- 第 1 列是 order-1，即连续 2 页。
- 第 n 列是连续 `2^n` 页。
- 高 order 长期为 0，说明大块连续物理内存稀缺，但不一定等于总内存不足。

调查高阶分配失败时，把它与以下信息对照：

```bash
# [只读]
cat /proc/pagetypeinfo
cat /proc/zoneinfo
cat /sys/kernel/debug/extfrag/extfrag_index
cat /sys/kernel/debug/extfrag/unusable_index
```

### 3.9 `/proc/pagetypeinfo`

它按 zone、order 和迁移类型展示空闲页分布：

```text
Unmovable
Movable
Reclaimable
HighAtomic
CMA
Isolate
```

它可以帮助回答：

- 高 order 块为何缺失。
- 空闲页是否被不可移动页分割。
- CMA 区域是否还有可用连续内存。
- 内存规整是否可能有效。

输出较大，推荐保存后分析：

```bash
# [只读]
cat /proc/pagetypeinfo > /tmp/pagetypeinfo.txt
```

### 3.10 `/proc/zoneinfo`

`/proc/zoneinfo` 按 NUMA node 和 zone 展示：

- present、managed、spanned 页面数量。
- min、low、high watermark。
- per-CPU page list 信息。
- 低内存保留和统计计数。

```bash
# [只读]
cat /proc/zoneinfo
```

常见关系：

```text
低于 low watermark  → kswapd 通常被唤醒后台回收
逼近 min watermark  → 分配路径可能进入 direct reclaim
回收仍无法满足      → 分配失败或进入 OOM 决策
```

具体行为还受分配标志、order、zone、memcg、保留页和内核版本影响，
不能只凭某一个 watermark 作绝对判断。

### 3.11 `/proc/slabinfo`

```bash
# [只读，通常需要 root]
cat /proc/slabinfo
slabtop -o
```

它按 slab cache 展示对象数量、对象大小和 slab 使用情况。
高频调查对象包括：

```text
dentry
inode_cache
kmalloc-*
task_struct
filp
buffer_head
网络相关 skb cache
```

判断 slab 泄漏不能只看某个 cache 很大，应观察：

1. 是否持续单调增长。
2. 业务负载下降后是否回落。
3. 对象数量还是每对象大小造成占用。
4. 该 cache 是否设计为长期缓存。
5. `SReclaimable` 与 `SUnreclaim` 如何变化。

### 3.12 `/proc/vmallocinfo`

```bash
# [只读，输出可能很大]
cat /proc/vmallocinfo
```

它列出 vmalloc/vmap 区域分配，包括地址范围、大小、调用位置和标志。
适合调查：

- vmalloc 虚拟地址空间耗尽。
- 某个调用点大量占用 vmalloc 区域。
- 模块、ioremap 或 vmap 相关问题。

读取本身可能生成大量文本，生产环境宜先限时、保存并离线筛选。

### 3.13 `/proc/diskstats`

```bash
# [只读]
cat /proc/diskstats
```

它按块设备提供累计 I/O 次数、扇区、合并、耗时、in-flight 等统计，
`iostat` 会利用这些底层计数计算每秒速率和平均延迟。

直接解析列号容易受文档版本影响。日常优先：

```bash
iostat -xz 1
```

直接读取适合：

- 工具缺失时做两点差分。
- 核对设备名和分区层级。
- 编写受控采集器。

### 3.14 `/proc/locks`

```bash
# [只读]
cat /proc/locks
```

它展示当前 POSIX lock、flock 和 lease 等文件锁，不是内核 spinlock/mutex 列表。
因此应用文件锁问题可查它，内核锁竞争则需要 perf lock、lock tracepoint 或专门调试配置。

### 3.15 `/proc/modules` 与 `/proc/kallsyms`

```bash
# [只读]
cat /proc/modules
head /proc/kallsyms
```

`/proc/modules` 可看模块名、大小、引用关系、状态和加载地址。
`/proc/kallsyms` 是内核符号表视图，地址是否可见受权限和 `/proc/sys/kernel/kptr_restrict` 控制。

用途：

- 核对驱动模块是否加载。
- 判断符号是否存在。
- 为 perf、ftrace、crash 等工具核对符号条件。
- 调查模块卸载、引用计数或 taint 相关问题。

### 3.16 `/proc/config.gz` 与内核配置

部分内核启用 IKCONFIG 后提供：

```bash
# [只读]
zcat /proc/config.gz
zgrep CONFIG_SCHEDSTATS /proc/config.gz
zgrep CONFIG_FUNCTION_TRACER /proc/config.gz
```

若不存在，再检查：

```bash
cat /boot/config-$(uname -r)
```

接口缺失时先查配置，不要立即推断是权限或工具错误。

### 3.17 `/proc/<pid>/status`

```bash
# [只读]
cat /proc/<pid>/status
```

高频字段：

| 字段                           | 含义                                        |
| ------------------------------ | ------------------------------------------- |
| `Name/State`                 | 任务名和状态                                |
| `Tgid/Pid/PPid`              | 线程组、线程和父进程关系                    |
| `Uid/Gid`                    | 身份                                        |
| `Threads`                    | 线程数                                      |
| `Cpus_allowed_list`          | CPU affinity 允许集合                       |
| `Mems_allowed_list`          | NUMA node 允许集合                          |
| `VmRSS`                      | 当前驻留内存                                |
| `VmSize`                     | 虚拟地址空间大小                            |
| `RssAnon/RssFile/RssShmem`   | RSS 组成                                    |
| `voluntary_ctxt_switches`    | 主动睡眠导致的切换累计次数                  |
| `nonvoluntary_ctxt_switches` | 被抢占等导致的非主动切换累计次数            |
| `Sig*`                       | 信号 pending、blocked、ignored、caught 状态 |
| `Cap*`                       | capability 集合                             |

### 3.18 `/proc/<pid>/stat`

单行提供 PID、comm、状态、父进程、fault、CPU 时间、优先级、nice、线程数、
启动时间、RSS、运行 CPU 等信息。

```bash
# [只读]
cat /proc/<pid>/stat
```

注意第二字段 `comm` 被圆括号包围且可能包含空格，不能用简单的空格切列解析。
脚本优先使用成熟库、`ps` 或明确遵循 procfs 文档。

### 3.19 `/proc/<pid>/sched` 与 `schedstat`

```bash
# [只读]
cat /proc/<pid>/sched
cat /proc/<pid>/schedstat
```

`sched` 常见信息包括：

- 调度策略、优先级和 nice。
- 在 CPU 上实际运行时间。
- 等待、迁移、切换等调度统计，具体字段取决于配置与版本。
- PELT 等调度实体指标，字段可能变化。

`schedstat` 是更紧凑的累计统计，常用于获得运行时间、runqueue 等待时间和时间片次数。
分析线程时应使用 TID：

```bash
cat /proc/<tgid>/task/<tid>/sched
cat /proc/<tgid>/task/<tid>/schedstat
```

### 3.20 `/proc/<pid>/stack` 与 `wchan`

```bash
# [只读，通常需要 root]
cat /proc/<pid>/stack
cat /proc/<pid>/wchan
```

- `stack` 给出任务当前内核调用栈快照。
- `wchan` 给出睡眠等待位置的符号摘要。

适合调查 D 状态、锁等待和卡住路径，但只有一个时间点：

```text
同一栈持续多次出现 → 卡住的证据更强
只读到一次某函数栈   → 可能只是正常短暂停留
```

### 3.21 `/proc/<pid>/io`

```bash
# [只读]
cat /proc/<pid>/io
```

常见字段：

| 字段                      | 含义                       |
| ------------------------- | -------------------------- |
| `rchar/wchar`           | 系统调用层请求读写的字符数 |
| `syscr/syscw`           | read/write 类系统调用次数  |
| `read_bytes`            | 实际从存储层读取的字节     |
| `write_bytes`           | 实际向存储层写出的字节     |
| `cancelled_write_bytes` | 被取消或截断的写入核算     |

page cache 会让 `rchar` 与 `read_bytes` 差别很大，这不是统计错误。

### 3.22 `/proc/<pid>/fd`

```bash
# [只读]
ls -l /proc/<pid>/fd
cat /proc/<pid>/limits
```

用途：

- 判断 fd 是否逼近限制。
- 看 socket、pipe、eventfd、anon_inode、普通文件的数量。
- 查“deleted”但仍被进程持有的文件。
- 配合 `ss -p`、`lsof` 或 inode 定位连接和文件。

### 3.23 `/proc/<pid>/maps` 与 `smaps`

```bash
# [只读]
cat /proc/<pid>/maps
cat /proc/<pid>/smaps
cat /proc/<pid>/smaps_rollup
```

| 文件             | 用途                                             |
| ---------------- | ------------------------------------------------ |
| `maps`         | 地址范围、权限、偏移、设备、inode、映射名称      |
| `smaps`        | 每个 VMA 的 RSS、PSS、匿名页、共享页、THP 等细节 |
| `smaps_rollup` | 汇总视图，读取成本和输出量通常更低               |

大型进程的 `smaps` 输出很多，频繁读取也有成本。只需总量时优先 `smaps_rollup`。

### 3.24 `/proc/<pid>/cgroup` 与 task 目录

```bash
# [只读]
cat /proc/<pid>/cgroup
ls /proc/<pid>/task
```

- `cgroup` 显示任务属于哪些控制组。
- `task` 下每个 TID 都有自己的 stat、status、sched、stack 等视图。
- CPU 高或调度延迟通常必须落到线程，而不只是进程。

### 3.25 `/proc/sysrq-trigger` 的安全边界

`/proc/sysrq-trigger` 是写入型控制接口，可触发任务栈转储、内存信息输出、
文件系统同步、重新挂载、崩溃或重启等动作。

```text
[高风险]
不要把不熟悉的字符写入该文件。
不要在生产环境试验 crash/reboot 类动作。
必须先确认 kernel.sysrq、目标字符、日志出口和恢复方案。
```

本文不提供可直接复制的崩溃或重启写入命令。

## 4. `/sys`：内核对象和设备属性

### 4.1 sysfs 的基本模型

sysfs 通常按对象组织目录，一个属性文件表达一个值：

```text
/sys
├── block/                 块设备视图
├── bus/                   总线
├── class/                 按设备类别组织
├── devices/               设备模型层级
├── dev/                   主次设备号索引
├── fs/                    文件系统和 cgroup 等
├── kernel/                内核子系统
└── module/                已加载模块及参数
```

读属性通常安全，写属性可能：

- 改 CPU online 状态。
- 改设备电源管理。
- 改队列参数。
- 解绑或绑定驱动。
- 改模块参数。

因此先通过 `stat`、`cat`、对应文档确认语义，不能把 sysfs 当普通配置文件。

### 4.2 CPU 拓扑和 online 状态

```bash
# [只读]
cat /sys/devices/system/cpu/online
cat /sys/devices/system/cpu/offline
cat /sys/devices/system/cpu/possible
cat /sys/devices/system/cpu/present
find /sys/devices/system/cpu/cpu0/topology -maxdepth 1 -type f -exec sh -c 'echo "$1: $(cat "$1")"' _ {} \;
```

常见区别：

| 文件         | 含义                             |
| ------------ | -------------------------------- |
| `possible` | 内核可能支持的 CPU 集合          |
| `present`  | 当前硬件/虚拟硬件呈现的 CPU 集合 |
| `online`   | 已上线参与调度的 CPU             |
| `offline`  | present 但未上线的 CPU           |

### 4.3 cpufreq 与 cpuidle

```bash
# [只读，接口存在时]
find /sys/devices/system/cpu/cpufreq -maxdepth 2 -type f
find /sys/devices/system/cpu/cpuidle -maxdepth 3 -type f
```

高频属性：

- 当前/最大/最小频率。
- scaling governor。
- idle state 名称、进入次数、驻留时间和延迟。
- `nohz_full`、`isolated`、housekeeping CPU 集合。

调度延迟或性能抖动可能与频率、深 idle、CPU isolation 联动，
但虚拟机中的频率数字未必代表真实宿主硬件频率。

### 4.4 NUMA node

```bash
# [只读，NUMA 系统]
ls /sys/devices/system/node
cat /sys/devices/system/node/online
cat /sys/devices/system/node/node*/meminfo
cat /sys/devices/system/node/node*/numastat
```

关注：

- CPU 属于哪个 node。
- node 的可用内存和回收情况。
- 远端访问、NUMA balancing 和内存策略。
- IRQ、设备、进程和内存是否具有合适 locality。

UMA 系统也可能只暴露 node0，不能因目录存在就断言存在多节点硬件。

### 4.5 块设备队列

```bash
# [只读]
lsblk
cat /sys/block/<dev>/queue/scheduler
cat /sys/block/<dev>/queue/nr_requests
cat /sys/block/<dev>/queue/logical_block_size
cat /sys/block/<dev>/queue/physical_block_size
cat /sys/block/<dev>/queue/rotational
```

这些属性帮助解释：

- 当前 I/O scheduler。
- 队列深度相关限制。
- 逻辑和物理扇区大小。
- 内核是否将设备视为旋转介质。

不要在故障现场未经评估直接改 scheduler 或队列深度，写入属于 `[修改状态]`。

### 4.6 网络设备队列

```bash
# [只读]
find /sys/class/net/<ifname>/queues -maxdepth 2 -type f
cat /sys/class/net/<ifname>/queues/rx-*/rps_cpus
cat /sys/class/net/<ifname>/queues/tx-*/xps_cpus
```

常见关系：

```text
RSS：网卡硬件把流量分到不同 RX queue / IRQ
RPS：内核软件把接收协议栈处理引导到 CPU mask
XPS：把发送队列选择与 CPU mask 关联
```

修改这些 mask 会改变网络处理 CPU 分布，应同时保存 IRQ affinity、队列配置和测试前后指标。

### 4.7 模块参数

```bash
# [只读]
find /sys/module/<module>/parameters -maxdepth 1 -type f
cat /sys/module/<module>/parameters/<param>
```

模块参数是否可写、何时生效、单位和边界由模块决定。
有的只在加载时读取，有的运行时写入会立即改变行为。

### 4.8 cgroup 文件系统

先判断版本：

```bash
# [只读]
stat -fc %T /sys/fs/cgroup
mount | grep cgroup
cat /proc/self/cgroup
```

- cgroup v2 常见为单一 `cgroup2` 层级。
- cgroup v1 常按 cpu、memory、blkio 等 controller 分开挂载。
- 文件名和语义不能跨版本照搬。

当前实测虚拟机为 cgroup v1，因此排查 CPU 限流时常见：

```bash
# [只读，路径按实际 cgroup 替换]
cat /sys/fs/cgroup/cpu/<group>/cpu.cfs_quota_us
cat /sys/fs/cgroup/cpu/<group>/cpu.cfs_period_us
cat /sys/fs/cgroup/cpu/<group>/cpu.stat
```

若目标机是 cgroup v2，应查看 `cpu.max`、`cpu.stat`、`cpu.weight` 等对应接口。

### 4.9 `/sys/kernel/irq/<irq>`

当前内核为部分 IRQ 暴露：

```bash
# [只读]
cat /sys/kernel/irq/<irq>/hwirq
cat /sys/kernel/irq/<irq>/chip_name
cat /sys/kernel/irq/<irq>/type
cat /sys/kernel/irq/<irq>/actions
cat /sys/kernel/irq/<irq>/per_cpu_count
cat /sys/kernel/irq/<irq>/wakeup
```

它们与 `/proc/interrupts`、`/proc/irq/<irq>` 互补：

```text
Linux virq <irq>
    ├── hwirq       中断控制器中的硬件编号
    ├── chip_name   irqchip，例如 GICv3
    ├── type        edge/level 等类型
    └── actions     注册的 handler/action 名称
```

这些文件不是所有内核版本都存在，应先 `ls /sys/kernel/irq/<irq>`。

## 5. debugfs：调试接口，不是稳定 ABI

### 5.1 确认挂载

```bash
# [只读]
findmnt -t debugfs
mountpoint /sys/kernel/debug
ls /sys/kernel/debug
```

若没有挂载，是否挂载应遵循目标环境安全策略。debugfs 可能暴露敏感信息和修改型接口，
生产环境不应为了“看看有什么”就随意开放权限。

### 5.2 debugfs 的使用原则

1. 先确认文件是否存在，不跨版本假设。
2. 先读对应内核文档、源码或驱动说明。
3. 只读接口也可能产生很大输出或持锁，需控制频率。
4. 写接口可能直接触发设备操作、故障注入或调参。
5. debugfs 文件名、格式和字段没有稳定用户 ABI 承诺。

### 5.3 调度器 debugfs

实测内核提供：

```text
/sys/kernel/debug/sched/debug
/sys/kernel/debug/sched/features
/sys/kernel/debug/sched/base_slice_ns
/sys/kernel/debug/sched/migration_cost_ns
/sys/kernel/debug/sched/nr_migrate
/sys/kernel/debug/sched/tunable_scaling
/sys/kernel/debug/sched/latency_warn_ms
/sys/kernel/debug/sched/latency_warn_once
/sys/kernel/debug/sched/numa_balancing/*
/sys/kernel/debug/sched/llc_balancing/*
```

只读查看：

```bash
# [只读]
cat /sys/kernel/debug/sched/debug
cat /sys/kernel/debug/sched/features
cat /sys/kernel/debug/sched/base_slice_ns
```

`sched/debug` 常包含：

- 每 CPU runqueue 概况。
- `nr_running`、当前任务、时钟和负载信息。
- CFS/RT/DL 等调度类的队列摘要。
- runnable task 列表或调度实体信息，具体格式随版本变化。

`sched/features` 展示可切换的调度器特性。即使文件可写，也不要在生产故障现场随意切换；
这会改变调度语义，属于 `[修改状态]`。

`base_slice_ns` 等 tunable 在不同调度器实现和版本中的含义可能变化，
不能拿旧版 CFS 的固定公式套用当前 EEVDF 或自定义内核。

### 5.4 内存碎片接口

```bash
# [只读]
cat /sys/kernel/debug/extfrag/extfrag_index
cat /sys/kernel/debug/extfrag/unusable_index
```

- `extfrag_index` 用于辅助判断高阶分配失败更像碎片还是内存不足。
- `unusable_index` 反映对特定 order 来说不可直接使用的空闲内存比例。
- 数值解释依赖内核实现，必须与 buddyinfo、pagetypeinfo、分配失败日志联合使用。

### 5.5 时钟、regulator 与设备电源

```bash
# [只读，接口存在时]
cat /sys/kernel/debug/clk/clk_summary
cat /sys/kernel/debug/regulator/regulator_summary
cat /sys/kernel/debug/pm_genpd/pm_genpd_summary
```

用于调查：

- 时钟是否启用、频率和使用计数。
- regulator 电压、状态和消费者。
- power domain 是否开启、挂载了哪些设备。

这些信息常用于驱动 probe、低功耗和 suspend 问题，不适合用来直接评判 CPU 调度性能。

### 5.6 wakeup 与 suspend

```bash
# [只读]
cat /sys/kernel/debug/wakeup_sources
cat /sys/kernel/debug/suspend_stats
```

`wakeup_sources` 可看唤醒源激活次数、事件次数、阻止 suspend 的累计时间等。
`suspend_stats` 可看 suspend 成功/失败次数及最近失败步骤、设备或 errno，字段由内核版本决定。

### 5.7 DMA、DMA-BUF 与 SWIOTLB

```bash
# [只读]
cat /sys/kernel/debug/dma_buf/bufinfo
cat /sys/kernel/debug/dmaengine/summary
find /sys/kernel/debug/swiotlb -maxdepth 1 -type f -exec sh -c 'echo "$1: $(cat "$1")"' _ {} \;
```

用途：

- 查看共享 DMA-BUF 的大小、导出者和引用情况。
- 查看 DMA engine channel 和使用摘要。
- 查看 SWIOTLB 池配置，辅助调查 DMA 映射失败或 bounce buffer 压力。

### 5.8 devices_deferred

```bash
# [只读]
cat /sys/kernel/debug/devices_deferred
```

驱动 probe 因依赖未就绪返回 defer 时，设备可能列在这里。
如果设备一直 deferred，应结合 `dmesg`、设备树/ACPI、时钟、regulator、GPIO、IOMMU 等依赖调查。

### 5.9 GPIO、I2C、regmap 等驱动接口

```bash
# [只读，接口存在时]
cat /sys/kernel/debug/gpio
find /sys/kernel/debug/i2c -maxdepth 2 -type f
find /sys/kernel/debug/regmap -maxdepth 2 -type f
```

这些接口高度依赖驱动。寄存器 dump 可能触发真实总线访问，
某些设备读寄存器还有 clear-on-read 等副作用，因此不能把所有“读取 debugfs”都视为绝对无扰动。

### 5.10 RAS、block、slab 和其他目录

常见类别：

| debugfs 路径      | 可能提供的信息                         |
| ----------------- | -------------------------------------- |
| `ras/`          | RAS daemon、错误注入或统计，依配置而定 |
| `block/`        | 块设备或 block layer 调试信息          |
| `bdi/`          | backing device writeback 状态          |
| `slab/`         | slab cache 调试属性                    |
| `memblock/`     | 启动期物理内存和 reserved 区间         |
| `iommu/`        | IOMMU 实现相关调试信息                 |
| `pinctrl/`      | pin controller、pinmux、pinconf 状态   |
| `remoteproc/`   | remote processor 状态                  |
| `virtio-ports/` | virtio console/port 信息               |

高频原则是按故障子系统进入对应目录，不要递归读取整个 debugfs。

## 6. tracefs：事件时间线的控制和数据接口

### 6.1 tracefs 与 ftrace 的关系

- tracefs 是 tracing 子系统暴露控制文件和 ring buffer 的文件系统。
- ftrace 是函数追踪和若干 tracer 的框架，也通过 tracefs 控制。
- tracepoint event tracing、kprobe/uprobe event 等能力也共享 tracefs。
- `current_tracer=nop` 只表示没有启用 function/graph 等 tracer，不妨碍独立启用 tracepoint event。

优先确定路径：

```bash
# [只读]
if mountpoint -q /sys/kernel/tracing; then
    TR=/sys/kernel/tracing
else
    TR=/sys/kernel/debug/tracing
fi
echo "$TR"
```

### 6.2 高频 tracefs 文件

| 文件/目录                       | 用途                            |
| ------------------------------- | ------------------------------- |
| `available_events`            | 可用 tracepoint 和动态事件列表  |
| `events/`                     | 按 subsystem/event 组织控制文件 |
| `events/<sys>/<event>/format` | 事件字段、类型和打印格式        |
| `events/<sys>/<event>/enable` | 单事件开关                      |
| `events/<sys>/<event>/filter` | 内核侧事件过滤                  |
| `set_event`                   | 集中启用或关闭事件              |
| `available_tracers`           | 当前内核可用 tracer             |
| `current_tracer`              | 当前选择的 tracer               |
| `tracing_on`                  | ring buffer 记录总开关          |
| `trace`                       | 当前 buffer 的快照式读取        |
| `trace_pipe`                  | 流式消费新事件                  |
| `trace_clock`                 | 时间戳时钟源                    |
| `buffer_size_kb`              | 每 CPU buffer 大小              |
| `tracing_cpumask`             | 允许记录的 CPU                  |
| `set_event_pid`               | 按 PID 限制部分事件             |
| `instances/`                  | 创建相对隔离的 tracing 实例     |
| `dynamic_events`              | 统一管理动态探针事件            |
| `error_log`                   | 动态事件或过滤表达式错误信息    |

### 6.3 安全发现接口

```bash
# [只读]
cat "$TR/available_tracers"
grep '^sched:' "$TR/available_events" | head
find "$TR/events/sched" -mindepth 1 -maxdepth 1 -type d
cat "$TR/events/sched/sched_switch/format"
```

判断事件是否存在，不能只根据文章或另一台机器：

```bash
test -d "$TR/events/irq/irq_handler_entry" && echo available
```

### 6.4 `trace` 与 `trace_pipe`

| 接口           | 行为                                             | 适合               |
| -------------- | ------------------------------------------------ | ------------------ |
| `trace`      | 读取当前 buffer 的已有内容，常用于采集结束后查看 | 有界采集和快照     |
| `trace_pipe` | 持续阻塞并消费新事件                             | 实时观察或管道处理 |

`trace_pipe` 不是永久日志；消费者跟不上时仍可能丢事件，退出后也不能回到过去补采。

### 6.5 最小 trace-cmd 采集

```bash
# [采集有开销] 采集 10 秒调度关键事件。
trace-cmd record \
  -e sched:sched_waking \
  -e sched:sched_wakeup \
  -e sched:sched_switch \
  sleep 10

# 离线查看。
trace-cmd report
```

中断与 softirq：

```bash
# [采集有开销]
trace-cmd record \
  -e irq:irq_handler_entry \
  -e irq:irq_handler_exit \
  -e irq:softirq_raise \
  -e irq:softirq_entry \
  -e irq:softirq_exit \
  sleep 10
```

使用原则：

- 只开需要的事件，不用 `-e all`。
- 采集时间先短后长。
- 记录内核版本、CPU、业务窗口和命令。
- 检查丢事件、buffer 和输出文件大小。
- `trace.dat` 可能包含进程名、路径等敏感信息。

### 6.6 手工 tracefs 的最小闭环

以下命令会修改 tracing 状态，只适合确认没有其他 tracing 使用者的实验环境：

```bash
# [修改状态][采集有开销]
TR=/sys/kernel/tracing

# 停止记录并确保本次只启用一个事件。
echo 0 > "$TR/tracing_on"
echo 0 > "$TR/events/enable"
echo 0 > "$TR/trace"

# 启用并记录短时间。
echo 1 > "$TR/events/sched/sched_switch/enable"
echo 1 > "$TR/tracing_on"
sleep 5
echo 0 > "$TR/tracing_on"

# 读取结果。
cat "$TR/trace"

# 只撤销本次启用的事件。
echo 0 > "$TR/events/sched/sched_switch/enable"
```

生产环境优先使用 `instances/<name>` 隔离，并保存所有被修改文件的原值。

### 6.7 实测 tracepoint 类别

当前虚拟机至少存在以下高频类别：

| 子系统        | 代表事件                                           |
| ------------- | -------------------------------------------------- |
| `sched`     | waking、wakeup、switch、migrate、process fork/exit |
| `irq`       | hardirq、softirq、tasklet entry/exit               |
| `ipi`       | raise、entry、exit、send                           |
| `timer`     | timer/hrtimer、tick_stop                           |
| `workqueue` | queue、activate、execute start/end                 |
| `block`     | bio、request insert/issue/complete/error           |
| `vmscan`    | kswapd、direct reclaim、shrink、throttle           |
| `kmem`      | page alloc/free、kmalloc/kfree、rss                |
| `writeback` | dirty、queue、start、written、balance              |
| `napi/net`  | NAPI poll、收包、发包、超时                        |
| `power`     | CPU idle/frequency、suspend、wakeup source         |

复杂过滤、trigger、动态探针和函数图请转到追踪专篇，本文不重复展开。

## 7. 调度维测：CPU 高、load 高与调度延迟

### 7.1 先把五种现象分开

| 现象         | 含义                          | 常见证据                          |
| ------------ | ----------------------------- | --------------------------------- |
| CPU 使用率高 | CPU 大部分时间不 idle         | `mpstat`、`top`               |
| load 高      | runnable 或部分不可中断任务多 | `uptime`、`loadavg`、任务状态 |
| runqueue 长  | 可运行任务数量超过 CPU 供给   | `vmstat r`、sched/debug         |
| 调度延迟高   | 任务被唤醒后很久才真正运行    | sched_wakeup → sched_switch      |
| iowait 高    | CPU 空闲期间存在未完成 I/O    | `mpstat %iowait`、`iostat`    |

它们可以同时出现，也可以彼此独立。例如大量 D 状态任务可能推高 load，
但 CPU 仍然很空闲；单个 CPU 忙循环可能让一核 100%，全机 load 却不高。

### 7.2 `mpstat -P ALL 1`

```bash
# [只读]
mpstat -P ALL 1
mpstat -P ALL 1 10
```

- `-P ALL`：显示总体和每个 CPU。
- `1`：每秒采样。
- 最后的 `10`：采样十次；不写则持续到 Ctrl+C。

| 字段              | 含义                          |
| ----------------- | ----------------------------- |
| `%usr`          | 默认 nice 的用户态时间        |
| `%nice`         | nice 值非默认的用户态时间     |
| `%sys`          | 普通内核态时间                |
| `%iowait`       | CPU 空闲且存在 I/O 等待的时间 |
| `%irq`          | hardirq 时间                  |
| `%soft`         | softirq 时间                  |
| `%steal`        | 虚拟机被宿主拿走的时间        |
| `%guest/%gnice` | 运行 guest vCPU 的时间        |
| `%idle`         | 空闲时间                      |

`%nice` 不是“nice 值”，而是 CPU 用于运行经过 nice 调整的普通用户任务的时间比例。
`%irq=0.00` 可能只是时间很短、四舍五入为 0，不代表没有中断发生。

### 7.3 `vmstat 1`

```bash
# [只读]
vmstat 1
vmstat 1 10
```

高频列：

| 列                       | 含义                                   |
| ------------------------ | -------------------------------------- |
| `r`                    | runnable 任务数量                      |
| `b`                    | blocked 任务数量                       |
| `swpd/free/buff/cache` | swap、空闲页和缓存概况                 |
| `si/so`                | 每秒 swap in/out                       |
| `bi/bo`                | 块设备输入/输出速率                    |
| `in`                   | 每秒中断次数                           |
| `cs`                   | 每秒上下文切换次数                     |
| `us/sy/id/wa/st`       | 用户、内核、idle、iowait、steal 百分比 |

带 interval 时，第一行在部分版本中是自启动以来平均值，后续行才是间隔统计；
解释输出前应查看本机 man page，并重点观察稳定的连续样本。

### 7.4 `top` 与线程视图

```bash
# [只读]
top
top -H -p <pid>
top -b -n 1
```

交互界面常用键：

| 键    | 作用                |
| ----- | ------------------- |
| `1` | 展开每 CPU 使用率   |
| `H` | 切换线程显示        |
| `P` | 按 CPU 排序         |
| `M` | 按内存排序          |
| `T` | 按累计 CPU 时间排序 |
| `f` | 选择显示字段        |

瞬时 100% 只表示采样窗口占满一个逻辑 CPU。在线程很多的进程中，必须用 `-H` 找到具体 TID。

### 7.5 `ps`：状态、CPU、优先级和运行 CPU

```bash
# [只读]
ps -eLo pid,tid,psr,cls,rtprio,pri,ni,stat,pcpu,comm --sort=-pcpu
ps -eo pid,ppid,stat,wchan:32,pcpu,pmem,comm --sort=-pcpu
```

常见状态字母：

| 状态  | 含义                                |
| ----- | ----------------------------------- |
| `R` | running 或 runnable                 |
| `S` | 可中断睡眠                          |
| `D` | 不可中断睡眠，常见于 I/O 或内核等待 |
| `T` | stopped/traced                      |
| `Z` | zombie，已退出等待父进程回收        |
| `I` | idle 内核线程，取决于工具版本       |

`PSR` 是最近/当前运行 CPU，`CLS` 是调度类，`NI` 是 nice。
`RTPRIO` 仅对实时策略有意义，普通 `SCHED_OTHER` 常显示 `-`。

### 7.6 `pidstat`

```bash
# [只读]
pidstat -u -p ALL 1
pidstat -t -u -p <pid> 1
pidstat -w -p <pid> 1
pidstat -r -p <pid> 1
```

| 选项   | 观察内容                                   |
| ------ | ------------------------------------------ |
| `-u` | 用户态、内核态、CPU 使用率和 CPU 编号      |
| `-t` | 展开线程                                   |
| `-w` | voluntary/nonvoluntary context switch 速率 |
| `-r` | page fault 和内存使用                      |
| `-d` | 进程 I/O                                   |

上下文切换多本身不是错误。需要结合每次切换原因、业务吞吐和延迟判断。

### 7.7 affinity、nice 和策略的只读检查

```bash
# [只读]
taskset -pc <pid>
chrt -p <pid>
ps -o pid,tid,psr,cls,rtprio,pri,ni,comm -L -p <pid>
cat /proc/<pid>/status | grep Cpus_allowed_list
```

排查要点：

- affinity 太窄可能让某些 CPU 排队，而其他 CPU 空闲。
- nice 只调节普通 fair 调度任务的相对权重，不是实时优先级。
- `SCHED_FIFO/RR/DL` 任务可能压制普通任务，应核对运行时间和优先级。
- cpuset/cgroup、CPU hotplug 和 isolation 也会限制可运行 CPU。

修改 affinity、nice 或调度策略属于 `[修改状态]`，不要把诊断命令和修复动作混为一谈。

### 7.8 debugfs 调度快照

```bash
# [只读]
cat /sys/kernel/debug/sched/debug
cat /sys/kernel/debug/sched/features
```

阅读顺序：

1. 找异常 CPU。
2. 看 `nr_running` 和当前任务。
3. 对比各 CPU 的队列、负载和 runnable 实体。
4. 检查目标任务允许 CPU 与所在 runqueue。
5. 再决定是否需要事件时间线。

快照可能在读取过程中变化，跨 CPU 信息并非严格原子快照。

### 7.9 调度四个核心 tracepoint

```text
sched_waking       唤醒方准备唤醒目标任务
sched_wakeup       目标任务已变为 runnable
sched_switch       CPU 从 prev 切换到 next
sched_migrate_task 任务迁移到另一 CPU
```

典型 wakeup latency：

```text
目标任务的 sched_wakeup 时间
             ↓ 等待 runqueue
同一任务成为 sched_switch 的 next
             ↓
两者时间差约为被唤醒到实际运行的调度等待延迟
```

必须按 PID/TID 关联，并考虑迁移、重复唤醒、任务退出和采集丢失。

```bash
# [采集有开销]
trace-cmd record \
  -e sched:sched_waking \
  -e sched:sched_wakeup \
  -e sched:sched_switch \
  -e sched:sched_migrate_task \
  sleep 10
```

### 7.10 `perf sched`

```bash
# [采集有开销]
perf sched record -- sleep 10
perf sched latency
perf sched timehist
```

- `latency` 汇总任务的调度延迟。
- `timehist` 展示调度时间线。
- 具体选项和可用字段取决于 perf 版本与内核事件。

如果 perf 与运行内核版本不一致，先执行 `perf version`、`perf list` 和一个短采集验证，不把解析失败误认为内核没有事件。

### 7.11 调度问题最短路径

```text
CPU 高
  → mpstat 区分 usr/sys/irq/soft
  → top -H / pidstat 找线程
  → perf top 或 perf record 找热点

load 高但 CPU 空闲
  → vmstat 看 r/b
  → ps 找 D 状态和 wchan
  → stack + I/O/锁/设备证据

任务响应慢
  → affinity/策略/cgroup
  → schedstat 与上下文切换
  → sched_wakeup + sched_switch 量化延迟
```

## 8. 中断维测：hardirq、softirq、affinity 与下半部

### 8.1 `/proc/interrupts` 怎么读

```bash
# [只读]
cat /proc/interrupts
watch -d -n 1 cat /proc/interrupts
```

典型 ARM64 行：

```text
           CPU0  CPU1  CPU2  CPU3
 11:       1000   900   950   980  GICv3  27  Level  arch_timer
```

| 部分           | 含义                             |
| -------------- | -------------------------------- |
| `11:`        | Linux IRQ number，即 virq        |
| CPU 列         | 该 IRQ 在各 CPU 上的累计处理次数 |
| `GICv3`      | 管理该 IRQ 的 irqchip/中断控制器 |
| `27`         | GIC 中的 hwirq/INTID             |
| `Level`      | 电平触发；另一常见类型是 Edge    |
| `arch_timer` | 注册的 irqaction/handler 名称    |

关系：

```text
设备或 per-CPU 中断源
    ↓ hwirq 27
GICv3
    ↓ irq_domain 映射
Linux virq 11
    ↓ irq_desc / irqaction
arch_timer handler
```

文件底部还可能有 NMI、IPI、timer、error 等体系结构统计，格式不一定与普通 IRQ 行相同。

### 8.2 判断 IRQ 是否集中

只看累计绝对值不够，应观察相同时间窗口内的增量：

```text
IRQ 增速集中在 CPU2
    + CPU2 的 mpstat %irq 高
    + 对应设备业务也活跃
    → IRQ 处理负载集中证据较强
```

如果计数增长快但 `%irq` 很低，可能是 handler 很短；如果 `%soft` 很高，
主要工作可能已转移到 softirq/NAPI。

### 8.3 `/proc/irq/<irq>`

```bash
# [只读]
cat /proc/irq/<irq>/smp_affinity_list
cat /proc/irq/<irq>/effective_affinity_list
cat /proc/irq/<irq>/affinity_hint
cat /proc/irq/<irq>/node
cat /proc/irq/<irq>/spurious
```

| 文件                    | 含义                                         |
| ----------------------- | -------------------------------------------- |
| `smp_affinity`        | 允许 CPU 的十六进制位图                      |
| `smp_affinity_list`   | 同一允许集合的 CPU list 表示                 |
| `effective_affinity*` | 控制器、驱动等约束后的实际有效集合           |
| `affinity_hint`       | 驱动提供给策略工具的建议，不一定等于实际设置 |
| `node`                | IRQ 关联 NUMA node，可能为 -1                |
| `spurious`            | 未处理/异常中断统计等信息                    |

affinity 不保证计数一定平均：流量、队列、设备哈希、per-CPU IRQ、managed IRQ、
CPU online 状态和 irqchip 能力都会影响实际分布。

写 `smp_affinity*` 属于 `[修改状态]`。修改前还要确认 irqbalance 是否会覆盖：

```bash
# [只读]
systemctl status irqbalance
systemctl is-active irqbalance
```

当前实测虚拟机返回 `not-found/inactive`，但这不是通用结论。

### 8.4 `/proc/softirqs` 十类含义

```bash
# [只读]
cat /proc/softirqs
watch -d -n 1 cat /proc/softirqs
```

| 名称         | 中文含义         | 核心工作                                  |
| ------------ | ---------------- | ----------------------------------------- |
| `HI`       | 高优先级 tasklet | 执行 HI_SOFTIRQ 上的旧式高优先级 tasklet  |
| `TIMER`    | 普通定时器       | 处理 timer 到期回调                       |
| `NET_TX`   | 网络发送         | 网络发送路径的延后工作                    |
| `NET_RX`   | 网络接收         | NAPI poll、协议栈接收等高频工作           |
| `BLOCK`    | 块设备           | 块 I/O 完成等延后处理，使用程度依内核版本 |
| `IRQ_POLL` | IRQ 轮询         | 块层等子系统的 IRQ poll 工作              |
| `TASKLET`  | 普通 tasklet     | 执行旧驱动调度的普通 tasklet              |
| `SCHED`    | 调度器           | 调度域负载均衡等调度延后工作              |
| `HRTIMER`  | 高精度定时器     | 需要在 softirq 中执行的 hrtimer 工作      |
| `RCU`      | RCU 回调         | 推进/执行 RCU 延迟回调等工作              |

softirq 类型是固定枚举，但每次进入可以处理一批对象。一次计数不等于一个网络包、
一个 timer 或一个回调，也不能直接比较不同类型的单位工作量。

### 8.5 `mpstat` 与 `/proc/softirqs` 联合判断

```text
/proc/softirqs：谁的次数在增长，增长在哪个 CPU
mpstat %soft：CPU 为 softirq 花了多少时间
perf/tracepoint：具体热点函数和每次事件时间线
```

例如 CPU2 的 NET_RX 累计值很高：

- 若当前增量接近 0：只是历史分布。
- 若当前增量很高但 `%soft` 低：单次处理可能较轻。
- 若当前增量和 `%soft` 都高：再查网卡 IRQ、NAPI、队列和协议栈热点。

### 8.6 `ksoftirqd/N`

```bash
# [只读]
ps -eLo pid,tid,psr,cls,rtprio,ni,pcpu,comm | grep ksoftirqd
```

- 每个 CPU 通常有一个 `ksoftirqd/N`。
- 普通非 RT 内核中，它通常是 `SCHED_OTHER`、nice 0 的内核线程。
- softirq 超出直接处理预算或被推迟时，可由它继续处理。
- 它等待工作时可以睡眠，但进入 softirq action 后仍遵守 softirq 不能睡眠的约束。
- `ksoftirqd/N` 高 CPU 表示该 CPU 存在大量推迟的 softirq 工作，需要继续区分 NET_RX、TIMER、RCU 等类型。

### 8.7 tasklet、workqueue 和 threaded IRQ 的观测

| 机制         | 执行上下文         | 观察入口                                           |
| ------------ | ------------------ | -------------------------------------------------- |
| tasklet      | TASKLET/HI softirq | `/proc/softirqs`、irq tasklet tracepoint         |
| workqueue    | kworker 线程       | `ps`、workqueue tracepoint、perf                 |
| threaded IRQ | IRQ 内核线程       | `ps`、`/proc/interrupts`、sched/irq tracepoint |

高优先级 tasklet 的“高”是 softirq 向量分发顺序，不是 `SCHED_FIFO` 实时优先级。
普通 tasklet 位于 `TASKLET_SOFTIRQ`，并不比所有其他 softirq 优先。

### 8.8 NAPI 与网络接收

典型高负载路径：

```text
网卡 IRQ
  → handler 确认事件并调度 NAPI
  → NET_RX_SOFTIRQ
  → napi_poll 批量收包
  → 协议栈
```

调查时对照：

```bash
# [只读]
cat /proc/interrupts
cat /proc/softirqs
mpstat -P ALL 1
ip -s link show <ifname>
ethtool -S <ifname>
```

若硬 IRQ 在 CPU0 而 NET_RX 主要在 CPU2，可能存在 RPS、队列映射或其他软件 steering，
不能简单要求两者必须在同一 CPU。

### 8.9 中断 tracepoint

```bash
# [采集有开销]
trace-cmd record \
  -e irq:irq_handler_entry \
  -e irq:irq_handler_exit \
  -e irq:softirq_raise \
  -e irq:softirq_entry \
  -e irq:softirq_exit \
  -e irq:tasklet_entry \
  -e irq:tasklet_exit \
  sleep 10
```

可以回答：

- 哪个 IRQ handler 进入频繁或持续较久。
- softirq 在哪里 raise、何时 entry/exit。
- tasklet 是否被频繁执行。
- hardirq/softirq 是否干扰目标任务的调度窗口。

### 8.10 中断问题最短路径

```text
某 CPU %irq 高
  → /proc/interrupts 找增速最快 IRQ
  → /proc/irq/N 和 /sys/kernel/irq/N 确认 affinity、hwirq、chip、action
  → 设备统计和 irq tracepoint

某 CPU %soft 高
  → /proc/softirqs 找增长类型
  → NET_RX：IRQ/NAPI/队列/丢包
  → TIMER/RCU/SCHED：对应 tracepoint 和 CPU 状态
  → ksoftirqd、perf 热点、事件持续时间
```

## 9. 内存、I/O、网络、日志与崩溃维测

### 9.1 内存压力的最小命令组

```bash
# [只读]
free -h
vmstat 1
grep -E 'MemAvailable|Dirty|Writeback|AnonPages|Slab|SReclaimable|SUnreclaim|Swap' /proc/meminfo
slabtop -o
dmesg -T | grep -Ei 'oom|out of memory|allocation failure|page allocation'
```

判断顺序：

```text
MemAvailable 是否持续低
  → si/so 是否持续非零，是否发生 thrashing
  → pgscan/pgsteal/allocstall 是否快速增长
  → 匿名页、page cache、slab 谁占用
  → 是全局压力、memcg 限制，还是高阶连续页失败
  → 是否已有 OOM、分配失败或业务延迟证据
```

`free` 中 used 高不是充分故障证据，Linux 会把空闲内存用于 page cache。

### 9.2 vmscan、kmem 和 writeback 事件

```bash
# [采集有开销]
trace-cmd record \
  -e vmscan:mm_vmscan_kswapd_wake \
  -e vmscan:mm_vmscan_direct_reclaim_begin \
  -e vmscan:mm_vmscan_direct_reclaim_end \
  -e kmem:mm_page_alloc_extfrag \
  -e writeback:writeback_start \
  -e writeback:writeback_written \
  sleep 10
```

- direct reclaim 落在业务分配路径，会直接增加延迟。
- kswapd 是后台回收线程，忙并不自动等于故障，但说明存在回收压力。
- `mm_page_alloc_extfrag` 帮助定位外部碎片。
- Dirty 持续积累且 writeback 慢，应继续查设备延迟和脏页限流。

### 9.3 PSI 的条件使用

支持 PSI 的机器可查看：

```bash
# [只读，接口存在时]
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

`some` 表示至少部分任务因资源等待受阻，`full` 表示所有非 idle 任务都受阻的窗口。
当前实测虚拟机没有 `/proc/pressure`，文档和脚本必须先判断文件存在。

### 9.4 `iostat -xz 1`

```bash
# [只读]
iostat -xz 1
iostat -xz 1 10
```

| 字段             | 常见含义                             |
| ---------------- | ------------------------------------ |
| `r/s、w/s`     | 每秒读写请求                         |
| `rMB/s、wMB/s` | 吞吐量                               |
| `await`        | 请求平均等待时间，字段可能拆分为读写 |
| `aqu-sz`       | 平均队列长度                         |
| `%util`        | 设备忙碌时间比例                     |

不要机械认为 `%util=100%` 就一定达到现代并行设备的性能极限；还要看设备模型、队列、
吞吐、await、业务 SLO 和控制器统计。

### 9.5 进程 I/O 和块层时间线

```bash
# [只读]
pidstat -d -p ALL 1
cat /proc/<pid>/io

# [采集有开销]
trace-cmd record \
  -e block:block_rq_insert \
  -e block:block_rq_issue \
  -e block:block_rq_complete \
  -e block:block_rq_error \
  sleep 10
```

通过 insert、issue、complete 可分解请求在队列中的等待与设备服务时间，
但需要按设备和 request 等字段正确关联，合并、重排和多队列会增加分析复杂度。

### 9.6 网络基础统计

```bash
# [只读]
ip -s link show <ifname>
ethtool <ifname>
ethtool -S <ifname>
ss -s
ss -lntup
sar -n DEV 1
cat /proc/net/softnet_stat
```

| 入口             | 主要回答                                                         |
| ---------------- | ---------------------------------------------------------------- |
| `ip -s link`   | 接口层 RX/TX packet、byte、error、drop                           |
| `ethtool`      | link、速率、双工、驱动信息                                       |
| `ethtool -S`   | 网卡和驱动私有队列/错误统计                                      |
| `ss`           | socket、监听端口、连接和 TCP 状态                                |
| `sar -n DEV`   | 周期吞吐和包速率                                                 |
| `softnet_stat` | 每 CPU 网络 backlog、drop 等十六进制统计，列定义需查目标内核文档 |

网络丢包要分层：网卡硬件、驱动 ring、softnet backlog、协议栈、socket buffer、应用消费。
某一层 drop 为 0，不能证明其他层没有丢包。

### 9.7 网络问题最短路径

```text
确认 link 与接口 error/drop
  → ethtool -S 找硬件/队列计数
  → /proc/interrupts 看网卡 IRQ 速率和 CPU
  → /proc/softirqs 看 NET_RX/NET_TX 分布
  → mpstat 看 %irq/%soft 时间
  → RSS/RPS/XPS、NAPI 与队列配置
  → napi/net/irq tracepoint 或 perf 找热点
```

### 9.8 `dmesg` 与 journal

```bash
# [只读，权限受策略控制]
dmesg -T
dmesg --level=emerg,alert,crit,err,warn
journalctl -k -b
journalctl -k -b -1
journalctl -u <service> --since '10 minutes ago'
```

- `dmesg` 读取当前内核 ring buffer，容量有限，旧消息会被覆盖。
- `-T` 的人类时间戳是换算值，时间调整后可能不精确。
- `journalctl -k -b` 按当前 boot 查询内核日志。
- `-b -1` 查看上一次启动，前提是 journal 有持久化数据。
- 日志没有报错，不代表没有性能问题或未记录的故障。

### 9.9 Oops、warn、pstore 与 vmcore

```bash
# [只读，接口存在时]
cat /sys/kernel/oops_count
cat /sys/kernel/warn_count
ls -l /sys/fs/pstore
cat /sys/kernel/kexec_crash_loaded
systemctl status kdump 2>/dev/null
```

证据优先级：

```text
console / serial 日志
  → journal 或持久 dmesg
  → pstore 保留的崩溃记录
  → 匹配版本的 vmlinux + vmcore
```

vmcore 分析必须匹配内核构建、调试符号和模块。运行时 trace 不能在 panic 后补采，
而 vmcore 也不能自动还原所有未记录的历史事件。

### 9.10 hung task、softlockup、hardlockup 和 RCU stall

| 现象       | 大意                                   | 第一证据                             |
| ---------- | -------------------------------------- | ------------------------------------ |
| hung task  | 任务长时间处于不可中断等待             | dmesg、任务 stack、wchan             |
| softlockup | CPU 长时间没有让 watchdog 线程得到运行 | dmesg、当前 CPU 栈、IRQ/抢占状态     |
| hardlockup | CPU 长时间连 NMI watchdog 进展也没有   | NMI/console、vmcore、硬件信息        |
| RCU stall  | RCU grace period 长时间无法推进        | stall 日志、CPU/任务栈、IRQ/调度状态 |

这四者可能互相关联，但名字不能互换。调查时保存完整日志，不要只截取最后一行。

## 10. 常用命令速查

### 10.1 工具、软件包与基础用法

| 命令           | 常见软件包 | 目的                     | 最小示例                                           |
| -------------- | ---------- | ------------------------ | -------------------------------------------------- |
| `watch`      | procps-ng  | 周期刷新命令             | `watch -d -n 1 cat /proc/interrupts`             |
| `top`        | procps-ng  | CPU、内存和任务概况      | `top -H -p PID`                                  |
| `ps`         | procps-ng  | 可脚本化任务快照         | `ps -eLo pid,tid,psr,stat,pcpu,comm`             |
| `vmstat`     | procps-ng  | runqueue、内存、I/O、CPU | `vmstat 1`                                       |
| `free`       | procps-ng  | 内存概况                 | `free -h`                                        |
| `mpstat`     | sysstat    | 每 CPU 时间分布          | `mpstat -P ALL 1`                                |
| `pidstat`    | sysstat    | 每进程/线程周期统计      | `pidstat -t -u -p PID 1`                         |
| `iostat`     | sysstat    | 块设备吞吐和延迟         | `iostat -xz 1`                                   |
| `sar`        | sysstat    | 系统历史/实时统计        | `sar -u -P ALL 1`                                |
| `slabtop`    | procps-ng  | slab cache 排名          | `slabtop -o`                                     |
| `perf`       | perf       | 计数、采样、热点、调度   | `perf top -a`                                    |
| `trace-cmd`  | trace-cmd  | tracefs 事件采集         | `trace-cmd record -e sched:sched_switch sleep 5` |
| `ss`         | iproute    | socket 状态              | `ss -s`                                          |
| `ip`         | iproute    | 链路、地址、路由、统计   | `ip -s link`                                     |
| `ethtool`    | ethtool    | 网卡和驱动统计           | `ethtool -S IFACE`                               |
| `dmesg`      | util-linux | 内核 ring buffer         | `dmesg --level=err,warn`                         |
| `journalctl` | systemd    | journal 查询             | `journalctl -k -b`                               |

`mpstat` 不是独立 RPM 包，安装通常使用：

```bash
# [修改状态] 安装软件包。
yum install sysstat
# 或 dnf install sysstat
```

### 10.2 perf 最常用四步

```bash
# [采集有开销] 实时热点。
perf top -a

# 计数器总览。
perf stat -a -- sleep 10

# 采样并带调用栈。
perf record -a -g -- sleep 10

# 离线报告。
perf report
```

先确认 `kernel.perf_event_paranoid`、符号、调用栈方式、采样频率和 perf/内核版本。
`perf top` 本身也消耗 CPU，不应无限期挂在高压生产机上。

### 10.3 一页故障速查

| 现象       | 立即执行                            | 需要确认的证据                  |
| ---------- | ----------------------------------- | ------------------------------- |
| CPU 高     | `mpstat -P ALL 1`、`top -H`     | usr/sys/irq/soft、异常 CPU/TID  |
| load 高    | `vmstat 1`、`ps ... stat,wchan` | r 还是 b、R 还是 D              |
| 调度慢     | `pidstat -w`、sched trace         | wakeup 到 switch 时间差         |
| hardirq 高 | interrupts + mpstat                 | 具体 IRQ 增速和`%irq`         |
| softirq 高 | softirqs + mpstat                   | 类型增速、CPU 和`%soft`       |
| 内存压力   | free + vmstat + meminfo             | available、si/so、reclaim、OOM  |
| I/O 慢     | `iostat -xz 1`、`pidstat -d`    | await、队列、设备和进程         |
| 网络丢包   | `ip -s`、`ethtool -S`           | 丢包层级、IRQ、NET_RX           |
| hung task  | dmesg + stack + wchan               | 阻塞路径、持锁者、设备进展      |
| panic      | console/pstore/vmcore               | 匹配符号、CPU、task、call trace |

### 10.4 最后检查清单

```text
□ 时间戳、主机、内核、CPU 和复现步骤是否记录
□ 数据是累计值、间隔比例、快照还是时间线
□ 是否同时观察了速率和耗时
□ 是否定位到具体 CPU、TID、IRQ、设备或 cgroup
□ 工具和内核版本是否匹配，目标接口是否实际存在
□ 采集是否限时、限范围并检查丢事件
□ 写接口是否保存原值并有恢复方案
□ 结论是否区分事实、推断和待验证假设
```

维测的核心不是记住最多命令，而是建立稳定的证据链：

```text
现象
  → 低成本统计确定子系统
  → 对象级接口确定 CPU/任务/IRQ/设备
  → 有界采集还原热点或时间线
  → 对照版本、配置和业务窗口验证因果
```
